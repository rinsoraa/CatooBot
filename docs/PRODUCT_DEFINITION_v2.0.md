# CatooBot 产品定义 v2.0

**版本日期：** 2026-10-18\
**适用范围：** CatooBot 长期产品目标、核心架构、安全原则与 Minecraft Companion Mod 的职责边界\
**模组暂定名称：** **Cato Play Minecraft Mod**

> 本文定义产品目标与架构契约，不代表任何功能已经实现或通过验收。实现进度、阶段证据与发布状态应在独立研发报告中记录，不应反向改写本产品定义。

---

## 1. 最终产品定义

CatooBot 不是“加了人设的 Minecraft 自动化工具”，也不是只会聊天、等待用户逐条下命令的 QQ Bot。CatooBot 的目标是一个能够长期存在、拥有持续角色状态与生活经历、主动形成有界想法、真正参与多人 Minecraft 游戏，并能从有证据的经历中积累可复用方法的 AI 角色。

Minecraft 是罐头生活的一部分，而不是产品的全部。她进入服务器不只是为了完成孤立的采集任务，也应逐渐能够探索、建造、合作、与熟悉的玩家互动、记住共同经历，并在能力范围内解决以前未解决的问题。

产品由三条互相连接但职责分离的能力主线组成：

1. **Life（生活）**：人格、作息、状态、需求、兴趣、目标、关系、承诺与虚拟活动持续演化。角色可以根据生活和经历主动形成想法，不必每次等待用户命令。
2. **Play（游玩）**：通过真实 Minecraft 世界观察、已注册工具与受控任务链参与游戏。实时事实、历史记忆、身份、计划、执行状态和结果必须严格区分。
3. **Learning（学习）**：从有真实证据的经历中提炼可复用方法，保存适用条件、步骤、预算、成功判据、失败边界与来源；后续任务先检索、再判断适用性，最后决定是否将方法作为计划候选。

三条主线由同一个角色身份、保留来源隔离的共享记忆，以及统一思考与执行控制层连接。不得把它们合并成没有预算、授权与退出条件的无限 LLM 循环。

## 2. Cato Play Minecraft Mod 的产品定位

**Cato Play Minecraft Mod** 是 CatooBot 的 Minecraft 伴侣模组（Companion Mod），为兼容的 Minecraft 服务端提供更可信的世界事实、玩家/方块/实体事件、动作关联证据与结果验证接口。

它是 CatooBot 的**证据与集成层**，不是独立 AI、不是第二个 Agent，也不是替代 Mineflayer 的游戏自动化器。

### 2.1 模组负责什么

- 从服务端可验证的事件中提供玩家会话、方块破坏、方块放置、实体变化、物品掉落/拾取等事实证据；具体事件按阶段单独实现和验收。
- 记录可信的服务端会话标识、维度、坐标、事件 ID、来源与事件关联关系。
- 在需要严格归因的动作前接收有界登记，并将服务端事件与登记进行唯一、幂等、可审计的匹配。
- 为世界观察提供来源、时间、新鲜度、覆盖范围以及明确的 `UNKNOWN` 语义；无法证明时不猜测。
- 向 CatooBot 提供经过认证、版本化、具备重放防护的只读接口。
- 为诊断、影子验证与后续技能学习提供可关联证据，但不直接决定角色意图或执行权限。

### 2.2 模组明确不负责什么

- 不理解自然语言，不决定罐头想做什么，不生成 LifeIntent 或 AgentPlan。
- 不授予权限、不批准任务、不改变风险等级、不绕过 Policy、TaskAuthorization、TaskStepAuthorization 或双确认门。
- 不替代 CatooBot 的任务规划、任务生命周期、动作预算、STOP/CANCEL 与独立结果核验。
- 不在服务端模组内直接执行产品动作；不因事件采集而自动挖掘、放置、攻击、传送或修改世界。
- 不把“事件发生”“方块消失”“掉落生成”“物品被拾取”“库存增加”合并为同一个成功状态。
- 不把记忆、技能、熟悉关系、离线 UUID 或玩家名称当作新授权。

### 2.3 功能依赖与降级规则

Cato Play Minecraft Mod 是逐步扩展 Minecraft 可信观察与结果归因能力的基础设施。基础聊天与不依赖服务端事件归因的现有能力不应无条件依赖模组；但需要严格服务端归因的能力，必须要求兼容模组与有效通道。

- **模组未安装或未启用：** 不伪装具有服务端归因能力；不依赖该能力的功能可以按各自安全规格运行。
- **模组启用且通道健康：** 可使用满足契约的服务端事件作为证据。
- **严格归因功能启用但通道不可用、登记缺失、事件冲突或证据过期：** 对依赖该证据的动作 fail-closed，进入既有的暂停/失败/未知结果处理；不得回退到仅凭时序推断的 `SELF_INFERRED` 并宣告严格成功。
- **影子模式：** 只记录“若使用严格归因将得到什么结果”，不得影响真实动作、任务终态、重试、库存处理或授权。

严格归因能力的缺失不能被隐式转换为成功；但也不能因此把所有不依赖该能力的 Minecraft 功能一概关闭。

## 3. 目标架构

```text
                           罐头的角色核心
          人格 / 作息 / 状态 / 需求 / 兴趣 / 目标 / 关系
                               │
              ┌────────────────┼─────────────────┐
              │                │                 │
          沙盒 Life          QQ 社交入口      Minecraft Play
       Episode/Goal/Intent        │          World Perception
              │                  │           Registered Tools
              └────────────────┼─────────────────┘
                               │
                   共享记忆与身份层（保留来源）
         沙盒经历 / QQ 关系 / MC 观察 / 玩家会话 / 技能候选
                               │
                    统一思考与执行控制层
      理解目标 → 检索事实/技能 → 判断适用性 → 计划候选
      → 前置条件/能力/风险/身份/预算检查 → 授权/确认
      → 既有任务执行链 → 真实结果验证 → 经历记录/学习候选
                               │
                 ┌─────────────┴──────────────┐
                 │                            │
      CatooBot 产品动作路径             证据与事件通道
                 │                            ▲
      TaskProposal → AgentPlan                │
      → TaskRuntime → Policy                  │
      → AgentBridge → ActionRuntime           │
      → MinecraftService → Mineflayer         │
                 │                            │
                 ▼                            │
          Minecraft 真实服务器 ◄──── Cato Play Minecraft Mod
                 │                 （服务端观察/登记/事件/关联）
                 └──────真实世界结果与独立核验──────┘
```

这是职责图而非要求源码逐字复制的层级。每个入口是否经过某个组件、哪些字段是权威事实，必须以实时源码和实际调用关系为准，不为迎合架构图重复创建组件。

### 3.1 固定产品执行链

主要产品动作沿用既有的安全基础设施：

`QQ / Minecraft Chat / WebUI / LifeIntent → TaskProposal → AgentPlan →（必要的批准/确认）→ TaskRuntime → Policy → AgentBridge → ActionRuntime → MinecraftService → Mineflayer → 真实结果验证`

各入口可有不同的调用路径，但授权来源必须可追溯。Cato Play Minecraft Mod 通过独立证据接口补充服务端事实，不得成为绕过该执行链的第二条动作通道。

### 3.2 共享状态与来源隔离

共享记忆可以关联检索，但以下数据类别必须保留差异：

- 用户陈述；
- 角色意图或 LifeIntent；
- TaskProposal；
- AgentPlan 及冻结的 `plan_hash`；
- 任务/动作运行状态；
- 客户端观察；
- 服务端事件；
- 独立世界/库存复核；
- 模型归纳与程序性技能候选。

不得把其中任何一种直接等同于另一种。服务端事件也必须带来源、会话、时间/有效期、维度和坐标等可审计字段。

## 4. Cato Play Minecraft Mod 的架构与部署约束

### 4.1 服务端权威与运行位置

需要服务端事实或严格归因的功能，原则上使用服务端侧模组。客户端本地预测、Mineflayer 缓存或客户端事件不能替代服务端事件证据。

产品长期目标可以支持两类运行环境，但必须分别验证：

1. **Fabric Dedicated Server**：模组作为服务端模组安装在服务器上。
2. **Integrated Server / 局域网开放世界**：通过兼容集成服务器的加载方式，让逻辑在集成服务器侧运行，并单独验证权限、生命周期与接口安全。不得仅通过将模组元数据改为客户端/通用环境就宣称兼容。

如果远程服务器管理员未安装兼容服务端实现，CatooBot 不得假设自己拥有相同的权威事件能力。

### 4.2 接口与安全

- 接口必须版本化、具备明确定义的 schema 与兼容策略。
- 同机通信优先使用回环地址、认证 token、HMAC、nonce、幂等事件 ID 与重放保护。
- CatooBot 与 Minecraft 不在同一机器时，不能继续假定 `127.0.0.1` 指向对端；必须采用另行审核的受保护通道，不可直接暴露未认证服务。
- 密钥不得进入 Git、Release、普通日志或对话导出。
- 登记、事件匹配、事件消费和影子记录必须幂等；旧会话、旧登记和迟到事件不得绑定新动作。
- 服务端重启、玩家重连、维度不一致、通道丢失、数据过期或候选不唯一时，按对应契约拒绝或降级为未知结果。

### 4.3 身份与会话

服务器内的玩家名称不是可信唯一身份。必须绑定当前服务器会话与服务端实际观察到的玩家标识。`online-mode=false` 时的 UUID 为离线推导 UUID，不应称为在线认证身份；需使用 `session_ref`、会话序号及当前连接上下文防止旧事件重用。

跨 QQ / Minecraft 的身份关联仍使用既有 Identity Bridge：

- `CANDIDATE` 仅为线索，不可用于受保护操作；
- `VERIFIED` 只能在已验证范围内使用；
- `CONFLICT`、`REVOKED`、`MISSING` 阻止依赖该关联的操作。

### 4.4 证据等级与归因语义

严格归因至少区分：

- `SELF_CONFIRMED`：有可信、唯一匹配、当前会话、当前 `action_id` 与目标一致的服务端玩家破坏证据；
- `EXTERNAL_CONFIRMED`：只有存在正面证据证明具体外部来源时才使用；
- `UNKNOWN`：没有足够证据、缺少事件、通道不通、存在歧义或事件失效；
- `REJECTED`：身份、认证、会话、签名或防重放检查不通过；被拒绝事件不能产生成功归因。

`UNKNOWN` 与 `EXTERNAL_CONFIRMED` 不可互换。没有收到事件只代表尚未证明，不自动证明某个特定外部来源。

方块破坏归因只说明破坏行为的归属，不证明掉落生成、物品拾取、库存净增或整个任务已完成。不同结果必须分别观察和核验。

## 5. Play：真实 Minecraft 游玩原则

### 5.1 先观察，再计划与执行

游玩系统必须通过当前、可信且带新鲜度/来源的观察确认目标、维度、坐标、实体、材料、危险与前置条件。LLM 可以理解意图或提供计划候选，但不能自行决定权限或把陈述变成世界事实。

### 5.2 能力按风险逐步扩展

- **聊天与观察**：普通聊天、实时世界查询、库存查询、实体/方块观察。
- **移动与跟随**：有界目标、距离、时间和重试预算；支持权威 STOP/CANCEL。
- **资源采集**：目标白名单、工具与耐久、危险地形、动作预算、掉落/拾取/库存分离验证。
- **合成**：使用真实配方与库存规划、冻结计划、外部变化后重新观察与重规划。
- **放置与建造**：区域、数量、材料、目标占位、支撑面、授权和每步后置验证。
- **敌对生物交互**：目标白名单、实时实体身份、生命/装备检查、距离/时长/攻击次数限制与撤退条件。
- **物品交付与合作**：可信接收对象、身份绑定、数量、交付状态与拾取状态分别验证。
- **共同经历**：与可信玩家合作、记录重要事件、基于证据更新关系与角色生活状态。

Cato Play Minecraft Mod 可以逐步为这些能力提供服务端证据，但不因新事件类型而自动获得执行权限。

### 5.3 世界变化与失败处理

观察过期、目标移动/消失、维度改变、路径失败、材料变化、事件缺失、服务离线或后置状态不一致时，系统必须按既有策略停止、重新观察、重规划、澄清或给出明确失败/未知结果。不得静默换目标或虚报成功。

## 6. Life：角色生活与有界主动性

- 作息、需求、情绪/状态、兴趣、关系、承诺和生活经历持续演化。
- 主动想法来自角色状态、已有经历、兴趣及当下情境，不是无依据随机生成无限任务。
- `LifeIntent` 只是候选意图，不代表任务已经创建、目标已经发生或获得执行授权。
- 每个自主目标必须有目的、期限、动作/时长预算、停止条件、冷却与重复抑制。
- 角色忙碌、休息、低生命、材料不足、观察缺失、服务不稳定或冲突任务存在时，应延期、澄清或放弃目标。
- 用户 STOP/CANCEL 优先于故事性计划、后台学习或模组事件处理。

## 7. Learning：经历与程序性技能

重要经历应尽可能关联：意图/输入、观察快照、计划版本及 `plan_hash`、任务 ID、`action_id`、授权来源、服务端事件、任务结果、独立后置验证、失败原因与环境条件。

技能候选至少包含：唯一标识/版本、来源事件、适用条件、所需材料/工具、风险与权限前提、步骤、预算、停止条件、成功判据、失败边界、反例、置信度与最后验证时间。

- 事实与执行轨迹先记录，技能候选后生成。
- 只有独立验证的成功经历才支持成功方法；失败也可形成边界/反例。
- 下次执行前重新检查世界、身份、库存、工具、版本与权限。
- 技能只作为 AgentPlan 的候选方法，不注册新工具、不扩大权限、不跳过确认。
- 通过多次受控复现评估成功率、耗时、重试、失败类型与副作用；一次成功不等于普遍学会。

## 8. 统一安全与真实性原则

1. **Fail closed**：无效模型结果、目标歧义、身份冲突、观察缺失/过期、工具未注册、预算超限或服务中断时，不执行未授权动作。
2. **没有旁路**：模组不得经命令、直接世界写入、数据库写入或其他私有通道绕过产品执行链。
3. **有界执行**：目标、动作数量、距离、时长、重试、路径长度与循环频率有集中且可审计的上限。
4. **及时取消**：STOP/CANCEL 不得被模型调用、事件重试、路线搜索或影子统计阻塞。
5. **可归因**：意图、计划、动作、服务端事件与独立结果是不同证据类型。
6. **结果独立验证**：工具或任务报告成功不能自动证明所有世界副作用发生。
7. **失败不被抹除**：保留首次失败、重试与撤回修复的原始证据；不放宽门槛凑 PASS。
8. **最小扩展**：先复用既有 TaskRuntime、Policy、ActionRuntime 和验证链，再增添经论证的能力。
9. **模组故障隔离**：事件监听/传输/统计失败不得崩溃服务器、阻塞 STOP/CANCEL 或伪造结果。
10. **阶段分离**：影子模式只观测和统计；只有经过单独审批与验收，才可让严格归因参与任务终态。

## 9. 兼容性与发布原则

Cato Play Minecraft Mod 应以兼容矩阵和独立 Release 管理。每个发行包至少提供：

- 针对明确 Minecraft / Fabric Loader / Fabric API 组合的 `.jar`；
- SHA-256 校验值；
- 安装、配置、启用/禁用、升级、回滚说明；
- 事件/API schema 版本、已知限制与迁移说明；
- 不含密钥、私有服务器数据或敏感日志的可复现构建信息。

在兼容性、真实性和安全门禁完成前，不将实验构建标记为稳定版。Dedicated Server 与 Integrated Server 支持需分别验证；不支持的服务端平台应明确说明，不能暗示通用兼容。

## 10. 一句话摘要

**CatooBot 是一个以持续角色生活为内核，通过统一的受控执行链真实参与 Minecraft、并从可归因经历中积累可复用技能的长期 AI 角色；Cato Play Minecraft Mod 为兼容服务器提供可信观察与事件证据，但 Life 负责形成有意义的目标，Play 负责在授权边界内执行，Learning 负责改善未来计划，三者及模组均不得绕过实时观察、身份、Policy、用户/策略授权、动作预算、STOP/CANCEL 与独立结果验证。**
