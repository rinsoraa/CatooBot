# CatooBot 产品与研发路线图 Rx v3.0

**版本日期：** 2026-10-18\
**核心原则：** Life（生活）· Play（游玩）· Learning（学习）共用一个角色身份与统一执行控制层；Cato Play Minecraft Mod 为 Minecraft 提供可信观察、事件与结果归因能力；不把 CatooBot 建成无限循环的 Minecraft 自动化工具。

> 本文只定义长期路线、依赖关系与验收出口，不展示当前进度或实时仓库状态。阶段编号 Rx 用于产品路线索引，不重命名、不覆盖仓库已有的历史 Phase、提交、报告或失败记录。

---

## 1. 路线图概览

| 路线阶段 | 主题 | 目标出口 |
|---|---|---|
| **R0** | 收敛既有安全与可靠性缺口 | 目标一致性、导航边界、证据链与文档口径可审计；运维迁移工作独立验收 |
| **R1** | 真实世界感知、导航与目标生命周期 | 世界观察有来源/覆盖/新鲜度；导航结果可复现；目标变化、维度变化与动作归因不产生假成功 |
| **R2** | Life → Play 目标桥接与有界主动性 | Life 可提出有限目标；执行仍由既有 TaskProposal、AgentPlan、Policy、授权和预算链控制 |
| **R3** | 通用有界资源采集 | 逐类实现采集、破坏、掉落、拾取与库存净增的独立验证 |
| **R4** | 受限方块放置与简单建造 | 固定区域、材料、数量、授权与每步结果验证 |
| **R5** | 有界敌对生物交互与战斗安全 | 目标白名单、装备/生命检查、攻击/追击预算与撤退/取消策略 |
| **R6** | 玩家物品交付与合作交互 | 可信对象、身份绑定、交付/丢出/拾取/未知状态分离 |
| **R7** | 游戏经历回流与程序性技能闭环 | 有来源的经历生成可检索技能候选，并经适用性判断与受控复现验证 |
| **R8** | 端到端简单游玩与长期角色验收 | Life、Play、Learning 在真实服务器与长期会话中形成有证据的闭环 |

“存在底层设施”不等于对应路线阶段完成。每个阶段必须按自己的验收出口判定，不能用单元测试、某个子阶段 PASS 或 CI 全绿替代真实闭环。

## 2. 产品架构更新：引入 Cato Play Minecraft Mod

### 2.1 更新后的逻辑架构

```text
                             罐头的角色核心
               人格 / 作息 / 状态 / 需求 / 兴趣 / 目标 / 关系
                                      │
                   ┌──────────────────┼──────────────────┐
                   │                  │                  │
                Life 系统            QQ 入口          Minecraft Play
             Episode/Goal/Intent        │             感知/计划/工具
                   └──────────────────┼──────────────────┘
                                      │
                         共享记忆与身份层（来源隔离）
                   Life / QQ / MC 观察 / 会话 / 技能候选
                                      │
                            统一思考与执行控制层
            意图理解 → 记忆检索 → 适用性判断 → 计划候选 → 风险检查
                   → 授权/确认 → 既有任务链 → 独立结果核验
                                      │
            ┌─────────────────────────┴─────────────────────────┐
            │                                                   │
       产品动作执行路径                                    服务端证据路径
 TaskProposal → AgentPlan                         Cato Play Minecraft Mod
 → TaskRuntime → Policy                           会话/世界/玩家/方块事件
 → AgentBridge → ActionRuntime                    动作登记/唯一关联/影子记录
 → MinecraftService → Mineflayer                  可信事件/覆盖/新鲜度
            │                                                   ▲
            ▼                                                   │
                   Minecraft 真实服务器 ────────────────────────┘
                        │
          真实方块 / 实体 / 掉落 / 拾取 / 玩家 / 世界状态
                        │
              结果核验 → 经历归因 → 学习候选 → 共享记忆
```

架构图表达职责，不要求源码中机械复制每一层。Cato Play Minecraft Mod 是服务端证据与集成能力，不是第二个执行器；正常游戏动作仍沿用 CatooBot 的既有执行链。

### 2.2 Cato Play Minecraft Mod 的长期职责

模组的长期目标是为兼容 Minecraft 服务端提供：

- 服务端玩家会话与维度信息；
- 带来源、会话与坐标的方块/实体/玩家事件；
- 按动作登记、服务端事件唯一匹配的归因证据；
- 世界观察的来源、新鲜度、覆盖状态与未知语义；
- 按能力阶段逐步扩展的放置、破坏、掉落、拾取与其他结果事件；
- 经过认证、版本化、具备幂等和重放保护的只读通信接口。

模组不负责自然语言理解、LifeIntent、AgentPlan、Policy、批准/确认、游戏动作执行或独立任务成败判定。模组中的任何状态都不能直接授予权限。

### 2.3 模组运行位置与能力边界

产品设计考虑两种运行环境，并要求分别进行兼容性验收：

1. **Fabric Dedicated Server**：在兼容的独立服务器实例中安装服务端模组。
2. **Integrated Server / 局域网开放世界**：通过兼容集成服务器的加载方式运行服务端逻辑，并单独验证生命周期、身份、安全与接口行为。

普通客户端安装不能替远程服务器提供服务端权威事件。第三方服务器需要管理员部署兼容实现，才可提供同等严格归因能力。

模组不可用时，不依赖它的基础功能可以按自身规格运行；需要严格服务端归因的功能必须按安全策略暂停、失败或返回未知结果，不得回退到仅凭时序推断的成功。

## 3. 各路线阶段说明

## R0 — 收敛既有安全与可靠性缺口

**目标：** 在扩展更多游戏动作前，先使既有计划/目标/动作语义与证据链可信、可审计。

### 工作范围

- 收敛已有待决提案与用户新目标冲突的问题，避免接受语句吞掉新的树种、数量、合成目标或其他意图。
- 复核导航不可达、路径中断、动作超时、暂停、取消与最终位置之间的关系；不以传送或放宽阈值替代真实导航能力。
- 统一日志关联：入口/session → 决策类别 → 提案/任务 ID → 冻结 `plan_hash` → `action_id` → 执行结果 → 独立世界/库存快照。
- 保留历史失败和文档冲突的原文，以追加更正修复口径，不抹除旧证据。
- 数据库真实成功迁移演练作为独立运维/质量工作跟踪，不与 Minecraft 功能验收混为一谈。

### 验收出口

新目标不能静默消费旧提案；STOP/CANCEL 保持权威；导航状态与真实坐标一致；缺失证据明确记为缺失；每一项结论都能追溯输入、计划、动作与真实结果。

## R1 — 真实世界感知、导航与目标生命周期

**目标：** 为后续采集、建造、战斗与合作建立可信的世界事实、可达性和结果归因基础。

### R1.1 感知与覆盖

- 观察带来源、时间、新鲜度、维度和覆盖状态。
- 将 `COMPLETE`、`PARTIAL`、`UNKNOWN` 等覆盖语义传递给消费端；只有完整覆盖才允许将空命中解释为明确“没有目标”。
- 服务离线、断线、重连或空载荷时，旧观察不得伪装为实时数据。
- 对独立观察来源如实标注证据等级，不能将同一来源的不同读取冒充第三方独立证据。

### R1.2 导航可靠性

- 真实坐标、路径状态、目标距离、到达阈值与任务状态必须一致。
- 覆盖平地、绕障、高差、不可达目标、路径搜索超时、目标丢失、观察过期、断线、STOP/CANCEL、迟到事件等场景。
- 成功必须经实际位置重新读取验证；失败关闭本身不能算作可达路径可靠性通过。
- 不自动搭桥、不自动破坏方块绕路，不通过 `/tp` 替代产品导航证据，不无依据放宽距离/时间/重试阈值。

### R1.3 目标、维度与动作归因

- 计划冻结目标、期望方块、坐标、维度与观察证据；关键动作前检查目标仍有效。
- 目标被移除、替换、换维度或信息过期时，不静默改选邻近目标，也不继续把旧目标当作有效对象。
- 引入 Cato Play Minecraft Mod 的服务端破坏事件关联，区分“世界发生变化”和“当前动作造成变化”。
- 方块破坏归因与掉落、拾取、库存净增独立核验。

### Cato Play Minecraft Mod 的技术验收门

这些 P 编号是模组专项内部的技术里程碑，不与 Rx 路线编号混用：

- **P1 — 事件可行性实验**：通过真实服务器对照确认玩家破坏事件的实际行为、命令修改是否触发、回调前后状态与身份字段；保留实测和未验证边界。
- **P2 — 登记/事件通道与影子模式**：服务端会话绑定、动作登记、唯一匹配、认证、幂等、重放防护、客户端影子接收与统计。影子结果不影响任务终态。
- **P3 — 严格归因接入**：经独立批准后才将 `SELF_CONFIRMED` 作为动作成功所需的一项证据，完成外部移除、他人破坏、事件缺失、通道故障、重复/迟到事件、重启和 STOP/CANCEL 竞态的真实验证。

P1 的事件可用性不能证明动作关联正确；P2 的影子匹配不能证明终态安全；只有 P3 完成真实执行窗口验收，才可关闭对应的目标归因缺口。

### R1 验收出口

世界观察可被追溯且具备覆盖/新鲜度契约；路径成功有真实位置证明；无法确认时保留失败/未知语义；维度和目标不匹配时零意外动作；严格归因只在唯一可信服务端事件匹配时成立，且不推断拾取或库存成功。

## R2 — Life → Play 目标桥接与有界主动性

**目标：** 让罐头能从生活状态、需求、承诺、兴趣、既有经历与当前情境产生有限游戏目标，同时不建立第二套执行控制系统。

### 工作范围

- 审计并复用现有 LifeIntent、Episode/Goal、TaskProposal、AgentPlan 与当前任务入口。
- Life 只生成带来源和原因的意图/目标候选，不直接调用 Minecraft 工具、不创建授权。
- 候选目标经过实时世界/库存观察、目标可行性、身份、风险、预算、冲突任务和角色状态检查，再进入既有任务链。
- 自主目标必须有期限、步数/时长/动作预算、冷却、重复抑制与停止条件。
- 尊重 `allow_medium` 默认值、双确认契约与现有工具白名单；记忆和技能不能增加权限。

### 验收出口

Life 能提出有限目标；缺失或过期事实不被伪装为真实；已有任务冲突时不叠加执行；提案不等于任务、计划不等于执行、记忆不等于授权；用户 STOP/CANCEL 始终优先。

## R3 — 通用有界资源采集

**目标：** 从已验证的低复杂度资源垂直闭环扩展到更多资源家族，每一类资源独立定义工具、风险、预算与验证契约。

### 工作范围

- 每类资源定义目标白名单、观察覆盖、新鲜度、工具等级/耐久、距离、数量、时长与动作预算。
- 逐类处理危险方块、液体、洞穴、坠落、路径可达性、目标消失和工具不足。
- 使用 Cato Play Minecraft Mod 提供的服务端事件作为可用证据，但不把服务端模组的存在当成采集成功本身。
- 明确区分方块破坏、掉落生成、拾取事件和库存净增；必要时用独立库存快照确认。
- 结果未知时保持 `UNKNOWN` 或既有非成功状态，不通过自动放置/破坏路径绕行偷渡 R4 能力。

### 验收出口

每种资源在真实服务器上有正向、拒绝、工具不足、目标失效、路径失败、掉落/拾取不确认、库存核验及 STOP/CANCEL 的独立证据；不满足前置条件时不执行未经批准的动作；成功记录不依赖推断性归因。

## R4 — 受限方块放置与简单建造

**目标：** 允许少量、明确目标、范围固定的方块放置，不支持无限自由建造。

### 工作范围

- 明确风险等级、授权、目标坐标/维度、区域边界、最大方块数、朝向、支撑面、占位、材料和背包空间。
- 每次放置前重新读取目标位置并检查外部变化。
- 记录每个 `action_id`，使用服务端放置事件或可信世界快照验证结果。
- 设计取消、超时、部分完成和失败后的恢复策略。
- 首期可从单个工作台、火把等简单放置开始；自动搭桥、自动拆除、大面积地形改造、爆炸物与红石机关不属于首期范围。

### 验收出口

确认前无世界修改；参数、数量、区域和授权冻结；每一步都可审计并核验实际方块；外部占位变化时不覆盖未知方块，不宣告完整成功。

## R5 — 有界敌对生物交互与战斗安全

**目标：** 仅在明确请求或明确策略允许时，对真实观察到的白名单敌对目标执行短时、有限交互。

### 工作范围

- 明确实体白名单、UUID/会话身份、当前位置与观察时间；玩家、村民、宠物/驯服实体默认禁止攻击。
- 检查生命、饥饿、装备、武器与耐久、逃离路径。
- 限制目标距离、攻击动作数、持续时间和追击距离。
- 不追入未知洞穴、熔岩、深水或高坠落风险区域。
- 通过 Cato Play Minecraft Mod 的实体/伤害/死亡事件（在对应能力完成独立验证后）与世界观察核对结果。
- 明确撤退、低生命、目标丢失、玩家进入区域、掉线、超时与 STOP/CANCEL 的处理。

### 验收出口

目标身份可信、攻击策略受限、攻击结果和死亡/经验/掉落分别验证；无无限巡逻、无限追击、PVP 或自主搜寻玩家；取消和撤退可及时执行。

## R6 — 玩家物品交付与合作交互

**目标：** 在对象身份可信、数量明确、授权成立时完成有限物品交付与合作行为，并准确表达真实结果。

### 工作范围

- 复用 Identity Bridge；`CANDIDATE` 不可授权，`CONFLICT`/`REVOKED`/`MISSING` 阻止相关操作。
- 目标玩家必须来自当前服务器会话内的可信观察，而不是只凭历史昵称。
- 使用明确交付状态区分：
  - `NOT_DROPPED`：没有发生丢出/交付动作；
  - `DROPPED`：物品丢出或交付动作已发生；
  - `PICKUP_CONFIRMED`：目标玩家拾取有直接证据；
  - `UNKNOWN`：物品状态变化但归属或最终结果无法确认。
- 使用模组可提供的玩家、掉落与拾取事件辅助归因；不把 `DROPPED` 直接当成 `PICKUP_CONFIRMED`。
- 对数量、背包变化、多人争抢、目标离开、事件丢失、超时与迟到事件设计幂等处理。

### 验收出口

身份/物品/数量可复核；确认前不交付；目标离开或竞争拾取时准确报告；无证据保留 UNKNOWN；不通过命令或数据库写入旁路交付。

## R7 — 游戏经历回流与程序性技能闭环

**目标：** 把真实任务经历转化为可检索、可评估、可复用和可撤回的方法，而不是把聊天摘要直接保存成技能。

### 工作范围

- 将 Life、QQ、Minecraft 事件、观察快照、任务/动作轨迹、服务端事件及独立后置验证关联起来，同时保留每类数据的来源和证据级别。
- 服务端事件只是其中一种证据；不能把模组输出自动当成整个任务成功。
- 技能候选记录唯一版本、来源事件、环境前提、所需资源/工具、授权前提、步骤、预算、成功判据、失败边界、反例和最后验证时间。
- 下次任务先检索技能、检查当前适用性，再把技能作为 AgentPlan 候选方法。
- 通过受控复现对比成功率、耗时、重试、失败原因和副作用；不因一次成功宣称学会。
- 记忆/技能不注册新工具，不扩大权限，不替代实时观察；跨重启恢复需通过版本与迁移测试。

### 验收出口

至少有带真实证据的技能候选、后续检索与适用性判定、反例处理、失败经历留存、版本兼容与重复复现实验；技能复用不改变授权规则。

## R8 — 端到端简单游玩与长期角色验收

**目标：** 验证 Life、Play 与 Learning 是同一个长期角色的互联系统，而不是若干独立工具的集合。

### 真实服务器用例矩阵

- 自然语言聊天、查询、世界观察、库存与实体信息；
- 有界移动、跟随、停止、取消、目标丢失与重新观察；
- 受限资源采集、服务端破坏归因、掉落/拾取/库存核验；
- 基础合成、工作台合成、缺料交接与重新规划；
- 受限放置与简单建造；
- 受限敌对生物交互及撤退；
- 玩家物品交付与拾取状态区分；
- LifeIntent 候选目标、冷却、重复目标抑制、已有任务冲突；
- 经历进入共享记忆/技能候选并在后续任务检索和验证；
- 歧义、拒绝、无效模型输出、Provider/服务端离线、维度变化、未知覆盖、身份冲突、外部世界变化、重复/迟到事件、重启与取消竞态。

### 验收出口

每个闭环都能从意图/输入追溯到决策、观察、计划、授权、动作、真实结果与经历回流。Cato Play Minecraft Mod 提供的证据必须与产品事件链关联，但不能代替 TaskRuntime、Policy 或独立结果验证。任何未知结果保留 UNKNOWN/失败，不推测成功。

## 4. 跨阶段工程与安全门禁

每个阶段都必须提供以下交付，不因模组接入而减少：

1. 开工 SHA、真实工作区状态、远端/镜像一致性、依赖和受保护区域审计。
2. 明确范围、非目标、风险、权限与回滚方案。
3. 正向、拒绝、歧义、异常、超时、重复、迟到、取消与零副作用测试矩阵。
4. 真实 Provider 语义验证、E2 单元/集成验证、E3 真实服务器验证、E4 独立结果复核分别报告。
5. 环境夹具、第二客户端、命令准备、事件注入与真实产品执行证据分开标注。
6. `session_ref`/`action_id`/任务 ID/`plan_hash`、事件 ID、授权来源、真实世界/库存前后快照与后置验证可关联。
7. `pytest tests -q`、Node 测试、ruff、format、mypy、`git diff --check`、凭据扫描与 CI。
8. 保留首次失败与修复撤回原始证据；不得只记录最终成功重跑。
9. 模组版本、Minecraft/Fabric 兼容性、接口 schema、禁用开关、部署/升级/回滚必须可审计。
10. `PASS`、`PARTIAL`、`BLOCKED` 按实际 DoD 裁决；模组构建成功或 CI 全绿不能代替真实世界闭环。

## 5. Cato Play Minecraft Mod 的发布与兼容路线

模组作为正式产品组件，建议在仓库中维护源码、可复现构建、测试和兼容矩阵，并在 GitHub Releases 发布经过对应门禁验证的 `.jar`。

每个 Release 应包含：

- 明确的模组版本和兼容的 Minecraft、Fabric Loader、Fabric API 组合；
- `.jar` 与 SHA-256 校验值；
- 安装、配置、启用/禁用、升级和回滚说明；
- API/schema 版本与兼容策略；
- 已知限制、安全边界、测试证据与变更说明；
- 不包含 token、密钥或私人服务器数据。

发布分为实验构建、候选构建与稳定版本。只有完成对应 E2/E3 验收的能力才能在 Release 说明中声明支持。

### 各服务器类型的兼容原则

- Fabric Dedicated Server：在声明支持的服务端版本上安装服务端模组。
- Integrated Server / LAN：另行验证集成服务器运行方式、生命周期与安全边界；不因专用服务器可运行就默认兼容。
- 第三方远程服务器：需要管理员部署兼容的服务端实现；客户端单独安装不能提供远程服务端权威事件。
- 不兼容平台：清楚声明无法提供依赖该模组的严格归因功能，不得静默模拟成功。
