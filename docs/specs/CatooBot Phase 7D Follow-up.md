## 0. 角色与任务

你现在负责 CatooBot 仓库的资深 Python / Node.js / Mineflayer 工程工作。

这不是一个单纯的挖掘成功判断问题，而是一个跨越 Minecraft Runtime、TaskRuntime、技能学习资格门与 Minecraft 长期记忆的执行结果归因问题。

## 1. 产品不变量

必须遵守 CatooBot 产品定义及以下原则：

1. 当前世界事实、历史记忆、任务计划、执行状态和执行结果是不同类别的证据，不能互相冒充。
2. `Task SUCCEEDED` 只说明任务的总体完成条件得到满足，不自动证明其中每一次世界修改都由罐头造成。
3. 工具调用成功、`bot.dig()` 完成、方块消失、背包增加、掉落物出现、耗时符合预期，均不能在没有相应因果证明时被单独升级为“罐头亲手挖掉了这个方块”。
4. 不能将无法归因的环境变化计为技能方法失败，也不能将其计为技能成功学习样本。
5. 角色长期记忆不得把未经归因的结果记录成“罐头亲手挖过”。
6. 普通聊天、LLM 自述、任务目标文字和模型置信度不能替代执行证据。

## 3. 第二阶段：审计实际可用的归因信号

检查当前依赖版本中以下事件、协议包和数据的真实语义：

- `bot.dig()` Promise 的完成条件。
- `diggingCompleted` / `diggingAborted`。
- `world` 的 `blockUpdate` 和坐标级更新事件。
- `blockBreakProgressObserved`、`blockBreakProgressEnd`（如果当前依赖版本提供）。
- 事件携带的实体 ID、实体身份与目标坐标。
- 罐头自己发送的挖掘动作、服务端确认，以及相关数据包的关联机制。
- 挖掘前后的目标方块状态。
- 挖掘前后的背包快照。
- 掉落物实体的生成、移动、消失及对应坐标。
- 动作开始、结束时间、超时、取消、断线和重连。
- 事件顺序、重复事件及延迟到达的事件。

对每种信号明确记录：

1. 它能证明什么。
2. 它不能证明什么。
3. 是否能可靠地对应当前 `action_id` 和目标坐标。
4. 是否具有真实的执行者身份信息。
5. 是否可能由其他玩家的行为触发或被并发世界变化污染。

**关键限制：不要把没有观察到其他玩家的破坏动画当成罐头自行完成挖掘的证明。**

同样，不得仅凭 `bot.dig()` 成功返回、目标位置变为 `air`、背包增量正确或挖掘耗时达到预期，就判定归属为自己。

如果当前 Java 客户端协议或 Mineflayer 事件没有提供充分的、与本次动作有因果关联的执行者证据，应明确记录这一技术边界。不得伪造服务端回执或虚构不存在的 Mineflayer 事件。

## 4. 第三阶段：建立分离的挖掘结果与归属模型

为挖掘动作建立结构化、可持久化、可审计的结果契约。

至少区分两个维度：

### A. 世界效果

表示目标方块的实际状态：

- `BLOCK_REMOVED`
- `BLOCK_REMAINS`
- `UNKNOWN`

具体枚举命名可遵循项目现有风格，但语义必须明确。

### B. 行为归属

至少支持：

- `SELF_CONFIRMED`：有可靠、与当前动作及目标对应的证据，足以证明罐头亲自完成了此次挖掘。
- `EXTERNAL_INDICATED`：有明确的外部玩家行为线索，但仍须依据证据强度区分“观察到他人正在挖掘”和“能够证明他人完成了移除”。
- `AMBIGUOUS`：方块变化已发生，但无法可靠确认行为归属。

如果实际发现了一种能够可靠确认其他玩家完成移除的来源，可使用独立的外部确认状态；如果无法证明，不得使用 `EXTERNAL_CONFIRMED` 这样的过强结论。

具体字段可包含：

- 归属判定及稳定原因码。
- 本次 `action_id`。
- 目标方块名称、坐标和维度 / 会话标识（现有架构能够提供时）。
- 方块变化前后的观察结果。
- 动作时间范围。
- 实际使用的证据来源及关键事件摘要。
- 必要的冲突或不确定性标记。

字段设计应最小化，优先使用当前 TaskStep 已有的持久化 `result` / JSON payload，而不是为了多几个字段就创建新表。

世界效果和行为归属必须互相独立。例如：

```text
world_effect = BLOCK_REMOVED
attribution  = AMBIGUOUS
```

这是允许且必须能正确表达的结果。

**不能为了让 TaskRuntime、WebUI 或技能学习模块更方便，而强行把上述结果折叠成 `SELF_CONFIRMED`。**

## 5. 第四阶段：修复 Minecraft Runtime 的归因根因

在 `minecraft_runtime/runtime.js` 中，围绕现有 `dig` 动作进行最小必要修改。

要求：

1. 为一次挖掘建立明确的动作级证据范围，与当前 `action_id`、目标方块、坐标、会话和时间范围关联。
2. 对实际可用的 Mineflayer / 协议事件使用精确的目标过滤，避免将其他坐标、其他区块、其他会话或上一次动作的事件混入当前结果。
3. 如果可靠的服务端/协议确认可以提供执行者归属，则必须验证该信号的语义、时序及其与本次动作的关联。
4. 对其他玩家在动作执行前、执行中以及即将完成时移除同一方块的竞态进行防护。
5. 如果只观察到方块变化而没有充分的行为归属证据，必须产生 `AMBIGUOUS`，不得假报 `SELF_CONFIRMED`。
6. 保留方块实际变化的事实，不要因为归属不明就伪造“方块仍在”。
7. 动作取消、失败、超时、离线、世界切换及 Runtime 销毁时，确保监听器和临时状态全部清理。
8. 延迟事件、重复事件及过期事件不能改变已终结动作的归属结论。
9. 不得通过缩短等待时间、固定 sleep 或无限轮询来假装修复竞态。
10. 不得让新的归属判定绕过现有授权、MEDIUM 确认、独占动作、超时和安全停止机制。

如果发现现有客户端路径无法获得严格的自行挖掘证明：

- 必须如实记录限制。
- 对无法证明的归属使用 `AMBIGUOUS`。
- 不得默认所有成功的 `bot.dig()` 都是自挖成功。
- 如果真正的严格自挖确认需要服务端辅助证据，应设计可选、显式的证据提供接口，并让缺失证据时保守降级；不能暗中假设服务器已安装插件，也不能把额外服务器插件变成未经论证的必需依赖。
- 即使暂时无法在无插件服务器上证明所有自挖行为，也必须确保系统不再把无法归因的世界变化错误地记录为自挖事实或技能成功样本。

## 6. 第五阶段：打通 Python 执行链和技能反馈

归因结果必须通过现有 Action 终态事件和 `action_id` 关联机制，进入真实持久化的 `TaskStep.result`，不能只写在 Node 日志中。

修改范围以实际需要为准，重点覆盖：

### 6.1 TaskRuntime

- 保持动作实际结果和归属结果分离。
- `on_action_event()` 必须正确持久化归因证据。
- 重复终态事件不得覆盖已有的有效结论或使结果被二次计分。
- 保留原有取消、超时、离线、世界变化和授权语义。
- 不要让 `Task SUCCEEDED` 自动将所有挖掘步骤提升为自挖成功。

### 6.2 技能资格门

在 `app/tasks/skill_service.py` / `app/tasks/skill_learning.py` 中：

- `minecraft_dig` 的正向学习必须有真实步骤结果、独立的世界效果验证及满足要求的归属证据。
- `block_absent` 与 `inventory_delta` 仍可作为效果证据，但不能单独充当行为归属证据。
- 现有预期挖掘时长可以保留为辅助信号，但不得继续被当作充分的归因证明。
- 已确认外部干扰或归属不明的样本，应记录 `AMBIGUOUS` 或其他语义准确的保守结论，不得生成 `POSITIVE` 或 `COUNTEREXAMPLE`。
- 增加稳定、可审计的原因码，例如 `dig_attribution_unproven:<step_id>`。最终命名应遵循项目现有原因码规范。
- 证据写入、幂等消费及成功 / 失败 / 歧义计数必须保持一致。
- 缺少归属证据时，不能通过字符串、模型自述或任务目标反推归属。

### 6.3 MinecraftMemoryBridge

在 `app/integrations/minecraft/memory_bridge.py` 中：

- `_remember_task_target()` 只有在对应 `minecraft_dig` 步骤有可靠自挖归属证据，并满足现有步骤成功和世界结果要求时，才能写入表达“罐头亲手挖过”的 `TASK_RESULT` 资源事实。
- 如果任务总体成功，但归属不明，可以保留任务总体经历，但不能把它升级成罐头亲手处理过该坐标的世界事实。
- 如果任务包含多个 `minecraft_dig` 步骤，应逐步判定，不能因为第一步存在或任务整体成功，就将其他步骤一并视为已归因。
- 不能破坏现有记忆来源、坐标复核、去重和历史记忆读取机制。

## 7. 明确不允许的修复方式

以下方式不能被视为根因修复：

- 只调小或调大 `dig_short_ratio`。
- 只增加一个 `block_removed_by_self: true` 布尔字段，但该字段没有对应的真实证据来源。
- 只增加挖掘开始和结束时间。
- 只依赖 `bot.dig()` 的 Promise 成功。
- 只依赖 `block_after === "air"`。
- 只依赖总背包增量、掉落物名称或掉落物距离。
- 通过提高技能学习阈值来掩盖 Runtime 缺少归因证据。
- 把所有模糊样本都当成技能失败，或全部拒绝所有历史证据而不保留原因码。
- 使用测试 mock 证明真实 Minecraft 协议必然能够提供某种事件。
- 为方便实现而新增不必要的 Minecraft 工具、ActionRuntime 动作、TaskRuntime 状态或风险权限。

## 8. 必须新增的回归测试

先新增会暴露旧缺陷的测试，再实现修复。至少覆盖以下矩阵。

| 场景 | 必须满足的结果 |
|---|---|
| 有可靠证据证明罐头完成挖掘 | 自挖归属判定成立；满足其他门槛后才允许作为正向样本 |
| 其他玩家在罐头开始执行前移除目标 | 不归因于罐头 |
| 其他玩家在挖掘过程中移除同一个方块 | 不得错误判定为罐头自挖成功 |
| 其他玩家在预计挖掘即将结束时移除目标 | 不得因耗时达到预期就判定自挖 |
| 方块消失，但没有可用的归属证据 | `AMBIGUOUS`，不产生正向技能样本 |
| 方块消失，但总背包增量来自其他操作 | 不得将背包效果误归因于本次挖掘 |
| 观察到其他玩家的破坏进度，但无法证明其最终完成移除 | 不得过度推断为已确认的外部归因 |
| 无掉落物或没有增加背包物品，但可独立证明自挖行为 | 不能仅因没有预期掉落物而误判行为归属 |
| 目标位置只发生其他类型的方块变化 | 不得错误判定为成功挖掘 |
| `action_id` 不匹配、过期事件、重复事件 | 不得污染当前动作归属或产生重复计分 |
| 超时、取消、断线、重连、World Changed | 保留原生命周期与清理语义，不生成虚假自挖证据 |
| 任务总体成功，但某个 dig 步骤归属不明 | 不写入该步骤的“亲手挖过”资源记忆 |
| InMemory / SQLite、序列执行 / 重启重放 | 归属结论、原因码、幂等与技能计数保持一致 |

测试需要分层：

1. Node.js Runtime 单元测试：动作事件时序、外部移除竞态、事件清理与结果结构。
2. Minecraft Runtime E2E：在当前测试服务器实际支持的范围内覆盖挖掘及相关事件。
3. Python 单元与服务级测试：TaskRuntime 归属传递、资格门、技能反馈、SQLite 持久化、MemoryBridge。
4. 双客户端或真实服务器测试：如果现有环境可以验证真正的外部玩家竞态，应实际运行并记录结果。如果环境无法提供相应能力，必须标记 `SKIPPED` 并解释限制，不能把 mock 测试包装成真实服务器 PASS。
