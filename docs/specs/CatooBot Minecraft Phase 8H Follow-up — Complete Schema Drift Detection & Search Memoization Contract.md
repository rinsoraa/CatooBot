## 2. F1：完整、可信的 SQLite schema 变化检测

### 2.1 当前已知限制

当前 `app/database/migration_report.py` 根据完整性、版本、`lost_rows` 和 `added_tables` 进行状态判定。`schema_changed_without_version_bump` 实际检测的是版本不变且 `added_tables` 非空。

它不能单凭这一条件证明不存在其他 schema 变化。

本阶段必须评估并处理以下情况：

1. 版本不变但现有表新增列。
2. 版本不变但现有表列、约束或表定义发生变化。
3. 版本不变但一张现存表被删除，特别是空表被删除、因而没有行数损失的情况。
4. 版本不变但索引、触发器或视图发生变化。
5. 正常迁移发生版本递增，同时产生预期的 schema 变化。
6. 没有任何待执行迁移，schema 与版本均保持不变的合法 `no_op`。

### 2.2 Schema 快照设计

先审计现有迁移演练是否已经采集足以判断 schema 变化的真实元数据。如果没有，应在演练过程中增量采集一个可比较的 schema 快照或规范化指纹。

实现要求：

- 数据只能来自实际 SQLite 数据库，不得使用固定成功值或虚构的 schema 元数据。
- 检测范围应覆盖对当前业务数据库有意义的表、列、索引、触发器、视图等结构。
- 应能发现对象新增、删除，以及已有对象定义发生变化。
- 使用确定性的规范化表示，避免无关排序差异制造假阳性。
- 应明确如何处理 SQLite 内部对象或自动生成索引，不能把这些对象的正常变化误判为产品 schema 漂移。
- 如果采集 schema 快照失败或结果不完整，必须明确失败或不确定状态，不得静默降级为合法 `no_op`。
- 不得仅比较表数量；表数量相同不代表 schema 没有变化。

建议优先使用项目现有数据库访问与快照机制。如果没有适用实现，可使用 SQLite 的 schema 元数据读取能力建立规范化快照，并用实际数据库副本验证。

### 2.3 状态契约

保留既有三态：

- `no_op`：没有执行迁移；版本、schema 和数据保真检查均符合合法无操作的契约。
- `migrated`：版本按预期递增，前后完整性检查通过，无未经允许的数据损失。
- `failed`：完整性异常、数据损失、版本倒退、版本未变却出现 schema 变化，或者必需的证据采集失败。

具体规则必须在实现、文档和测试中一致。

如果迁移确实发生版本递增，但前后 schema 快照存在预期变化，应按照迁移状态契约判断，而不是一概判错。反之，版本未变但现有表的列、索引或其他 schema 对象发生变化，不能自动当成合法 `no_op`。

### 2.4 报告字段

保留现有 JSON 字段及兼容性。可以增量添加有价值的诊断字段，例如：

- `schema_changed`
- `schema_changed_without_version_bump`
- schema 快照计算是否成功，或稳定的差异摘要。

新增字段必须来源于真实快照，不能只是把预设常量写进报告。

如果添加 schema 差异摘要，优先记录结构对象名称、类型及差异方向，不必把完整数据库内容写入日志。

### 2.5 必须提供的测试

至少覆盖：

- 完整性正常、版本不变、schema 不变、无数据损失：`no_op`。
- 版本递增、前后完整性正常、迁移合法：`migrated`。
- 迁移前或迁移后完整性异常：`failed`。
- 发生数据损失或版本倒退：`failed`。
- 版本不变但新增表：`failed`。
- 版本不变但现有表新增列：`failed`。
- 版本不变但现有表定义发生变化：`failed`。
- 版本不变但删除空表：`failed`。
- 版本不变但索引、触发器或视图发生受监控的变化：`failed`。
- 版本递增且发生预期 schema 变化：`migrated`。
- schema 快照采集失败：不得报告 `ok=true` 的合法 `no_op`。
- 未发生任何变化的真实 SQLite 副本演练仍能报告 `no_op`，且退出码符合既有契约。

测试必须实际操作隔离的临时 SQLite 数据库或副本，不得通过直接构造预期结果代替 schema 采集与比较。

## 3. F2：配方搜索记忆化的实现与文档对齐

### 3.1 当前审计点

Phase 8H 文档说明，无配方、循环、超深等与库存无关的失败会按 `(item, amount)` 记忆化。但目前可以核验的 `craft_plan.py` 中，`impossible` 缓存写入发生在“没有候选配方”分支；循环和深度超限则直接抛出 `CraftPlanError`。

本阶段必须确认：

- 循环和深度失败是否确实重复消耗搜索状态。
- 哪些失败具有可安全缓存的条件。
- 是否存在被当前状态缓存错误地复用、从而忽略库存上下文的风险。
- 是否存在分支回滚未完整恢复库存、节点、工作台标志或输入计数的问题。
- 搜索预算是以实际候选尝试次数还是其他状态计数为准，并保持语义一致。

### 3.2 选择最小必要方案

如果经过审计可以证明某些失败可以安全记忆化：

- 使用清晰的缓存键，至少区分相关的目标、数量和影响该失败结论的上下文。
- 只有对库存及当前分支上下文不敏感的失败才能跨分支复用。
- 不得把“当前库存不足”缓存成所有候选都不可行的永久结论。
- 循环检测仍须正确处理当前展开栈，不能用全局 visited 标记替代递归路径检测。

如果某些失败无法安全缓存：

- 不强行实现缓存。
- 将文档改为准确描述当前实现。
- 保留集中搜索上限，确保重复失败最多消耗明确预算。
- 通过测试证明超限会按 `search_budget_exceeded` 明确拒绝，不会返回部分或伪造计划。

不得为了实现“记忆化”而改变原有计划正确性或放宽搜索预算。

### 3.3 必须提供的测试

至少新增或更新测试，证明：

- 同样的无配方子问题可以按设计安全复用。
- 成环的候选不会无限展开。
- 超深失败不会无限重复展开。
- 不同库存状态下的可行性判断不会错误共享缓存。
- 一个候选失败后，库存、节点、`requires_table` 和累计输入状态均正确回滚。
- 预算耗尽时返回稳定原因码，既有候选结果不会被悄悄提升为未经完整评估的最终计划。
- 相同输入、候选、库存与预算会得到相同计划和配方序列。
- 文档描述与真实缓存写入路径完全一致。

如果实测表明现有搜索行为已经满足正确性和有界性要求，只需修正文档并通过针对性测试，不要为追求代码改动而增加复杂度。
