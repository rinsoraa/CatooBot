# Part I — 产品定义与路线校准

## 1. CatooBot 的最终产品定义

CatooBot 不是“加了人设的 Minecraft 自动化工具”，也不是只会聊天、等用户下命令的 QQ Bot。最终目标是一个能够长期存在、拥有持续角色状态与生活经历、会主动形成想法、能够真正参与多人 Minecraft 游戏，并能从经验中积累可复用方法的 AI 角色。

Minecraft 是罐头生活的一部分，而不是产品的全部。她进入服务器的目的不只是完成孤立的采集任务，还应逐渐能够探索、建造、合作、和熟悉的玩家互动、记住共同经历，并在能力范围内解决以前没解决过的问题。

整个产品有三个互相连接但职责分离的核心能力：

1. **生活（Life）**：角色人格、作息、状态、需求、目标、关系、承诺和虚拟活动持续运转；她能产生自己的想法，而不必每次都等用户发起。
2. **游玩（Play）**：通过真实的 Minecraft 世界感知、已注册工具和受控任务链参与游戏；观察到的当前事实、历史记忆、用户身份、计划、执行状态和执行结果必须严格区分。
3. **学习（Learning）**：从有真实证据的经历中归纳方法，保存适用条件、步骤、成功判据、失败边界和来源；下一次任务先检索并判断是否适用，再决定是否把方法作为计划候选。

三者由同一个角色身份、共享但有来源隔离的记忆，以及统一的思考与执行控制层连接。它们不能合并成一个无限制 LLM 循环。

## 2. 目标架构

```text
                 罐头的角色核心
     人格 / 状态 / 需求 / 作息 / 目标 / 关系
                         │
           ┌─────────────┼─────────────┐
           │             │             │
      沙盒生活系统    QQ 社交入口    Minecraft 游玩系统
   Episode/Goal/Intent   │          WorldPerception
           │             │          已注册工具/动作
           └─────────────┼─────────────┘
                         │
                 共享记忆与身份层
       沙盒经历 / QQ关系 / MC世界事实 / 程序性技能
       每条记录保留来源、角色范围、时间、置信度与证据
                         │
                 统一思考与执行控制层
     理解目标 → 检索记忆/技能 → 判断适用性 → 规划
              → 能力/风险/身份/前置条件检查
              → 用户授权 → 既有任务执行链
              → 结果验证 → 记录经历 → 学习候选
```

**执行链固定为既有链路：**

`QQ / Minecraft Chat / WebUI / LifeIntent → TaskProposal → AgentPlan →（必要的批准/确认）→ TaskRuntime → Policy → AgentBridge → ActionRuntime → MinecraftService → Mineflayer → 真实结果验证`

实际某个入口是否经过每一个中间层，以当前源码中的真实调用关系为准；不得为了让实现“看起来符合图”而重复建层。所有入口共享安全执行基础设施，但授权来源必须可追溯且不可互相冒充。

## 3. 共享身份与记忆原则

### 3.1 跨平台身份

罐头需要理解同一个人可能在 QQ、Minecraft 和 WebUI 中分别呈现不同身份，但“名字像”不能成为可信绑定。

- `CANDIDATE`：推测关联，只能作为待核实线索。
- `VERIFIED`：来自可信验证或管理员确认，可以用于受授权的跨平台解析和记忆关联。
- `CONFLICT / REVOKED / MISSING`：禁止继续依赖该关联执行操作；不能用昵称、聊天内容或技能记忆绕过身份门。

仓库已经有 Minecraft Identity Bridge 和可信绑定机制。本产品目标是持续完善其正确使用，而不是在每个新阶段重复实现身份系统。

### 3.2 记忆必须保留来源与可信度

QQ 对话经历、MC 玩家/世界事实、沙盒生活经历和程序性技能可以关联检索，但不能把它们混成无来源的文本。当前观察与历史记忆必须分开；当前世界状态以真实感知为准。

- 用户说过什么，不等于真实世界已发生什么。
- `LifeIntent` 表示想法，不等于活动已经发生。
- `TaskProposal` 表示候选方案，不等于已经建立任务。
- `AgentPlan` 是规划和审计层，不等于任务执行状态。
- `Task SUCCEEDED` 是重要证据，但不代表所有模糊世界变化都已被归因到罐头自己的操作。
- 普通记忆和用户输入永远不能授予执行权限。

## 5. 本次仓库审计确定的现有基础与缺口

实现前先复核以下文件和它们的真实调用者；本文不是允许直接跳过代码审计的理由。

### 已有基础

- `app/memory/`：统一记忆引擎、模型、Repository、检索、语义/关键词索引、提取与巩固。
- `app/memory/minecraft/`：Minecraft 语义事实模型、写入、检索、存储和世界事实对账；`MinecraftMemoryFact` 已保留 `server_id`、`task_id`、`plan_version`、`initiator`、`outcome`、`world_revision`、来源、新鲜度和置信度等元数据。其 `MinecraftMemoryKind` 当前严格定义为七种语义事实类型，不应未经审计就把程序性技能硬塞进去。
- `app/integrations/minecraft/memory_bridge.py`：订阅任务收尾；对 `SUCCEEDED / FAILED / EXPIRED` 写入相应任务经历，对成功任务还会记下可追溯的挖掘目标世界事实。这是“任务经历记忆”，不等于可复用技能库。
- `app/tasks/models.py` 与 `app/tasks/runtime.py`：现有 Task/TaskStep 状态、计划版本、步骤参数、真实工具结果、失败/重试信息、事件序号、确认授权和持久化 checkpoint。Task 是学习候选的重要证据源。
- `app/tasks/agent_plan.py`、`agent_planner.py`、`agent_service.py`：`AgentPlan` 与有界规划器；当前规划器是受限、确定性的模板规划，不是允许模型任意生成与执行工具链的通用代理。
- `app/sandbox/experience.py` 与 `app/sandbox/memory_foundation.py`：已有 `SandboxEvent → ExperienceRecord → MemoryCandidate → existing memories` 的带来源经历/记忆晋升管线；它解决的是沙盒经历与长期记忆，不等于 Minecraft 程序性技能。
- `docs/MINECRAFT_PHASE7A.md`、`7B.md`、`7C.md`、`7D.md` 与 `CHANGELOG.md`：阶段约束、门禁和历史证据是实现基线，必须同步更新。

### 本阶段要填的缺口

现有 Minecraft 记忆主要回答“我见过谁、哪里有什么、我做过什么”；Phase 7E 应补足“**我掌握了怎样的方法、它依赖哪些前提、证据证明它曾成功、现在能否安全复用**”。

不能把一条“成功做过任务”的自然语言事实直接当成可运行技能；也不能把 Task 的原始 JSON 整包写入普通记忆后，让模型自己从中猜方法。技能必须是独立、结构化、可校验、有生命周期的程序性知识，但底层存储和检索应最大程度复用现有基础设施。

### 已知数据质量风险：不要把它错排成 7E

`docs/MINECRAFT_PHASE7D.md` §10.4 记录了一个尚未在 7D.2.1 修复的旧问题：`minecraft_dig` 在挖掘进行中如果方块被其他玩家移除，当前结果检查可能只因“原方块消失”就将结果判为成功，无法归因究竟是谁移除了方块。这是单独跟踪的 **Phase 7D 后续结果完整性缺陷**，不是 Phase 7E 的主目标。

Phase 7E 必须对它实施学习数据质量隔离：任何无法可靠归因的挖掘结果都不能作为“罐头已验证掌握该挖掘方法”的正向训练样本；必要时应标为 `AMBIGUOUS / INELIGIBLE` 并保留来源。不允许为完成 7E 而顺手把该问题改名成 7E，也不要扩大修复到这一缺陷本身。若必须修改 7D 路径才能安全接入学习，请拆分并清楚标记为独立的 7D follow-up，先论证必要性。

# Part II — Phase 7E 实施目标

## 6. 唯一阶段目标

在保留当前所有安全边界的前提下，建立一个**最小但完整的程序性技能生命周期**：

```text
TaskRuntime 真实终态 + 步骤结果 + 可验证的后置条件
                         │
                   Evidence Qualifier
                         │
             不合格 ─────┴───── 合格
                │                  │
          不晋升 / 留痕         Skill Candidate
                                   │
                         结构归一化 / 条件抽取
                                   │
                       验证 / 去重 / 版本管理
                                   │
                         Procedural Skill Store
                                   │
目标 → bounded retrieval → Applicability Check
                                   │
                    ┌──────────────┴────────────┐
                 不适用                       适用
                    │                            │
          现有规划器正常回退          生成计划候选（不是任务）
                                                 │
                                      能力/前置/风险再检查
                                                 │
                                  现有批准/确认 + TaskRuntime
                                                 │
                                        真实执行与结果验证
                                                 │
                                    成功/失败/失效反馈到技能
```

这不是在本阶段实现无限自主游玩。7E 的交付重点是“会学习一项可验证的方法，并且在下一次遇到相似任务时知道是否适用、如何提出复用方案”。执行仍由既有任务执行链管理。

## 7. 必须交付的能力

### 7.1 结构化技能模型

结合源码审计后确定最小 schema。至少应能表达：

- `skill_id`、`schema_version`、技能名称/目标模式、简短说明、生命周期状态；
- 所属角色/记忆隔离范围，以及学习来源的服务器/游戏环境范围；不能默认不同服务器、版本、模组和规则完全等价；
- 可复用的有界步骤模板：只允许当前已注册的工具和合法参数 schema；明确变量槽位、步骤依赖和参数来源；
- 前置条件：所需能力、库存/物品/环境/玩家身份/目标可见性等可从既有 SAFE 观察中验证的条件；只保留实现确实能验证的条件，不能编造感知能力；
- 预期效果和可观察成功判据；区分“工具调用成功”与“目标已实现”；
- 来源证据：源 `task_id`、最终 plan version/hash、相关步骤/事件、真实执行结果和后置条件验证证据；
- 证据计数、成功/失败/模糊记录、创建/最后使用/最后验证时间、版本和失效原因；
- `required_capabilities`、风险摘要和确认要求。技能无权修改或降低风险等级。

应区分 `CANDIDATE`、`VALIDATED/ACTIVE`、`STALE/INAPPLICABLE`、`REJECTED/INVALIDATED` 等生命周期语义。最终枚举和状态转换由审计结果决定，但必须显式、有界、可恢复，禁止把未验证候选直接当成可用技能。

**程序性技能不是任意代码。** 第一版只保存结构化步骤/参数模板/条件/验证器元数据，不允许模型生成后直接执行 Python、JavaScript、Shell、Minecraft 命令脚本或动态插件。

### 7.2 严格的学习资格门

技能学习必须由可信的 TaskRuntime 记录驱动，不得由 LLM 自述、普通聊天记忆、用户 pasted 方案或 `LifeIntent` 文本直接晋升。

至少执行以下判定：

1. 来源是实际持久化的 Task/TaskStep/事件/checkpoint，而不是模型回复中的“我已经完成”。
2. Task 为真实 `SUCCEEDED` 终态；取消、失败、过期、暂停、等待动作、待确认、重新规划中或终态不明的记录不能晋升。
3. 被抽取的每个步骤都必须是被纳入当前最终计划版本且具有可信结果的步骤；不能把之前失败/废弃计划版本的步骤拼到最终成功路径里。
4. 必须检查重试、异步 `action_id`、步骤状态和事件序号；同一终态事件重放、同一 task 多次回调、服务重启恢复不能重复计数或重复创建技能。
5. 对依赖世界变化的步骤，必须要求相应的可验证后置条件。只有 action 返回 `ok` 或步骤标记 `SUCCEEDED`，在证据不足时仍不够。
6. 已知的 `minecraft_dig` 他人移除歧义结果必须排除或降为不可晋升的模糊证据。**不要将其误学成成功方法。**
7. 学习资格判定必须可解释：每个拒绝/暂缓都产生稳定的 reason code，不将不确定状态默认成成功。

请设计明确的资格规则，不要只用一个模型生成的 confidence 分数取代判定。可采用两阶段流程：先生成 `CANDIDATE`，再按独立成功证据或强后置验证证据晋升为 `VALIDATED/ACTIVE`。具体阈值应由现有真实证据结构支持，并写入文档和测试；不允许因为测试需要而放松标准。

### 7.3 方法归一化与去重

- 把实际成功任务归一化为可复用的结构模板，而不是保存具体位置、实体 ID、会话 ID、随机 UUID 等一次性执行值。
- 区分稳定参数、目标槽位和必须实时重新观察的动态参数；无法安全泛化的值保留为硬约束或直接不允许跨场景复用。
- 基于规范化步骤/能力/条件生成稳定 fingerprint；相同 Task 的重复事件不能生成重复技能，同一方法的证据可以有幂等地合并路径。
- 不把整份 world snapshot、凭据、完整聊天记录或非必要的原始 Task payload 复制进技能正文。用 ID 和证据引用保留可追溯性。
- 对版本升级或策略/工具 schema 发生变化的技能，旧版本应能被识别为待重新验证，而不是静默当作仍然有效。

### 7.4 有界技能检索与适用性评估

接到新的 USER 请求或来自既有流程的 LIFE 计划候选时，可在现有有界规划流程内检索相关技能。检索结果只是辅助计划的候选上下文，绝不是执行指令。

适用性评估至少覆盖：

- 当前目标是否与技能目标/参数槽位匹配；
- 当前注册工具是否仍存在，工具 schema、风险类别和能力标记是否兼容；
- 当前环境/服务器/游戏版本范围是否满足技能声明；
- 前置条件是否可通过最新 SAFE 观察证实；无法观察或观察失败视为 `UNKNOWN`，不当作满足；
- 用户指定对象的身份是否仍为当前服务器上的 `VERIFIED`；
- 技能是否过期、被失效、被新版本取代或曾出现足以触发暂停/失效的反例；
- 技能的风险、步骤数和动作数是否在当前既有预算内。

必须给出可审计结果，例如 `APPLICABLE / INAPPLICABLE / UNKNOWN / STALE` 以及原因；具体名称可服从现有项目枚举风格。`UNKNOWN` 不能自动升级为适用。适用性不成立时必须回退到现有规划器，或返回“需要更多信息/不支持”，绝不为了复用强行改写当前世界事实。

### 7.5 在现有 Planner/Agent Harness 内复用

- 优先以最小改动扩展 `app/tasks/agent_planner.py` / `agent_service.py` 或当前最合适的调用点；审计后再决定准确位置。
- 至少为一个**当前已支持、参数边界清晰**的任务类别建立端到端“成功任务 → 技能候选/验证 → 后续检索 → 适用性判断 → 生成计划候选”的垂直切片，并证明它在第二次任务中确实有复用作用，而不是只写入数据库、不被读取。
- 技能输出只能转换为经 schema 校验的计划候选；继续使用现有能力目录、`validate_plan`、风险分类、身份解析、TaskProposal/AgentPlan 与 `TaskRuntime`。
- 不得由技能直接调用工具、`MinecraftService`、`ActionRuntime` 或 Mineflayer。
- 不得绕过既有用户批准/确认、`Policy`、`TaskAuthorization` / `TaskStepAuthorization`、当前目标复核、停止/取消/超时/重启恢复路径。
- USER 任务仍走现有 USER 授权流程；LIFE 任务仍保留 7D 定义的两道门：批准计划后才创建待确认任务，用户再次确认后才能执行。**学习过一次不等于以后可以自行执行。**
- 当前工具集合 19 个、`allow_medium=false`、TaskRuntime 状态集合、ActionRuntime 动作集合均保持不变，除非另行提出独立且有证据支持的变更申请；本阶段默认不改。

### 7.6 使用效果与失效回流

- 任务执行后，将技能引用和执行结果通过现有 task/event/checkpoint 体系关联起来；不另造一套执行状态机。
- 经验证的成功可以更新该技能的证据计数/最近成功记录；失败、反例、前置条件失效、工具版本不兼容应使技能转入待验证、暂停或失效状态，具体转移有规则可查。
- “计划被生成/被用户批准/任务建立”不能计入技能成功次数。只有合格的真实执行终态和所需后置条件验证可以计入。
- 相同 `task_id + plan_version + step/event identity` 的重复事件必须幂等。
- 本阶段不实现模型权重训练、在线自改代码或自动安装新能力。如果运行中发现缺少工具，沿用 7C/7D 的能力缺口结果与用户可见说明；不能把失败技能自动升级成新工具。

# Part III — 架构与安全硬约束

## 8. 实施前必须完成的审计

在修改任何源码前，先给出简短、基于行号/函数名的审计结论：

1. `MinecraftMemoryBridge.on_task_finished()` 的实际订阅点、调用频率、事件幂等机制，以及写入 TASK fact 的行为。

3. 现有 `MinecraftMemoryKind`、`MinecraftMemoryStore`、通用 `MemoryRepository` 与 `SandboxMemoryStore` 的适用边界；哪些可复用，哪些不能直接承载程序性技能。

5. 数据库初始化/迁移/回滚的现有做法、最新 schema 版本/迁移记录、测试使用的真实持久化设施。

7. 7D §10.4 dig 归因缺陷的当前实现、现有测试覆盖和可识别的歧义情形；只定义技能学习的排除策略，不顺手将它改号为 7E。

## 9. 存储决策约束

本项目已有多个记忆域，不允许新建一个与它们无关的“第二记忆系统”。但也**不允许**为了避免迁移就把有状态、有条件、有版本的程序性技能压成普通自然语言事实。

实现前比较至少两种最小方案：

- 复用现有持久化/Repository 基础设施，增加有类型约束的技能记录与索引；或
- 如果现有 schema 无法安全存储技能的步骤模板、生命周期和证据链接，新增一份专用的最小结构化存储，并明确说明它为何仍属于同一个共享记忆/技能体系，而非独立的第二引擎。

选择能满足幂等、事务、恢复、版本、适用性检索和溯源的最小方案。若新增 schema/migration，必须随实现提供迁移/初始化/升级兼容测试和文档；不能修改或复用 31/32/33 迁移的历史含义。没有必要则不要迁移。

## 10. 禁止事项

- 不新建第二套 TaskRuntime、Agent Harness、Policy、Minecraft 执行入口、MemoryManager 或独立调度循环。
- 不让 `LifeIntent`、`ActivityPlan`、`TaskProposal`、`AgentPlan`、技能记录互相冒充；程序性技能不是 Task。
- 不新增 Minecraft 原子工具、ActionRuntime 动作、TaskRuntime 状态，除非单独申请并有必要性证明。
- 不调低现有风险、授权、确认和速率预算；不能修改 `allow_medium=false`。
- 不让技能记忆、普通聊天记忆、用户输入或 LLM 输出增加执行权限。
- 不允许动态执行生成代码、任意脚本、未注册工具或未经审查的新工具。
- 不把所有 `SUCCEEDED` 都视为无条件高质量训练数据；不把不确定当成功。
- 不删除历史证据来换取“干净的”测试结果，不用 mock-only 测试冒充真实 Java/QQ 验收。
- 不编辑、不上传或覆盖本地私密角色 Bible、token、API key、`.env`、真实配置和用户运行数据；发布镜像遵循仓库既有隔离方式。
- 不修改与 Phase 7E 无关的 CSS/WebUI、业务逻辑或数据库数据；如发现阻塞问题，先记录为单独 follow-up。

# Part IV — 验收标准

## 11. 功能验收矩阵

必须为每一项增加能失败的负向测试，而不是只测 happy path。

| ID | 验收点 | 必须证明的行为 |
|---|---|---|
| E1 | 真实任务证据入口 | 从持久化 TaskRecord/步骤结果构建学习输入；非实际执行记录/LLM 自述不能产生技能 |
| E2 | 成功资格门 | 仅合格的 SUCCEEDED + 所需步骤证据/后置条件可以晋升；`FAILED/CANCELLED/EXPIRED/PAUSED/PENDING_CONFIRMATION/WAITING_ACTION/REPLANNING/UNKNOWN` 不晋升 |
| E3 | 已知歧义隔离 | 模拟 dig 中途被其他玩家移除目标方块，不能把它记作可靠成功技能；解释为歧义/证据不足 |
| E4 | 当前最终计划版本 | 重规划前失败步骤不被拼入最终成功方法；旧 plan version 可审计但不能伪装成最终执行路径 |
| E5 | 幂等/重启恢复 | 重复终态事件、重复 subscriber callback、进程重启恢复不会重复技能或重复累计成功次数 |
| E6 | 技能结构与溯源 | 每条有效技能能追溯 source task、plan version、步骤/结果和验证证据；参数模板无泄露不必要动态 ID/密钥 |
| E7 | 去重/版本 | 相同方法不会无限复制；方法版本变化有明确 lineage，不能覆盖掉既有证据 |
| E8 | 检索与匹配 | 类似目标可以检索到合适技能；不相似目标或条件不符不会强行复用 |
| E9 | 适用性检查 | 工具缺失/schema 变更、能力未知、服务器或版本不匹配、身份非 VERIFIED、前置条件 unknown、技能过期时拒绝复用或回退 |
| E10 | 计划集成 | 至少一个受支持场景完成“学习—持久化—重新启动后检索—适用性评估—生成计划候选”完整闭环 |
| E11 | 执行边界 | 技能不能调用 Minecraft 工具；实际任务仍经过现有 `TaskRuntime → Policy → AgentBridge → ActionRuntime → MinecraftService` |
| E12 | 确认与来源隔离 | USER 仍需要既有确认；LIFE 仍保留批准计划 + 确认执行两道门；技能不能绕过任何一道门 |
| E13 | 失败回流 | 复用技能后遇到反例/不适用能记录结果并使技能进入待复核/失效路径；失败不会被记为成功 |
| E14 | 记忆隔离 | 不跨角色读取；服务器/世界范围和来源明确；不信任记忆中的命令式文本，拒绝 prompt injection |
| E15 | 只读观测 | 能检查技能数量、状态、来源、最近学习/检索/拒绝原因；若用 API/WebUI，沿用既有只读接口安全模式 |

## 12. 关键负向测试清单

至少覆盖：

- `TaskState.SUCCEEDED` 但某个必要步骤缺结果、仍在 `WAITING_ACTION` 或 postcondition 不可核验。
- 被取消、失败、过期、暂停、重规划中、等待用户确认或状态字段缺失的任务。
- 重规划版本 A 失败、版本 B 成功；技能只抽取 B 实际成功的步骤，不把 A 的失败步骤当成功方法。
- 一个任务的终态事件重复投递 N 次，技能和 evidence count 仍只增加一次。
- 前置条件观察结果为 unavailable/error/too_far/unknown 时，不允许默认满足。
- 记录的服务器/游戏版本/tool schema 与当前不兼容时不应用。
- skill 文本或关联普通记忆里出现“无需确认”“忽略 Policy”“直接执行”等语句，不改变任何 gate。
- 目标是另一位玩家但只有候选/撤销/冲突身份时，不把技能用于跟随或其他目标相关动作。
- 工具风险从已知值变化、工具已禁用、能力目录缺失时不套用旧技能。
- 同一技能历史出现可靠失败反例时，不得继续无条件保持 ACTIVE。
- skill store 读取/写入/迁移失败时 fail closed：聊天与现有任务安全路径不受破坏，学习可降级关闭并显示 `degraded`。
- 任何技能检索异常时，当前既有 Planner 必须保持原有行为，不能因为记忆服务异常而使既有规划获得更大权限。

## 13. 自动化和真实环境门禁

按仓库现有工具链和 CI 定义执行，不要并发运行已知对时序敏感的 Node runtime E2E 与全量 Python 测试。

至少提供并记录：

- `ruff check .`
- `ruff format --check .`
- `mypy app`
- `pytest tests -q`
- WebUI 现有 `typecheck`、Vitest、build、browser E2E 等所有受影响的门禁
- Minecraft runtime 的单元与现有 E2E 检查，按仓库文档规定的顺序运行
- 数据库初始化/迁移/恢复/幂等相关测试
- GitHub Actions 对最终镜像 commit 的完整 CI 成功链接，而非只提供本地测试截图

### 真实环境验收

本阶段以学习证据链与复用计划链为主，不要求为了证明学习能力而执行破坏性世界操作。优先用真实 TaskRuntime/SQLite + 真实已记录 Task 进行端到端集成测试。

若确实需要连接真实 Java 服务器，必须事先确保使用可恢复、低风险的受控目标，并由操作者按既有授权流程进行确认；不得自动批准、不新增未确认的世界操作。真实验收应记录：开始 commit、当前服务器身份/环境范围、任务/计划版本、执行前置状态、用户确认时间、Task/Step 真实状态、后置条件证据、技能保存与重新检索结果、结束时世界/配置是否复原。无法完成的真实用例标为 `BLOCKED` 或 `SKIPPED`，说明原因；不能以单测通过替代真实证据，也不能伪造 PASS。

## 15. Phase 7E 完成后的产品状态

7E 通过意味着罐头不再只是“记住做过某件事”，而是开始具备可验证、带适用条件的程序性记忆：她能从真实成功经历中抽出一条有来源的方法，能说清楚什么时候可以用，什么时候不能用，并把方法作为下一次计划的候选交回既有控制层。
