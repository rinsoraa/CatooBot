# Phase 7D — Agent Harness: Bounded Planning & Authorized Execution

## 0. 任务定位

基于 Phase 7C 最终基线：

- Mirror commit: `7b1d982`
- TaskProposal、LifeIntent、IdentityLink、TaskRuntime、ActionRuntime、Policy 与 MinecraftService 均复用现有实现。
- 当前 Minecraft 工具数保持 19 个。
- `allow_medium=false` 必须保持不变。

目标是为罐头建立一个有界 Agent Harness，使她能够把复杂目标拆解为可验证的步骤，通过真实观察决定下一步，并在失败时安全停止或重新规划。

本阶段不是无限制自主执行，也不是创建新工具的阶段。

**核心原则：模型可以提出计划，但不能自行授予权限；每一步执行都必须经过既有授权、策略与执行链。**

## 1. 开始前：审计现有实现

先检查 7C 与所有相关执行链，建立准确的调用关系：

`User / LifeIntent → TaskProposal → Authorization → TaskRuntime → Policy → AgentBridge → ActionRuntime → MinecraftService → Mineflayer`

实际实现可能与上述概念图存在差异，应以源码为准，不得为了符合图示而重复创建既有模块。

重点审计：

1. TaskProposal 的完整状态机、来源隔离、风险字段与确认接口。
2. TaskRuntime 已支持的创建、运行、暂停、恢复、取消、超时与重启恢复路径。
3. 每一种工具的参数校验、风险等级、权限检查和执行入口。
4. 现有计划、Episode、ActivityPlanner 与 DecisionEngine 的职责边界。
5. 任务执行完成、失败、取消和世界状态变化时的事件传播机制。
6. `minecraft_memory.identities` 中身份关系的实际查询契约。
7. 真实 QQ 命令“跟着我”为什么没有进入现有执行链。

先输出审计结果和最小改动设计，再实施代码。不得另建第二套 TaskRuntime、策略引擎或 Minecraft 执行入口。

## 2. AgentPlan 与 PlanStep

建立结构化、可持久化、可审计的 AgentPlan 和 PlanStep。

具体字段可根据现有数据模型调整，但至少需要表达：

- plan_id、来源、目标描述与关联 proposal_id。
- 发起者及经过验证的目标实体。
- 基于当前状态计算的计划版本与指纹。
- 每一步的目标、所需能力、输入参数和前置条件。
- 预期结果与可以观察到的成功判据。
- 风险摘要、授权要求、超时与失败处理方式。
- 步骤状态、执行记录和重规划原因。
- 整体计划的截止时间与最大步骤预算。

步骤状态必须与真实执行状态一致。不得在任务尚未执行时提前标记成功，也不得仅凭模型自述判定完成。

如果现有 TaskRuntime 状态无法表达计划步骤状态，应在 Agent Harness 内建立独立的计划状态，而不是擅自增加 TaskRuntime 状态。

## 3. 受限规划器

将目标转化为有限、可检查的步骤序列。

规划器只能从当前已注册、实际支持的能力中选择操作。禁止：

- 虚构工具、参数或工具返回结果。
- 把 UNKNOWN 或 UNSUPPORTED 自动升级为 SUPPORTED。
- 通过任意 Python、JavaScript、Shell 或动态代码执行绕过工具注册。
- 擅自安装依赖、生成工具并投入运行。
- 将普通观察结果当作用户授权。

如果目标无法完成，必须明确返回以下某种可审计结果：

- READY_FOR_APPROVAL
- NEEDS_MORE_INFORMATION
- UNSUPPORTED
- BLOCKED_BY_POLICY
- BLOCKED_BY_PRECONDITION
- REPLAN_REQUIRED

可以复用 7C 的能力检测、风险分类和身份解析，不要重新定义一套不兼容的分类体系。

## 4. 来源与授权边界

必须保留 USER 与 LIFE 的来源隔离。

### USER 来源

用户发出的明确操作请求，可以进入现有的用户任务与授权链。

需要确认的操作必须通过现有确认机制。不得仅仅因为用户提出了复杂目标，就自动取得额外权限。

### LIFE 来源

由 LifeIntent 产生的计划默认只具备规划和提案权限。

必须满足明确、可审计的用户批准条件，才可以沿既有授权路径提交为实际任务。任何自动批准、自动创建 Task 或自动触发 Minecraft 操作的旁路都不允许出现。

不得将 ActivityPlan、LifeIntent、TaskProposal、AgentPlan 与实际 Task 混为同一对象。

## 5. 单步执行与反馈闭环

执行器必须遵循如下控制循环：

1. 检查计划是否有效、是否过期、授权是否仍然有效。
2. 使用既有安全观察接口获取当前真实状态。
3. 检查下一步的前置条件和能力声明。
4. 通过既有 TaskRuntime、Policy 与 ActionRuntime 执行获准步骤。
5. 获取真实执行结果与新的世界状态。
6. 根据预期结果判断继续、停止或重新规划。
7. 持久化步骤结果、任务事件、失败原因和计划版本。

任何步骤执行前都必须再次验证当前授权与前置条件。计划创建时通过检查，不代表数分钟后仍然可以无条件执行。

任务暂停、取消、超时、授权失效、身份冲突、服务断线或进程重启，都必须使执行循环安全停下或进入现有恢复流程。

禁止模型直接调用 Mineflayer、MinecraftService 或其他底层执行对象。

## 6. 重新规划与错误恢复

重新规划必须基于真实观察、工具返回值或明确的状态事件，而不是无限重试。

必须支持：

- 前置条件不满足时停止执行并说明原因。
- 工具失败后判断是否可以安全重试。
- 世界状态发生显著变化时使旧计划失效。
- 能力不足时退回提案层，不得现场创造并运行新工具。
- 用户取消或授权失效时停止后续步骤。
- 重启后恢复可恢复的记录，但绝不重复执行已完成且不可重复的动作。

建立最大步骤数、重试次数、计划总时限及重规划预算。默认值应从实际架构与风险出发并有配置依据，不得使用无界循环。

## 7. 安全边界

本阶段必须继续遵守：

- `allow_medium=false` 不变。
- 不降低现有风险等级，不绕过既有确认规则。
- 不增加 Minecraft 工具或 Action。
- 不增加 TaskRuntime 状态。
- 不增加任意代码执行、自动安装或自动注册能力。
- 不允许未经确认的 LIFE 来源提案产生世界动作。
- 身份关系只有 VERIFIED 时才能自动解析跨平台目标。
- REVOKED、CONFLICT、缺失或不唯一的身份关系必须安全拒绝或要求补充信息。
- 计划中的目标、参数与执行对象不能仅由模型自由文本决定。
- 任何失败和拒绝都必须保留可审计记录。

如果现有安全机制无法明确表达某项操作的授权条件，应停止该操作并报告缺口，而不是推断放行。

## 8. QQ 与 Minecraft 集成

重点覆盖两个真实场景。

### 场景 A：明确的用户请求

通过真实 QQ 会话发送一个涉及多步骤 Minecraft 操作的请求。

验证系统能识别请求、构建结构化计划、展示必要的授权边界，并且仅通过既有安全执行链完成获准操作。

对需要确认的步骤，必须实际验证确认前后行为不同。

### 场景 B：“跟着我”

重新检查 7C 留下的真实 QQ 集成缺口：

用户通过 QQ 发送“跟着我”，系统应依据当前有效的 QQ–Minecraft VERIFIED 身份关系解析 `RinsoraNeko`，并沿既有安全用户任务路径处理请求。

必须先证明消息确实进入了正确处理器，再验证计划、授权、TaskRuntime 与执行结果。

不得仅凭日志中出现玩家名称就判定功能成功。

如果现有自然语言检测器、授权设计或任务入口不能支持此场景，应精确定位并修复属于本阶段范围内的问题；若需要改变既有策略或权限语义，则记录为阻塞项，不得擅自放宽安全边界。

## 9. 观测性与审计

至少提供只读查询能力，能够检查：

- 当前计划及其来源。
- 每一步的状态和预期结果。
- 能力与授权检查结果。
- 实际执行结果及可验证的状态变化。
- 重新规划的原因。
- 取消、过期、重启恢复与拒绝记录。

WebUI 只展示经过授权的可见信息，不新增隐含的授权按钮或执行旁路。

禁止将模型内部推理文本作为正确性证据。审计记录应关注输入、结构化决策、检查结果、执行事件及实际状态。

## 10. 测试要求

### 自动化测试

覆盖：

- 计划解析、结构校验和不支持的能力。
- USER 与 LIFE 来源隔离。
- 缺失、撤销及冲突的身份关系。
- 过期计划、指纹变更与授权失效。
- 前置条件变化、工具失败与有限重试。
- 取消、暂停、重启恢复及重复执行保护。
- 重新规划循环预算。
- 模型超时、无效结构化结果与降级路径。
- 未批准的 LIFE 提案不会产生 Task 或 Minecraft 操作。
- `allow_medium=false` 与既有风险规则保持不变。

### 真实 Java 验收

使用真实 Minecraft Java 服务端验证至少：

A. 从真实状态构建多步骤计划。

B. 经过实际授权后完成一个有限的多步骤任务。

C. 中途改变世界状态，观察系统停止、重新规划或安全失败。

D. 在执行过程中取消任务，确认后续步骤不再发生。

E. 模拟或实际触发可安全复现的重启恢复，并证明已完成步骤不会被重复执行。

F. 使用不支持的能力或无效身份，证明执行被阻断。

### 真实 QQ 验收

验证真实 QQ 消息、真实身份解析、真实任务入口、必要的用户确认、实际 Minecraft 结果和可审计记录。

不要把 API 单测、模拟 QQ 事件或伪造的 Minecraft 状态记为真实验收。

若有项目环境限制无法完成某项真机测试，必须明确标记 BLOCKED 或 SKIPPED，并提供可复现的原因，不能用单测代替真实覆盖。
