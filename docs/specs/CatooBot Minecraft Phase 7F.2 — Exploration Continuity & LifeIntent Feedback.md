## 二、阶段目标

把一次真实 Minecraft 探索的结果接回罐头的生活系统，使其能够影响未来的记忆检索、生活意图和活动规划。

目标闭环：

真实探索任务及后置验证
→ 结构化探索结果
→ 可信事实和经历回流
→ 现有 LifeIntent 候选生成与资格评估
→ ActivityPlanner 形成后续虚拟生活计划
→ LIFE TaskProposal
→ AgentPlan
→ 既有批准与执行确认
→ 后续受控游玩。

本阶段不重新实现 Minecraft 执行层，不扩大动作权限，不实现无界自主游玩。

审计之后，提出最小设计与文件清单，再继续实施。

## 四、实施要求

### 4.1 结构化探索结果

以真实持久化 TaskRecord 与运行时验证结果为依据，建立最小的探索结果投影。

至少区分：

- `ARRIVED_VERIFIED`：真实世界坐标满足 `position_within`。
- `ARRIVED_NO_NEW_FACT`：已确认到达，但没有发现可确认的新事实。
- `NEW_FACTS_VERIFIED`：存在由真实 SAFE 观察支持的新事实。
- `BLOCKED`：目标不可达或前置条件不满足。
- `CANCELLED_OR_INTERRUPTED`：任务被取消、中断或未完成。

以上是建议的结果分类；实施前应检查现有枚举和模型，优先复用兼容的既有契约，不应为了这些名字另造状态机。

不得把动作返回成功、计划批准或任务建立当作真实探索完成。任何新事实必须有明确来源、时间、服务器范围及可追溯依据。若现有数据没有足够证据，就不产生已确认事实。

### 4.2 记忆与世界事实

优先复用现有 MinecraftMemoryBridge、MinecraftMemoryStore、世界事实对账及通用经历存储。

- 只保存有价值且有证据支持的事实和结果摘要。
- 采用现有来源隔离、服务器作用域、新鲜度、去重与冲突规则。
- 不把完整世界快照或所有探索日志永久注入角色上下文。
- 旧观察不能自动覆盖更新的世界事实。
- 不新增第二套记忆系统；如果必须新增表，先论证现有存储无法表达的语义及迁移必要性。

### 4.3 LifeIntent 回流

让经过验证的探索经历能够成为现有生活意图系统的输入，但绝不能跳过 InitiativeGate。

- 只有合格的事实或目标变化才能触发有意义的后续意图候选。
- 继续遵循现有冷却、频率上限、指纹去重、恢复静默期和抑制规则。
- 普通到达但没有新信息，不应反复生成“继续探索”意图。
- 失败、取消和中断应保留真实结果，不能伪造成成功后再引导生活规划。
- 后续意图仍只是想法。它不能直接调用 TaskRuntime、ActionRuntime 或 MinecraftService。
- 利用现有 ActivityPlanner 将合格 LifeIntent 作为软候选，而不是强制切换活动。

如果现有 LifeIntent 生成机制不能消费合适的 Minecraft 经历，应在最小的数据适配层解决，不要重新实现 InitiativeEngine 或 ActivityPlanner。

### 4.4 提案与授权边界

必须沿用现有链路：

`LifeIntent → TaskProposal → AgentPlan → 批准 → 待确认 Task → 确认执行 → TaskRuntime`

- LIFE 计划批准之前不得建立执行任务。
- 计划批准后，执行仍须等待第二道确认。
- 用户拒绝、取消、身份缺失、世界离线或能力不足时，如实结束或阻止。
- 维持现有 `Policy`、授权、风险、超时、停止、暂停和恢复语义。
- 不修改 `allow_medium=false`，不新增工具、动作或隐式授权方式。

### 4.5 幂等与恢复

- 同一探索终态重复发布，不得重复写入新事实或反复生成意图。
- 重启后，历史事实和对应任务的来源仍然可追溯。
- 已被抑制、解决或过期的 LifeIntent 不得因为重放再次变为有效。
- 更新失败时应保留原始经历，并让生活规划正常降级，不能编造新的探索结果。

## 五、测试与真实服务器验收

最少覆盖：

1. 到达成功，但没有新事实：保存结果，不制造重复 LifeIntent。
2. 到达成功，SAFE 观察到可信新事实：按规则进入记忆与意图候选管线。
3. 目标不可达：不产生正向探索事实。
4. 用户取消或超时：记录实际结果，不产生虚假的成功经历。
5. 观察数据缺失、离线、陈旧或互相矛盾：不晋升为确认事实。
6. 重复终态事件、事件重放及进程重启：记忆和意图均保持幂等。
7. LifeIntent 到 TaskProposal、AgentPlan 的真实路径可追溯。
8. 未批准或未确认时不执行任何 Minecraft 世界动作。
9. 新候选能进入现有生活规划，同时旧有虚拟活动规则保持有效。
10. InMemory 与 SQLite 的行为一致，相关数据库升级过程幂等。

必须进行真实 Java 服务器测试，验证至少一个成功探索结果经过完整的事实/生活意图反馈路径，并明确记录每一步的来源与状态。

同时进行受阻和取消场景回归，证明停止机制和原有授权门没有被破坏。若需要真实 QQ 或真实 LIFE 入口才能验证，使用实际集成链，不得仅以直接调用内部方法代替完整验收。

按项目既定纪律串行执行 ruff、format、mypy、全量 pytest、WebUI typecheck/Vitest/build、浏览器 E2E、Minecraft Node 单测及 E2E、数据库一致性、真实服务器和 CI。真机未执行时必须标记 `SKIPPED`。

## 六、范围冻结与交付

本阶段只解决探索结果的可信反馈与生活连续性。

暂不实施：
- 多段或无界路线规划。
- 挖掘、放置、攻击、合成和容器操作。
- 自动降低确认频率或新增自主执行授权。
- 新的记忆系统、任务状态机或调度器。
- 模型权重训练和自动修改代码。

交付：
1. 源码与运行环境审计。
2. 真实调用链及最小设计。
3. 实现、回归测试、数据库与幂等性证据。
4. 真实 Java 服务器结果及所有 SKIPPED 项。
5. 修改文件、数据迁移、敏感文件和工作区差异核对。
6. 最终裁决、提交 SHA、镜像/远端一致性和 CI 链接。
7. 明确未完成项及下一阶段建议。

**验收标准：一次真实探索带来的可信结果，能够影响罐头后续的生活规划；但这个反馈链绝不自行获得执行权限。**
