## §1. 产品目标

### 1.1 目标体验

罐头能够理解用户提出的基础制作需求，例如：

- “把这些橡木原木做成木板。”
- “帮我做 8 根木棍。”
- “用我背包里的材料做一点木板。”
- “先看看材料够不够。”
- “算了，先别做。”
- “材料不够的话就告诉我缺什么。”

她需要根据当前上下文、实际库存、游戏配方及当前任务状态决定如何处理请求。

完整执行链应当是：

```text
自然语言请求
    ↓
统一 LLM 决策入口
    ↓
TASK_PROPOSAL 或 QUERY
    ↓
严格校验目标与参数
    ↓
读取真实库存和配方
    ↓
验证材料、产物、空间及工作台要求
    ↓
构建有界且冻结的合成计划
    ↓
按既有策略及授权要求批准
    ↓
通过现有任务与工具执行链进行合成
    ↓
重新读取真实库存
    ↓
独立验证产物增加与材料消耗
    ↓
根据实际结果向用户报告
```

**目标不是让 LLM 自己编写合成指令并直接执行，而是让它理解用户目标，再由可信代码根据真实配方、库存和既有执行机制完成任务。**

### 1.2 核心验收场景

至少完成一种有真实结果的基础合成任务。

建议优先选择“使用橡木原木制作木棍”这一目标，前提是当前服务器配方查询、材料状态与现有合成能力确实支持该任务。它可以覆盖原材料检查、配方计算、中间产物与最终产物验证。

如果该配方或对应能力在当前实现中不可用，则由 DSH 根据实际注册能力选择另一个最简单的、确实支持的配方，并在开工报告中说明替代理由。

必须区分：

- 用户已提出目标；
- 合成计划已创建；
- 计划已获批准；
- 合成动作已执行；
- 产物已通过独立验证。

这几个状态不得混为一谈。

## §3. 合成任务的类型化契约

### 3.1 复用统一 LLM 决策

所有进入 Minecraft 角色处理链的自然语言输入，继续经过 Follow-up 4 的统一决策入口。

合成目标原则上使用 `TASK_PROPOSAL`，而不是让 LLM 直接通过 `ATOMIC_ACTION` 选择合成工具。

示例：

```text
“帮我做 8 根木棍”
    ↓
TASK_PROPOSAL
    ↓
受支持的合成目标解析
    ↓
库存与配方验证
    ↓
现有任务规划和授权流程
```

对于“材料够不够”“我有多少木板”之类查询，可以使用 `QUERY` 和既有只读能力。

必须保留 Follow-up 4 的类型化决策契约和严格解析。不得允许模型在 JSON 中自行写入授权结论、成功状态、风险豁免或任意工具名称。

### 3.2 引入最小的合成目标模型

在审查现有数据结构后，优先复用仓库已经存在的任务目标和配方模型。只有没有可复用接口时，才创建最小的数据结构。

逻辑上至少需要表达：

- 目标物品的规范标识；
- 目标数量；
- 配方标识或可核验的配方引用；
- 每次合成的产出量；
- 每种材料的需求数量；
- 现有库存中可用于该任务的数量；
- 是否需要工作台或其他现有条件；
- 计划中的合成操作与预计材料消耗；
- 执行前库存快照；
- 执行后预期库存状态；
- 任务预算与当前授权状态。

数据结构的具体字段由实际实现确定。

LLM 提出的物品名称必须转换为注册表或服务器可以识别的规范标识。无法唯一解析、没有支持配方或缺失关键参数时，必须澄清或明确不支持。

不得直接将 LLM 给出的自由文本配方作为执行依据。

## §4. 真实配方与背包验证

### 4.1 读取真实库存

通过现有 `minecraft_inventory` 只读能力读取当前背包。

必须区分：

- 背包读取成功且为空；
- 背包读取成功且有物品；
- 背包读取失败；
- 当前服务离线；
- 背包状态未知；
- 返回快照过期或无法确认当前状态。

不得将读取失败转换为空背包，也不得仅凭 LLM 上下文中的旧摘要确定当前材料数量。

合成任务在创建可执行计划前必须取得可用的真实库存快照。

### 4.2 配方查询与材料计算

优先使用项目已经存在且经审计可用的配方查询接口；如果 Minecraft Runtime 只是实现了基础 recipe test，却没有向任务规划暴露可复用接口，应先明确缺口，并建立最小必要的受限读取接口。

不得凭空猜配方、材料消耗、每批产出量或工作台需求。

对于目标数量 \(N\)，如果配方每次产出 \(q\) 个，所需批次数应由可信代码计算：

\[
\text{batches}=\left\lceil\frac{N}{q}\right\rceil
\]

再依据服务器实际配方计算材料需求。如果最终产出会超过用户指定数量，必须依据当前任务语义定义处理规则，并向用户说明，而不是静默消耗额外材料。

### 4.3 执行前检查

必须验证：

- 目标物品在当前实现中支持合成；
- 有可用且明确的配方；
- 材料数量充足；
- 背包及配方槽位符合实际合成条件；
- 需要工作台时，已经满足该条件；
- 合成计划在现有预算内；
- 当前任务与其他正在执行的动作不存在冲突；
- 任务需要的授权或确认已通过；
- 使用的物品和工具均来自可信的真实观察。

任何一项无法验证，都必须停止计划生成、澄清或安全退出。

禁止为了满足材料条件而自动丢弃物品、擅自打开容器或扩大任务范围。

## §5. 合成计划与现有执行链集成

### 5.1 规划边界

合成计划必须复用现有 TaskRuntime、任务授权、步骤授权、Policy、执行和验证体系。

不得建立第二套任务状态机，也不得通过直接调用 Mineflayer 或 Minecraft Service 的底层方法绕过既有安全链。

合成规划至少能够表达：

1. 初始库存观察；
2. 配方及材料验证；
3. 必要的前置准备；
4. 有界的合成步骤；
5. 合成结果检查；
6. 最终库存复核。

如果现有规划器不支持这些步骤，允许在审计后对现有规划器做最小范围的扩展；但不得绕过现有任务生命周期，也不得擅自修改数据库 schema 或迁移。

### 5.2 计划冻结

在计划进入批准或执行阶段后，必须冻结：

- 目标物品及数量；
- 配方与材料消耗；
- 每个合成步骤的输入和预期输出；
- 任务预算与范围；
- 最终库存后置条件。

计划冻结后，LLM 不能静默替换配方、增加数量、改变材料、插入额外操作或重新解释为另一个目标。

如果真实库存变化导致计划失效，应暂停或终止，并重新读取状态。任何重规划都必须重新经过参数、授权和预算检查。

### 5.3 合成能力白名单

Follow-up 4 的自然语言能力白名单不包含 `minecraft_craft`。在启用它之前，必须完成独立审计。

若合成工具已存在，应优先复用而不是创建重复工具。在证明其 schema、风险、授权、执行、取消和结果复核均满足要求后，才能将它接入专门的任务步骤。

如果合成能力实际不存在或无法安全复用，应明确记录阻塞项，而不是通过把工具加入通用自由调用白名单来“临时打通”。

本阶段只为基础合成任务开放最小必要能力。不得顺手开放容器操作、任意物品搬运、丢弃或其他世界修改工具。

## §6. 风险、授权和安全不变量

合成属于会改变真实世界状态的操作，必须遵守既有策略。

以下内容不得进行未经批准的修改：

- `ACTION_RISK` 及风险映射；
- `allow_medium` 默认值；
- ToolPolicy；
- 两道确认门；
- TaskAuthorization / TaskStepAuthorization；
- 用户与可信玩家身份校验；
- 任务预算、距离和时间限制；
- 冻结计划与计划哈希；
- Action Runtime 生命周期；
- 取消和停止语义；
- 真实库存验证；
- Follow-up 4 的通用决策契约与上下文来源可信度；
- 数据库 schema 和迁移。

如果当前合成工具的风险策略导致操作被阻止，本阶段必须如实处理。真实测试可以使用符合既有政策的显式用户确认或隔离测试配置，但不得为了通过而改变生产默认权限、绕过确认或篡改风险映射。

用户取消时，执行链必须停止派发后续步骤，清理相关的未完成状态，并处理晚到事件。

## §7. 独立结果验证

工具返回成功不等于合成任务成功。

### 7.1 库存快照

在第一次状态改变前，记录真实库存快照。每次合成后重新读取库存，并在最终完成时再次读取完整的可用库存信息。

验证器必须区分同名物品的原有数量与本次任务新增数量。

对于目标物品，依据前后快照计算：

\[
\Delta I_{\text{target}}
=I_{\text{after}}-I_{\text{before}}
\]

对于材料，依据实际配方和合成批次数核对预期消耗，并明确处理同一物品既作为材料又作为目标产物的情况。

### 7.2 成功、部分成功与失败

必须能够区分：

- 计划成功生成，但尚未执行；
- 动作已经执行，但尚未完成后置验证；
- 完成并通过库存后置验证；
- 部分完成；
- 材料不足或库存变化导致阻塞；
- 合成失败；
- 取消；
- 服务器断开或状态不确定；
- 库存读回失败。

如果已经制作了一部分物品但任务未完成，必须报告实际新增数量，不得谎称全部成功。

如果合成工具报成功，但库存没有出现相符增量，必须暂停任务并检查状态，不能直接重试以避免重复制作。

## §8. STOP/CANCEL、异常与并发

必须继承 Follow-up 3 和 Follow-up 4 已验收的控制语义。

测试至少包括：

- 创建计划前取消；
- 等待确认时取消；
- 执行步骤之间取消；
- 合成工具超时；
- 合成后库存读取超时；
- 服务器断开；
- 材料被外部玩家或其他行为改变；
- 任务状态异常；
- 并发聊天与合成请求；
- 旧动作的晚到成功或失败事件；
- 同一任务重复终态事件。

STOP/CANCEL 必须及时生效，不依赖 LLM 完成调用；不能因取消消息被分类为 `CHAT` 或 `NARRATION` 而忽略正在执行的控制动作。

旧任务的晚到事件不能修改无关的新任务、重派合成步骤或造成重复制作。

## §9. 确定性测试与路由矩阵

所有测试必须通过现有统一决策入口、可信校验器和真实任务组装接口进行验证。允许使用脚本化 Provider 验证确定性分支，但必须标清它不能代替真实模型评测。

### 9.1 决策与参数

至少覆盖：

1. 明确要求制作合法目标及数量；
2. 只说“做一点木板”，缺少必要条件时按任务语义采用已定义的默认值或澄清；
3. 目标物品未知；
4. 当前没有支持配方；
5. 材料不足；
6. 工作台条件不满足；
7. 背包读取失败；
8. 世界服务离线；
9. 非法决策 JSON；
10. 未注册或不允许的合成能力；
11. 含有伪造授权字段的模型输出；
12. 合成数量越界；
13. 模型生成了与任务目标不一致的额外操作。

### 9.2 执行及结果

必须覆盖：

- 计划生成后、确认前无世界修改；
- 未批准时不得创建可执行动作；
- 合成步骤使用真实注册能力；
- 每一步使用正确的配方及参数；
- 执行后真实读取库存；
- 目标产物增量符合预期；
- 材料消耗符合配方；
- 产物数量错误时失败关闭；
- 工具返回成功但库存未变化时不得宣告成功；
- 部分完成时准确报告；
- 取消和异常后不重复执行。

至少使用真实哨兵检查：

- AgentRuntime 调用；
- ToolExecutor 调用轨迹；
- TaskRuntime 任务与步骤状态；
- 实际 Minecraft Service 动作；
- `action_id`；
- 执行前后的真实库存；
- 任务终态和后置验证结果。

不得仅凭文本断言或工具 `ok=true` 就判定任务成功。

## §10. 真实 Provider 与真实服务器验收

### 10.1 真实 Provider

使用当前实际可用的 WorkBuddy2API Manager 与 CatooBot Provider 配置（如果开工时仍然可用），验证模型能否：

- 将明确制作请求识别为受支持的 `TASK_PROPOSAL`；
- 将库存查询请求识别为 `QUERY`；
- 对缺少关键参数的目标澄清；
- 对不支持的物品明确拒绝或澄清；
- 不因提示词注入而输出未注册能力或伪造权限；
- 不将聊天或叙述升级成合成任务。

记录实际 Provider、模型标识、预期决策、实际决策、延迟、重试与错误。

语义评测集必须预先标记并保留版本。若沿用 42 样本集，应先完成 Follow-up 4 的统计复核，并确保新合成样本独立记录。

### 10.2 真实 Minecraft 服务器门禁

至少完成一个真正改变背包状态的合成闭环：

1. 使用真实 Java Minecraft 服务器及真实 CatooBot Minecraft Runtime。
2. 由真实游戏客户端在游戏内发送自然语言请求。
3. 真实 Provider 输出类型化决策。
4. 系统读取真实背包和支持的配方数据。
5. 生成合成计划并满足现有批准要求。
6. 通过既有执行链实际完成合成。
7. 独立读取执行后的真实库存。
8. 证明目标产物实际增加，且材料消耗符合配方。
9. 记录任务 ID、步骤 ID、相关 `action_id`、服务器结果及前后库存快照。
10. 若任何关键证据缺失，真实闭环不得记为 PASS。

真机脚本按项目现有纪律保留在本地，不因验收需要而将测试凭据、模型密钥或专用环境脚本发布到镜像。

真实 Provider 测试和真实服务器测试必须分开记录。二者都通过才算完成真正的合成闭环。

## §11. 明确不属于本阶段的范围

本阶段不得顺带实现：

- 新的矿物采集或自动挖掘能力；
- 方块放置或建造；
- 敌对生物交互或自主战斗；
- 玩家物品交付；
- 通用容器整理；
- 自动丢弃物品以清理空间；
- 无限探索或无限制作；
- 新的任务状态机；
- 未经批准的数据库 schema 或迁移；
- 训练或更新模型权重。

如果发现当前合成目标无法安全实现，应明确报告缺少的能力、阻塞位置及证据。不得为了阶段进度降低安全边界。

## §12. 门禁与回归

```powershell
pytest tests -q

ruff format --check .
mypy app
```

同时执行项目现有凭据扫描、数据库迁移演练、合成相关 Minecraft Runtime 测试及其他发布前检查。

必须覆盖：

- Follow-up 3 决策契约和路由矩阵；
- Follow-up 4 上下文、语义路由和真实查询相关测试；
- Phase 8D 木材采集；

不得删除断言、降低阈值、扩大超时或增加没有解释的 skip 来获取绿色结果。

CI 若命中已知环境敏感 E2E flake，应记录失败证据并只重跑失败 job。重跑成功不等于故障已经从根本上修复。

## §14. 最终报告格式

最终报告至少包含：

2. 开工基线与真实 Git 状态。
3. Follow-up 4 评测数据统计复核结果。

5. 实际合成工具、配方接口和执行链审计。
6. 合成任务的决策、参数和配方契约。
7. 上下文、库存和配方真实数据来源。
8. 计划冻结、授权、执行和库存后置验证设计。
9. 所有新增测试、全量测试及静态检查结果。
10. 真实 Provider 语义验证结果。
11. 真实服务器合成闭环证据。
12. STOP/CANCEL、异常和重复事件回归。
13. 受保护文件、数据库 schema 和迁移核验。
14. 变更文件、净增删行数和提交 SHA。

16. 尚未验证的项目及下一阶段建议。

所有数字与结论必须来自实际输出，不得预先填写通过结果。

## §15. DoD — Definition of Done

仅当以下条件全部满足时，才允许判定 `PASS`：

- [ ] 开工前完成真实仓库与合成能力审计。
- [ ] Follow-up 4 的统计矛盾得到可复现解释，或明确记录未能复核的证据限制。
- [ ] 已注册并审计的基础合成能力通过统一 LLM 决策与现有任务链接入。
- [ ] 用户提出基础制作目标后，模型能够提出正确的类型化任务决策。
- [ ] 当前背包和配方经过真实读取及可信校验。
- [ ] 材料不足、目标不支持、服务离线或参数非法均会安全退出。
- [ ] 合成计划有明确数量、材料、步骤、预算和后置条件，并在执行前冻结。
- [ ] 现有授权、确认门、Policy、AgentBridge 和 Action Runtime 全部保留。
- [ ] 不新增未批准的 Minecraft 世界修改能力、数据库表或迁移。
- [ ] 合成动作由既有任务和执行链完成，而非通过底层旁路。
- [ ] 执行后真实库存验证能区分成功、部分成功、失败和未知结果。
- [ ] STOP/CANCEL、并发、异常恢复和晚到事件测试通过。
- [ ] 全量测试与静态检查通过，无新增无解释的 skip。
- [ ] 真实 Provider 的任务决策行为有独立证据。
- [ ] 真实 Java 服务器至少完成一个合成任务的实际执行与库存增量验证。
- [ ] 文档、实现提交、证据提交、镜像、远端和 CI 证据一致且可核验。

如果真实 Provider 或真实服务器验收因为环境问题无法完成，必须明确标为 `SKIPPED` 或 `BLOCKED`，最终裁决为 `PARTIAL`；不能仅凭脚本化工具返回值或单元测试宣称真实合成闭环通过。

**最终原则：LLM 理解用户想制作什么；真实配方和背包决定是否可制作；现有任务及授权机制决定能否执行；服务器状态和独立库存验证决定是否成功。**
