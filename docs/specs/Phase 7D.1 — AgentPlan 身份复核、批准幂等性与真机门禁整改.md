## 1. P1 — 修复跟随任务与 AgentPlan 的重复指纹关联缺陷

### 1.1 审计发现

在基线源码中，`AgentPlanService.plan_follow_from_user()` 先调用 `TaskRuntime.create_task()`，随后才调用 `_create()` 保存 AgentPlan。存储层 `create()` 遇到唯一指纹冲突时会返回已有 AgentPlan。

因此，同一个目标、相同 10 分钟指纹桶内重复发出跟随请求时，存在如下风险：新 Task 已创建，但 `_create()` 返回旧 AgentPlan，旧记录的 `task_id` 与新 Task 不一致。随后确认新 Task 时，`plan_for_task()` 可能无法找到关联记录，而当前身份复核函数又将“计划查不到”解释为放行。

### 1.2 修复要求

1. 重新设计 USER 跟随请求的幂等顺序，保证在创建 Task 前就处理同指纹已有记录或占用该指纹；不得先创建一个可能无法关联 AgentPlan 的 Task。
2. 对已有记录，读取其关联 Task 的实际状态。若已有 Task 仍待确认或正在执行，不得重复创建 Task，应返回已有任务的可审计状态或提示用户处理已有任务。
3. 若已有计划关联的是终态 Task，不得无声地将它当作新任务计划，也不得创建新 Task 后再接受旧 AgentPlan。必须定义有界、确定且可测试的重试/新请求策略。
4. 考虑并发重复请求，不仅仅处理顺序调用。唯一指纹约束或原子占用必须真正保护关键区间。
5. 如果 Task 创建成功但 AgentPlan 关联持久化失败，必须采取明确的安全补偿：取消或安全回滚尚未执行的待确认 Task，并记录可查询的失败原因。不能留下一个没有可信计划关联的跟随任务。
6. 不要假设跨 SQLite 表与 TaskRuntime 的调用天然具备同一事务。必须在设计里写清楚崩溃边界、补偿策略与恢复策略。
7. 只在当前架构能保证关联一致性的范围内修改。若无法安全保证，应拒绝新任务并返回明确错误，而不是放行。

### 1.3 必须新增的回归测试

- 同一指纹桶对相同目标连续发送两次跟随请求。
- 第一份 Task 已终态、同桶内第二次请求。
- 第一份 Task 仍为 `PENDING_CONFIRMATION`、同桶内第二次请求。
- 两个并发请求竞争同一指纹。
- Task 创建成功但 AgentPlan 写入失败。
- 进程在 Task 创建与计划关联之间中断后执行恢复。

每项都必须断言：没有孤儿跟随 Task、没有错误 task_id 关联、不会产生重复执行，并且最终结果可通过日志/持久化记录审计。

## 2. P1 — 将跟随任务的确认前身份复核改为真正 fail-closed

### 2.1 审计发现

基线 `QQTaskEntry._verify_follow_identity()` 在若干异常或数据缺失路径返回 `None`，而调用方把 `None` 当作允许继续：例如 AgentPlan 服务不可用、读取 Task/计划发生异常、关联计划找不到或目标 UUID 缺失。

对于实际包含 `minecraft_follow_player` 的待确认任务，这些条件并不能证明身份复核“不适用”。复核依据缺失时不应放行。

此外，必须验证服务器范围，而不能只比较玩家 UUID。可信目标至少应核对 `VERIFIED` 状态、`player_uuid`、当前 `server_id`，并与待确认 Task 实际被冻结的跟随参数保持一致。

### 2.2 修复要求

1. 从**当前 Task 的实际冻结步骤**识别该任务是否含 `minecraft_follow_player`，不能完全依赖 AgentPlan 是否存在来判断任务类型。
2. 普通非跟随任务继续走原有确认逻辑；但一旦确认该 Task 是跟随任务，缺失或无法读取必要复核信息必须拒绝确认。
3. 对跟随任务，以下任何情况都不能允许进入动作派发：
   - AgentPlan 缺失或无法读取；
   - 当前 Task/冻结步骤无法可靠读取；
   - `PlanTarget` 缺失、UUID 缺失或冻结参数与可信目标不一致；
   - 身份解析异常、缺失、冲突、撤销或不再是 `VERIFIED`；
   - `player_uuid` 不一致；
   - `server_id` 不一致或当前服务器身份无法可靠确认；
   - 当前身份桥返回的玩家名与冻结计划中的用户名不一致。
4. 对以上失败，返回明确拒绝结果，并使用既有安全路径取消仍处于待确认状态的跟随任务（如果取消失败，必须记录失败并继续阻止确认；不能声称已成功取消）。不得以异常处理为由退回 `None` 放行。
5. 只有能够证明当前任务是普通非跟随任务时，才允许跳过跟随专用身份复核。遇到无法判定任务类型的读取错误时，采用安全拒绝，而不是猜测。
6. 身份复核逻辑应保持范围窄、可审计，不得改变其他 Task 的风险或授权语义。

### 2.3 必须新增的负面测试

至少覆盖：

- 跟随任务缺少 AgentPlan；
- `plan_for_task()` 抛异常；
- `runtime.current()` 或读取冻结任务失败；
- 跟随 Task 的目标 UUID 缺失；
- 身份绑定撤销、冲突、缺失或换号；
- UUID 相同但 `server_id` 不同；
- 当前 VERIFIED 身份与 Task 冻结的 username 不一致；
- 身份复核失败时取消调用本身失败。

每个用例都必须证明 `confirm_and_start()` 不会被调用，`minecraft_follow_player` 不会被派发，且失败原因有审计记录。

## 3. P1 — 修复 LIFE 计划过期批准和并发双重批准

### 3.1 审计发现

基线 `AgentPlanService.approve()` 检查了来源、状态和计划步骤，但未在创建 Task 前直接检查 `plan.expired_at(now)`。`handle_qq()` 从开放计划中选择 `READY_FOR_APPROVAL` 时，也未直接排除期限已过但尚未被 `expire_due()` 更新状态的计划。

另外，当前流程在调用 `TaskRuntime.create_task()` 之后才尝试将计划变成 `LINKED`。两个并发批准请求可能都通过 `READY_FOR_APPROVAL` 检查，并分别创建 Task，之后才争抢状态更新。

### 3.2 修复要求

1. `approve()` 必须使用同一个 `now` 在创建 Task 前直接检查 `expires_at`。如果过期，原子地将仍处于开放状态的计划更新为 `EXPIRED`，记录原因，且不创建 Task。
2. `handle_qq()` 选择候选计划时同样必须排除已过期计划。定时 `expire_due()` 仅是清理机制，不是批准入口的安全边界。
3. 为批准操作增加原子占用/条件状态更新。只有一个请求能将指定计划从 `READY_FOR_APPROVAL` 占用为批准处理中状态（可复用既有 `APPROVED` 状态），其他并发请求必须失败退出，不得创建第二份 Task。
4. 占用操作必须同时保护过期条件：仅当当前数据库记录仍未过期且状态仍符合要求时才能成功。请依据现有 SQLite store API 设计 compare-and-set/事务操作。
5. 记录批准者 `user_id`、`session_id` 和 `approved_at`，并继续要求第二道 `TaskRuntime` 确认门绑定同一人、同一会话。
6. 如果 Task 创建失败，必须将占用状态安全地终结（例如转为 `CANCELLED` 并写清失败原因），不能留下永远无法解释的 `APPROVED` 半完成记录。
7. 如果 `create_task()` 返回一个已进入 `FAILED` 等非预期状态的记录，也不能当成成功创建了待确认任务。必须验证实际返回状态，然后安全补偿与记录审计。
8. 任务成功创建后，计划与唯一 `task_id` 的关联更新必须有明确结果。如果关联失败，不能向用户宣称批准完成；应采取安全补偿并使故障可追踪。
9. 「批准」命令在多个待批准 LIFE 计划并存时，仍需避免误批准错误计划。至少明确当前规则、返回被批准计划的可识别摘要，并保证过期、重复或并发请求不能越权。如果当前产品暂时保留“取最近一份”规则，应在回复中明确计划目标和摘要，不能含糊地批准用户未看过的计划。

### 3.3 必须新增的回归测试

- `expires_at` 已过，但尚未运行 `expire_due()`，随后收到「批准」。预期：计划过期、零 Task。
- `handle_qq()` 面对已过期但数据库状态仍为 `READY_FOR_APPROVAL` 的计划。预期：不批准、不建 Task。
- 同一计划两个并发批准请求。预期：恰好一个占用成功，至多一个 Task。
- 计划占用后 `create_task()` 抛异常或返回非 `PENDING_CONFIRMATION` 状态。预期：没有错误的成功宣告，没有无法解释的半完成记录。
- Task 建立后 AgentPlan 关联更新失败。预期：安全补偿与审计记录有效。
- 第二道确认由不同用户或不同会话发出。预期：既有确认门拒绝，零动作。

## 4. P1 — 完成真实 Minecraft Java 中途世界变化门禁 C

### 4.2 安全的验证方式

优先选择一个可控的真实测试环境：

- 使用独立测试世界/测试服务器，或
- 使用第二个真实客户端/管理员控制台作为外部操作者。

不得为此在生产机器人执行链里添加 `setblock`、任意命令执行、临时高权限接口或绕过 Policy 的测试开关。

### 4.3 真机测试步骤

1. 在真实 Java 服务端建立一个可以确定性复现的多步任务，记录初始世界状态、任务计划、计划 hash、步骤 checkpoint 与预期结果。
2. 按既有确认流程授权后，等待任务实际进入运行状态，并确认至少已观察或完成一个步骤。
3. 由第二个客户端或测试服务器控制台在任务中途真实改变下一步依赖的世界状态，例如移除/替换预定目标方块或使计划依赖的目标丢失。记录改变前后的实际世界状态与准确时间戳。
4. 观察机器人后续真实反应：必须停止原计划中已不再满足前置条件的动作，进入既有 `REPLANNING`、安全暂停/失败或其他正确的受控路径；不可对过期目标盲目继续。
5. 对比任务事件、checkpoint、Policy/ActionRuntime 日志及新的 SAFE 世界观察，证明世界状态变化确实发生在任务运行中，并且导致了对应的控制结果。
6. 验证没有未授权的后续世界动作、没有把失败写成成功、没有重复执行已经完成的非幂等动作。
7. 保存可复现的命令/操作步骤、时间线、关键日志、任务 ID、plan hash、前后世界状态，以及结果判定。

若当前环境无法提供第二操作者或管理员控制台，允许先保持 `BLOCKED/SKIPPED` 并报告具体障碍；不得把单测、既有历史案例或代码结构证明包装成这次 Real Java C 已通过。
