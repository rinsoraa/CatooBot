## §1. 任务目标

### 1.1 产品目标

罐头不应再依赖一个仅负责木材请求的意图解释器来决定自然语言消息能否进入 Minecraft 行动链。

本阶段将所有进入 Minecraft 角色对话链的用户自然语言消息统一交给 LLM 理解与决策。LLM 根据当前系统实际提供的上下文，判断用户是在闲聊、查询、叙述、发出行动请求、提出多步骤目标、表达否定、要求澄清，还是取消或停止正在进行的行动。

决策结果必须以明确、类型化、可验证的数据结构传递给现有运行时，再由普通代码负责权限检查、能力分流、执行和结果验证。

目标体验示例：

| 用户输入 | 期望的决策方向 |
|---|---|
| “这里的树真高啊。” | 结合语境判断为感叹或闲聊，不自动砍树 |
| “帮我砍 8 个橡木原木。” | 在目标与参数验证通过后进入现有木材任务链 |
| “木头不够做工作台了。” | 结合已有上下文判断是陈述、建议还是隐含目标；必要时澄清，不能仅因出现“木头”便行动 |
| “你看看附近有什么。” | 只有在存在可用的只读观察能力时才查询；回答必须有真实观察证据 |
| “走到那个玩家旁边。” | 只能使用现有且经过验证的玩家目标、移动能力和权限路径 |
| “别挖了，停下来。” | 立即走已有安全停止路径，不等待 LLM 完成推理 |
| “帮我把这里围起来。” | 如果当前没有适用的、已注册且获准执行的建造能力，应澄清或说明不支持，不得自行放置方块 |
| “去把那只怪打掉。” | 本阶段不得新增战斗能力；应依据当前已实现能力和策略明确处理，不得绕过限制 |

**核心原则：每条用户自然语言消息都必须经过统一的 LLM 决策入口，但并不是每条消息都可以执行 Minecraft 动作。**

本阶段不要求一次性实现全部 Minecraft 基本操作。它要求建立能够承载未来能力的通用决策架构，让木材、采矿、合成、方块放置、实体交互和物品交付以后都使用统一的语义决策机制，而不是各自形成独立的关键词或专用分类入口。

### 1.2 本阶段交付结果

完成以下工作：

1. 查清当前自然语言输入的真实调用链及所有可能进入 Agent、Tool、TaskRuntime、CharacterRuntime 和 Minecraft Action Runtime 的路径。
2. 建立统一、显式、类型化的 LLM 回合决策契约。
3. 将通用决策入口接入现有 Minecraft 自然语言处理链，消除“木材专用解释器决定其他所有消息去向”的架构依赖。
4. 将决策结果安全映射到现有聊天、只读查询、原子工具、木材任务、澄清、拒绝、取消和停止路径。
5. 以真实调用计数器、哨兵、轨迹和确定性测试证明：正常聊天不会误触发动作，合法请求不会因普通聊天短路而无故丢失，非法及不确定决策不能进入动作执行链。
6. 保留 Follow-up 2 的安全不变量，更新必要的回归测试与文档，并按仓库现有工作流程完成提交和发布证据。

## §3. 决策契约设计

### 3.1 统一类型化决策

建立由项目实际代码风格决定名称的类型化决策模型。可以采用枚举加数据类、严格 Pydantic 模型或仓库已有的等价结构，但必须满足：

- 决策类型显式；
- 必填字段和可选字段清楚；
- 参数有严格类型与边界验证；
- 未知决策类型、未知能力、非法参数和缺失字段不会被当作默认成功；
- 禁止用 `str | None`、空字符串或其他模糊值同时表达不同的路由语义。

决策至少支持以下语义类别：

| 类别 | 语义 |
|---|---|
| `CHAT` | 普通角色聊天 |
| `QUERY` | 对世界、玩家、背包或状态的查询 |
| `NARRATION` | 对当前情境的叙述或回应，但不主动产生世界动作 |
| `ATOMIC_ACTION` | 单步行动意图，限于已有且获准的能力 |
| `TASK_PROPOSAL` | 希望达成一个有限目标，需要进入现有任务规划、校验及授权流程 |
| `CLARIFY` | 关键意图、参数、目标或授权条件不明确，需要先询问 |
| `UNSUPPORTED` | 所需能力没有实现、不可用或未获准 |
| `CANCEL` | 请求取消相关任务或动作 |
| `STOP` | 请求立即停止正在进行的相关行动 |

最终类型名称可按仓库约定调整，但不得删除上述语义边界，也不得将所有非聊天输入合并为一个泛化的“执行”类别。

### 3.2 决策数据结构

设计一个经过严格校验的决策结果，至少需要表达：

- `kind`：决策类别。
- `reply_text`：如果本回合需要直接回复，其回复内容。
- `capability_id`：适用时引用一个已注册的能力，而不是任意工具名。
- `arguments`：适用时携带经过 schema 验证的参数。
- `task_goal`：适用时描述待规划目标。
- `clarification_question`：需要澄清时要向用户询问的问题。

字段命名可以调整，但字段含义必须明确。

以下信息不得由模型自行决定为可信事实：

- `action_id`；
- 已获得授权的结论；
- 风险等级或风险豁免；
- `allow_medium` 状态；
- 策略检查是否通过；
- 用户身份是否可信；
- 工具是否真实执行成功；
- 任务是否完成；
- 最终世界状态。

这些值必须来自真实运行时、可信身份解析、策略组件或独立验证器。

LLM 可以提出意图、目标和参数候选，但不能通过返回 `"authorized": true` 一类字段让系统绕开正常安全检查。

### 3.3 决策输出解析

实施严格的模型输出解析与校验。

必须考虑：

- 合法结构化输出；
- 非法 JSON；
- JSON 被普通文本包裹；
- 字段类型错误；
- 枚举值未知；
- 能力不存在或不在允许范围内；
- 参数缺失、越界或类型错误；
- 回复里包含伪造的工具调用 JSON；
- 模型拒绝、超时、异常和空输出；
- 上下文或目标引用无法验证。

**不得将模型原始文本直接当成可执行工具调用。不得从任意文本中宽松提取一段 JSON，再将其交给执行器。**

如果模型输出无效，应走明确、可观测的失败或澄清路径。允许有限次数的结构化重试，但必须有明确次数上限、记录每次结果，且不能在重试失败后静默降级到未经校验的通用工具调用。

## §4. 统一 LLM 决策入口

### 4.1 所有自然语言消息的统一语义决策

本阶段要求所有进入 Minecraft 角色自然语言处理链的用户消息，首先进入统一的 LLM 决策入口，然后再决定后续行为。

不允许出现以下架构：

```text
出现“木头”关键词
    → 木材专用意图判断
其他所有输入
    → 直接决定走普通聊天或其他硬编码分支
```

目标架构：

```text
用户自然语言消息
        │
        ▼
统一 LLM 回合决策入口
        │
        ▼
严格解析与类型校验
        │
        ▼
安全分流器
        │
        ├── CHAT / NARRATION
        │       └── 角色回复，不执行世界动作
        │
        ├── QUERY
        │       └── 现有只读能力（仅在已验证可用时）
        │
        ├── ATOMIC_ACTION
        │       └── 已注册且现有的单步能力
        │
        ├── TASK_PROPOSAL
        │       └── 现有任务规划、授权与生命周期
        │
        ├── CLARIFY
        │       └── 澄清回复，不执行世界动作
        │
        ├── UNSUPPORTED
        │       └── 明确说明限制，不执行世界动作
        │
        ├── CANCEL
        │       └── 既有取消和清理流程
        │
        └── STOP
                └── 最高优先级停止控制路径
```

这张图是目标结构，具体代码位置需由调用链审计决定。

### 4.2 是否使用同一次 LLM 调用完成回复

优先评估是否可以使用一次受约束的 LLM 调用同时输出类型化决策和聊天回复，从而避免聊天被无意义地调用两次。

如果受到现有角色运行时架构限制，需要在决策后再调用既有的 `CharacterRuntime.respond(..., mode=CHAT_ONLY)`，则可以采用两次受控调用，但必须：

1. 明确区分决策调用与回复生成调用；
2. 保证回复生成仍是 `CHAT_ONLY`；
3. 不因为第二次调用而重新打开 Agent 或 ToolOrchestrator；
4. 不把未经验证的决策 JSON 原样呈现给用户；
5. 在阶段报告中记录实际调用次数、延迟和成本影响。

无论使用一次还是两次调用，每条自然语言输入都必须有对应的 LLM 决策记录。不得声称未实际测量的调用次数或性能收益。

### 4.3 与现有木材任务的兼容

木材请求不再作为通用入口的唯一特例，但现有木材处理链和已验收校验必须继续工作。

要求：

- LLM 负责理解用户语义并提出木材任务候选。
- 既有木材肯定请求验证和参数校验仍须执行。
- 只有正向意图明确、目标参数合法且满足现有条件时，才允许进入现有木材计划链。
- 否定请求、歧义请求、需澄清请求、非法参数和解释器异常不能因未进入木材链而自动回落到通用 Agent 或 ToolOrchestrator。
- 不得让 LLM 直接绕过任务计划、授权、预算或后置验证。
- 不得因为通用 LLM 已经分类为 `TASK_PROPOSAL`，就假定任何任务都已具备执行能力。

本阶段只需通过统一决策契约承载当前已支持的木材任务，不应在此阶段扩展复杂采集能力。

## §5. 当前可用能力的路由规则

本阶段不新增 Minecraft 动作，但必须使统一决策入口能够正确使用已存在、已注册并经审计确认可用的能力。

### 5.1 现有能力审计

根据当前仓库实际情况核验能力目录和执行路径，重点审查已接入的：

- 世界状态只读观察与查询；
- 聊天能力；
- `look_at`；
- `stop`；
- `move_to`；
- `follow_player`；
- 现有木材任务链。

这只是审计线索，不代表所有工具当前均可由自然语言直接调用。

应根据实际 schema、风险、身份要求、配置开关和权限门逐项建立本阶段的允许路由清单。

### 5.2 路由约束

- `QUERY` 只能进入已审计的只读能力；若没有实际可用路径，必须明确返回不支持，不能编造观察。
- `ATOMIC_ACTION` 必须引用已注册能力并满足现有参数、目标、身份和策略要求。
- `TASK_PROPOSAL` 必须进入既有任务运行时和授权机制，不能直接操作 Mineflayer 或 Action Runtime。
- 所有实际动作必须复用当前 Policy、AgentBridge、Action Runtime 与其执行前后检查。
- 模型输出的任意工具名称、任意 JSON 或自然语言步骤不得被自动注册为新能力。
- 未列入本阶段允许路由清单的能力不得因为 LLM 判断“用户想要做”就被打开。

`move_to`、`follow_player` 等现有能力如受明确用户意图、LOW 风险条件或额外策略限制，必须维持原有限制。当前能力注册清单和具体策略若与本任务书示例不同，以实测的仓库实现及受保护安全要求为准。

### 5.3 未来行为只保留接口，不提前开通

本阶段只为未来统一接入能力定义决策契约，不实施以下新功能：

- 新的采矿和无限资源探索行为；
- 方块放置及自动建造；
- 攻击实体和自主战斗；
- 通用物品丢弃或玩家交付；
- 新的合成工作流；
- 新的任务状态机或数据库 schema。

未来能力必须逐类立项、开发和验收。不得以“通用 LLM 路由”的名义提前打开。

## §6. 上下文边界与数据真实性

本阶段必须先明确哪些上下文已经真实存在于当前调用链，不能假定所有数据已经可用。

应审查现有代码实际提供的：

- 当前用户消息与对话历史；
- 已关联的角色记忆；
- 已验证的 QQ / Minecraft 身份信息；
- 当前活动任务及步骤状态；
- 当前世界观察；
- 玩家、方块和实体的实际引用；
- 背包快照；
- 当前启用的工具及配置。

### 6.1 本阶段需要做什么

- 决策输入结构必须允许显式表示已获得的上下文，以及未获得或不可用的上下文。
- 当前链路已能稳定提供的数据，可以在不扩大本阶段范围的前提下复用。
- 未接入的数据必须保留为未知，不能伪造为空背包、无玩家、没有目标或其他看似确定的状态。
- 与世界事实相关的决策必须能够区分“模型推断”与“真实观察证据”。
- 如果用户的要求依赖实时世界状态，而当前没有可验证的观察数据，应调用现有只读能力（如确实存在）或向用户说明无法确认。

### 6.2 不属于本阶段的工作

本阶段不要求全面重构记忆系统、身份系统或 Minecraft 感知系统。不得为了让演示通过而加入一套模拟真实世界的假数据。

如果审计发现记忆、实时观察或能力目录尚未可靠接入，应记录缺口，并在 Follow-up 4 中专门处理。

本阶段的通过不等于已完成“基于所有记忆和实时世界上下文的高准确率通用决策”。

## §7. STOP、CANCEL、否定输入与回合隔离

### 7.1 停止优先级

停止控制不得依赖 LLM 返回速度、模型可用性或输出格式。

对可识别的紧急停止和取消请求：

1. 必须尽可能在现有控制路径中及时生效；
2. 不得等待 LLM 完成推理后才允许停止；
3. 自然语言消息仍应进入统一决策流程并留下对应的决策记录，但该记录不能成为停止生效的前置条件；
4. 若消息同时包含停止和其他行动诉求，停止优先，不能在同一个请求中继续启动新动作；
5. 必须复用既有停止、取消、清理和晚到事件处理机制。

既有控制命令语义和 Phase 7F.5.3 生命周期不因本阶段而重写。仅在回归测试明确证明存在新缺陷时，才允许进行最小修复并单独记录证据。

### 7.2 否定与歧义

至少覆盖：

- 否定请求：“不要挖矿。”
- 取消正在执行的行动：“别挖了。”
- 单纯描述：“我不喜欢这里的洞穴。”
- 感叹：“那棵树真高。”
- 不明确的目标：“去那里看看。”
- 缺失必要参数：“挖一点矿。”
- 未支持的目标：“给我建一座城堡。”
- 带上下文的指代：“把那个拿过来。”
- 玩家身份不明确：“给小王一些木头。”
- 互相冲突的请求：“继续挖，但马上停止。”

不能因为含有动作关键词，就把上述输入一律分类为执行意图。

### 7.3 并发与隔离

模式、决策对象和参数必须按回合传递，不得引入共享的可变全局路由开关。

测试至少证明：

- 并发的聊天和行动请求不会共享或污染决策类别；
- 前一回合的工具意图不会泄漏到下一回合；
- 异常和超时后能够恢复；
- 旧任务的晚到事件不会改变不相关新回合的路由；
- 每条消息及其决策、任务和动作轨迹可以正确关联。

## §8. 安全日志与决策可观测性

本阶段应扩展现有结构化日志或诊断事件，使开发者能解释一条消息为什么走到特定路径。

根据现有日志设计，至少记录以下信息中适用的部分：

- `turn_id` 或可关联的回合标识；
- 决策类别；
- 路由目标；
- `reason_code`；
- 决策解析成功或失败；
- 能力标识；
- 参数校验结果；
- 策略检查结果；
- 任务标识和运行时生成的 `action_id`；
- 决策耗时及实际 LLM 调用次数；
- 动作是否开始、是否结束和后置验证结果。

**`reason_code` 应由可信代码生成，而不是直接相信模型自行报告的原因。**

建议覆盖以下故障区分：

- `decision_model_error`
- `decision_timeout`
- `decision_schema_invalid`
- `unsupported_capability`
- `parameter_validation_failed`
- `policy_denied`
- `capability_disabled`
- `service_offline`
- `action_failed`
- `verification_failed`
- `action_succeeded`

具体名称可遵从仓库现有约定，但不能把以上不同情况全部合并为“未执行”或“模型没有选择工具”。

日志不得输出原始敏感聊天内容、完整记忆内容、访问令牌、API Key 或异常正文中可能包含的敏感信息。需要关联内容时，优先使用现有脱敏、摘要或安全标识机制。

不要为了通过日志测试而把原文复制进新的诊断字段。

## §9. 测试与验收设计

必须增量添加测试，不得仅凭手动聊天成功或现有全量测试通过就宣布完成。

### 9.1 决策契约单元测试

覆盖：

- 所有合法类别；
- 缺失字段；
- 非法 JSON；
- 未知枚举；
- 错误参数类型；
- 未知能力；
- 模型超时、异常和空输出；
- 工具调用型 JSON；
- 非法输出后的安全失败；
- 有界重试次数和错误记录。

### 9.2 全入口路由矩阵

使用脚本化 Provider / LLM 替身，让每种输入获得预先指定的决策结果，再验证实际分流。

至少包括：

| 输入类别 | 预期行为 |
|---|---|
| 普通聊天 | 产生角色回复；Agent、Tool、任务和世界动作均无非预期调用 |
| 世界查询 | 仅使用经审计的只读路径；无能力则明确不支持 |
| 普通叙述 | 回复或继续正常对话，不自行触发世界动作 |
| 合法木材请求 | 进入既有木材校验和计划路径 |
| 否定木材请求 | 不进入木材计划和动作路径 |
| 模糊采矿请求 | 澄清或不支持，不进入采集执行 |
| 现有 `look_at` 请求 | 仅在能力及参数合法时调用现有执行路径 |
| 现有移动/跟随请求 | 保留当前风险与明确意图限制 |
| 未支持的放置请求 | 不得调用放置动作 |
| 未支持的战斗请求 | 不得调用攻击动作 |
| 非法决策输出 | 安全失败，无世界动作 |
| 模型超时或异常 | 明确结束或澄清，无世界动作 |
| STOP / CANCEL | 控制路径不依赖 LLM 返回；生命周期回归通过 |
| 并发回合 | 决策和动作状态互不污染 |

对普通聊天、否定、歧义、非法输出和不支持能力，必须用真实调用哨兵证明：

- `AgentRuntime.handle_control()` 调用数；
- `AgentRuntime.run()` 调用数；
- `ToolOrchestrator.run()` 调用数；
- `TaskRuntime.create_task()` 调用数；
- 计划服务调用数；
- Minecraft Service 动作数；
- 是否生成了不应存在的 `action_id`；
- 动作追踪列表中是否出现意外执行记录。

不能仅通过检查回复文本或者日志为空，推断没有发生副作用。

### 9.3 已有安全边界回归

保留并运行 Follow-up 2 的测试：

- `tests/test_phase8e_followup2_turn_mode.py`
- Phase 8D 与 8E 既有相关测试；
- Follow-up 1 和 Follow-up 2 已验收用例；
- 控制命令、busy 行为、隐私日志、否定分流及木材正向流程回归。

必须特别注意：Follow-up 2 中部分 `turns == 0` 断言用于证明旧路径不进入角色运行时。统一决策入口会改变部分内部调用结构。如果这种断言因安全的决策调用发生变化，只允许在确认测试语义确实变化后进行最小调整，并改用真实 Agent、Tool、TaskRuntime 和 Service 哨兵继续证明零副作用。禁止简单删除失败断言或放宽全部测试。

### 9.4 变异测试

至少执行以下变异，并证明测试可以捕获：

- **M1：** 绕过统一决策入口，直接进入旧的木材或普通聊天分支。
- **M2：** 将普通聊天分支错误映射到可执行工具的正常 Agent 路径。
- **M3：** 让无效的模型输出或未知能力继续进入 ToolOrchestrator。
- **M4：** 让否定或歧义输入回落到可执行路径。
- **M5：** 让 STOP/CANCEL 等待 LLM 返回后才生效。
- **M6：** 将异常正文或原始敏感输入写入日志。
- **M7：** 把一个回合的模式或路由结果污染到并发回合。

每个变异都应记录变异点、预期失败的测试、实际失败结果和恢复后验证结果。变异后必须恢复源码，并核验没有残留。

如果某项变异无法实施，应说明具体原因，并提供等价的负向测试证据，不得虚报验证通过。

### 9.5 真实 Provider 验证

脚本化模型测试只能证明：给定一个决策结果，代码是否正确分流。它不能证明真实模型理解用户语义的准确率。

若当前环境能够安全调用真实 Provider，应建立一个小型、可复现的自然语言验证集，覆盖肯定、否定、感叹、歧义、指代、澄清、停止、未支持能力和多轮上下文。

记录：

- 测试样本及其预期类别；
- 实际决策类别；
- 错误类型；
- 是否发生非预期工具或动作调用；
- Provider 与模型标识；
- 延迟、重试次数及可获得的成本数据。

不得在日志或报告中暴露 API Key、聊天隐私或完整敏感上下文。

如果没有可用的真实 Provider，明确标记为 `SKIPPED`，并说明这是环境限制。不得用脚本化替身数据冒充真实 Provider 的准确率。

## §10. 明确禁止的实现方式

以下任何一项发生，均不得判定本阶段 PASS：

1. 仍然让木材专用解释器决定所有消息的最终分流。
2. 以增加关键词、正则表达式或硬编码意图规则的方式代替统一 LLM 决策。
3. 将 LLM 生成的 JSON 直接作为任意工具调用指令。
4. 为了使普通请求可以行动而全局启用 Agent 或 Tool。
5. 将 `CharacterTurnMode.NORMAL` 视作“用户同意执行”的证明。
6. 修改 `ACTION_RISK`、`allow_medium` 默认值、现有确认门或授权机制以便测试通过。
7. 绕过 `TaskTurnHandler`、TaskRuntime、Policy、AgentBridge 或 Action Runtime 直接操纵 Mineflayer。
8. 通过共享全局布尔值决定所有并发回合的工具能力。
9. 将真实世界状态、物品数量、目标身份或动作成功结果交由模型自行编造。
10. 为通过测试而删除已有安全断言、增加无解释的 skip，或者降低原有保护标准。
11. 把未来的采矿、合成、放置、战斗或物品交付能力提前纳入执行白名单。
12. 引入本阶段未批准的数据库表、迁移或第二套任务生命周期。
13. 仅凭当前全量测试通过，便声称真实 Provider 决策准确或真实 Minecraft 动作闭环已验证。
14. 在没有证据的情况下声称 CI、远端同步、真机测试或发布完成。

## §13. DoD — Definition of Done

只有以下条件全部满足，才允许判定 `PASS`：

- [ ] 开工前完成真实仓库及调用链审计。
- [ ] 所有 Minecraft 角色自然语言输入均经过统一 LLM 决策入口；停止控制不依赖模型响应。
- [ ] 决策协议类型化、严格校验，模型输出不能自行授予权限。
- [ ] 旧的木材专用判断不再是所有消息的通用总入口；既有木材安全校验与任务链保持完整。
- [ ] 普通聊天、叙述、澄清、拒绝与非法输出不会产生非预期 Agent、Tool、Task 或 Minecraft 世界副作用。
- [ ] 已存在的单步能力仅通过经审计的路由和原有策略被调用。
- [ ] 未支持的采矿、合成、放置、战斗及交付能力不会因为模型提出请求而被打开。
- [ ] 回合隔离、停止、取消、异常恢复和原有生命周期回归通过。
- [ ] 决策轨迹能够区分关键路由、模型、配置、策略、服务及执行失败。
- [ ] 相关测试、全量测试、静态检查和凭据扫描实际执行并通过。
- [ ] M1–M7 变异验证有真实、可审计的结果。
- [ ] 真实 Provider 测试的执行状态明确；未验证事项被完整记录。
- [ ] 受保护文件没有未批准变化。
- [ ] 文档、提交、工作区、镜像、远端和 CI 证据一致且可核验。
- [ ] 最终报告严格区分已完成、未完成、未验证与被跳过项目。

只要有关键安全不变量未通过，或者存在未经解释的执行链回落，就必须裁定 `PARTIAL` 或 `FAIL`，不能为了阶段进度强行宣布 PASS。

## §14. 本阶段完成后的后续方向

本阶段的通过，只表示通用 LLM 决策契约与统一安全路由已建立，不代表所有 Minecraft 能力已经可用。

后续建议：

- **Phase 8E Follow-up 4：** 记忆、实时世界观察、身份、背包和能力目录的上下文整合，以及真实 Provider 语义质量验证。
- **后续合成阶段：** 在统一决策入口下完成材料检查、配方验证、合成和库存后置验证。
- **后续采矿扩展阶段：** 逐类增加有界资源采集能力。
- **后续放置阶段：** 建立单独的方块放置风险、授权和结果验证。
- **后续战斗阶段：** 另行设计敌对实体交互范围和安全政策，不得由本阶段默认开放。
- **后续交付与经历回流阶段：** 继续沿用统一决策契约与现有授权、任务和验证基础。

**最终产品原则：LLM 负责理解语境并提出决策；可信代码负责校验权限、执行有限动作和验证真实结果。能力可以逐步扩展，但绝不能通过扩大模型输出的自由度来替代安全设计。**
