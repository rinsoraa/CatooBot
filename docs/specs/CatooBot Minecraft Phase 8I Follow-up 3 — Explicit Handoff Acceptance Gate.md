## 1. 目标

修复 Phase 8I H3 的剩余语义缺口：

> 存在待决资源交接，不代表用户已经接受。只有当前消息被可靠识别为对该待决提案的明确接受，才可以消费提案并进入既有资源任务入口。

当前新增的 `_is_new_craft_request()` 只识别一种“不是接受”的消息类型，不足以证明其余消息都是接受。

特别关注以下风险路径：

1. 用户提出合成需求，罐头给出资源获取提案。
2. 用户没有接受，而是发送一个新的采集请求，例如“砍两根橡木原木”。
3. 决策层将新采集请求归类为 `TASK_PROPOSAL`。
4. 现有分支尝试接受旧提案，可能忽略用户当前请求并消费旧提案。

本阶段必须通过真实路由测试证明该路径已被关闭。

## 4. 第二阶段：补齐接受判定

实现一个最小且可测试的接受门，遵守以下契约。

### 4.1 可以接受的消息

当存在同一用户、同一 session 中尚未过期的待决资源提案时，类似下列表达可作为候选接受语义：

- “同意”
- “可以”
- “好，去砍橡木原木”
- “好，就按这个方案来”

具体规则应结合当前对话路由确定，不能仅凭“决策层判成 `TASK_PROPOSAL`”就认定已接受。

### 4.2 必须识别为新意图的消息

至少覆盖：

- 新合成请求：“给我做 64 块橡木木板”
- 新采集请求：“砍两根橡木原木”
- 与待决方案无关的其他新任务
- 询问、澄清或不确定表达
- 否定、取消或 STOP/CANCEL 表达

新目标必须按其自身语义走原有规划及安全链。不得把它静默解释成对上一轮资源提案的接受。

对确实存在歧义的消息，必须要求澄清或走现有安全拒绝路径。不得消费旧提案来猜测用户意图。

### 4.3 状态生命周期

- 只有通过接受门后，才能消费待决提案。
- 接受仍必须经过原有批准与执行确认门。
- 未通过接受门时，不得建立由旧提案派生的采集任务。
- 新目标、取消及过期提案必须有明确、可测试的状态处理。
- 不得因失败重试、重复消息或无关消息复活已消费的提案。
- 用户与 session 隔离必须保持。

## 5. 第三阶段：真实路由回归测试

新增或扩展测试，直接执行真实 `_route_turn` 路径或等价的完整桥接调用。不能只断言某条消息是不是合成请求。

必须至少覆盖以下矩阵：

| 场景 | 期望行为 |
|---|---|
| 存在待决提案，用户明确接受 | 进入既有资源规划；继续经过原有确认门 |
| 用户重复提出合成请求 | 重新评估合成目标；不接受旧提案 |
| 用户提出新的采集命令 | 不消费旧提案；按新意图走原有路由 |
| 用户提出无关新任务 | 不消费旧提案 |
| 用户仅询问或表达不确定 | 不启动资源任务；必要时澄清 |
| 用户明确拒绝、取消或 STOP | 不启动资源任务；不复活提案 |
| 待决提案已经过期 | 不创建任务；明确提示重新观察或重新提出需求 |
| 不同用户或 session | 不得跨用户或跨 session 消费提案 |
| 提案已经被接受一次 | 重复接受不得创建第二个资源任务 |
| 新请求数量或树种不同于提案 | 不得静默使用旧提案中的目标与数量 |

对每个负向用例，明确断言：

- 旧提案未被误消费
- 不存在意外建立的资源任务
- 没有动作执行轨迹或非预期 `action_id`
- 背包及世界状态没有因这条负向消息发生变化

如果合法的新请求本身会建立任务，则应验证它独立走完既有批准与确认流程，而不是用“任务数为零”错误地限制正常功能。

## 6. 第四阶段：真实服务器验证

使用真实 Java 服务器、真实 MinecraftService、真实 Provider 与可用的第二个 Mineflayer 客户端验证关键路径。

至少执行：

1. 缺料请求 → 真实观察到资源目标 → 资源提案。
2. 明确接受 → 既有资源任务进入原有确认门。
3. 在另一个独立会话中重复请求合成 → 不得消费旧提案。
4. 重新提交新的采集请求 → 不得静默转化成旧提案任务。
5. 明确接受有效提案后完成资源任务；确认新合成计划仍需要新确认。
6. STOP/CANCEL 或外部状态变化时，禁止迟到执行与虚报成功。

对于负向消息，应检查完整任务记录、动作轨迹及库存快照，不得只根据聊天回复判断通过。

如果第二客户端不可用，可以保留独立的桥接事件注入测试，但必须明确标记为替代证据，不能冒称第二客户端真机测试。
