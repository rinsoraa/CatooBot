# CatooBot Phase 7F.4 — Action Dispatch & Recovery Safety

## 目标

基于当前最终提交 `4ce219d2acda2aa92486ac4ca88c9eb1227f7d9c`，修复 TaskRuntime 在“外部动作已经接受，但本地尚未持久化动作关联信息”时的恢复歧义。

这是恢复可靠性阶段，不新增 Minecraft 游玩能力，不扩大权限。

## 一、先审计当前真实调用链

重点检查：

- `app/tasks/runtime.py`：`_run_step`、`_invoke_step`、`_settle`、`resume`、`recover`、动作事件处理与任务终态转换。
- `app/tasks/models.py`：`TaskRecord`、`TaskStep`、动作关联字段、序列化与反序列化。
- AgentBridge / ActionRuntime / Minecraft runtime 的动作启动、action_id 返回、事件关联与状态查询。
- 现有授权和恢复测试，尤其是取消后恢复、`WAITING_ACTION`、`RUNNING` 步骤与进程重启场景。

已知风险窗口：

外部 runtime 已经接受动作请求，但进程在任务记录持久化 `action_id` 之前退出；恢复后如果只根据本地记录判断，就可能再次发起同一个动作。

先给出状态机与崩溃窗口分析，再实施修复。不要假设只在 `_settle` 里增加一次 `_save` 就能解决问题，因为外部副作用可能发生在第一次持久化之前或之后。

## 二、核心不变量

必须明确区分以下状态：

1. 已持久化派发意图，但还不能证明外部 runtime 是否接受。
2. 已接受动作，已知 `action_id`，正在等待真实终态。
3. 外部动作终态已知，可以安全继续推进。
4. 外部是否接受动作存在歧义，暂时无法安全恢复。

**恢复时，不得将“动作状态未知”直接等同于“动作没有执行”，然后无条件重新派发。**

如果 runtime 支持稳定幂等键和按键查询，应优先使用它们；如果无法确认外部执行状态，则必须采用受控暂停与人工介入等安全策略，不得虚构 exactly-once 保证。

## 三、实施要求

### 1. 派发前持久化

在可能产生真实外部副作用之前，先持久化足以识别这次逻辑派发的信息。

字段与状态设计应优先复用现有 `TaskRecord` / `TaskStep` 序列化模型；先确认现有数据库存储结构是否允许无迁移扩展，不要先入为主地新增列或新表。

### 2. 稳定关联及去重

审计 runtime 是否可以支持稳定的调用关联键，例如基于 `task_id`、冻结 `plan_hash`、`step_id` 与明确派发代次构成的 idempotency key。

要求：

- 同一派发请求的重放可以被识别，不产生第二个独立动作。
- 服务端已经接受请求但客户端丢失响应时，可以通过同一关联键查询或复用原动作。
- 必须区分“崩溃后恢复同一次未决派发”和“原动作已经明确终止后，用户按既有语义显式恢复该步骤”。
- 新的显式执行尝试必须有持久化、可审计的代次，不能因重启自动生成一个新的键来掩盖重复派发。
- 不能仅在 Python 内存中做去重。进程退出和 runtime 重启都必须纳入设计。

如果当前 runtime 无法实现可靠幂等与查询，应明确记录能力限制，并先实现 fail-closed 歧义处理，不要模拟一个并不存在的服务端保证。

### 3. 恢复语义

针对派发前、派发中、已接受但未写回 action_id、等待动作、已完成但未保存终态等窗口，逐一建立明确的恢复策略。

必须保持：

- 已完成步骤的持久化结果不被无故覆盖。
- 未完成动作的真实状态得到核验，不能只信任旧的内存状态。
- 取消、过期或撤销授权的任务不能因为恢复而重新执行。
- 已验证的多段路点不会重新触发不必要的移动。
- 未经确认的下一步不能因恢复跳过逐段验证。
- 需要用户重新确认的计划，仍通过现有确认机制处理。

## 四、必须增加的故障注入测试

至少覆盖以下时点：

1. 写入派发意图之前崩溃。
2. 派发意图已持久化，但尚未向 runtime 发送请求。
3. runtime 已接受请求，但本地尚未持久化 `action_id`。
4. `action_id` 已持久化，但尚未进入稳定等待状态。
5. 外部动作已经结束，但终态尚未持久化。
6. 同一任务经历恢复或重复事件投递。
7. 动作明确失败、取消后，用户通过既有入口显式恢复。
8. 任务在崩溃期间过期、撤销授权或被取消。
9. 多段路线的当前段恢复后，仍先验证前序路点，不得直接执行后续路点。
10. runtime 查询结果未知、冲突或无法关联时，系统安全停止，不得猜测。

测试应检查外部动作启动次数、真实 action_id 关联、任务持久化状态和最终世界动作数；不能只检查函数返回值或终态枚举。

对于每个“崩溃点”，说明预期恢复行为及其为何不会重复派发。

## 五、权限与范围边界

本阶段不做：

- 新 Minecraft 工具或新世界操作。
- 改变 19 个工具、`ACTION_RISK` 或 `allow_medium=false`。
- 改变 LifeIntent、TaskProposal、AgentPlan 的语义。
- 绕过计划批准、第二道执行确认、TaskAuthorization、TaskStepAuthorization 或 Policy。
- 改变多段探索的最大三段与共享 24 格预算。
- 修改 `explore_legs=1` 的默认值。
- 引入无界自动重试。
- 因恢复实现困难而把动作失败伪装成成功。
- 修改真实 Character Bible、密钥、`.env` 或敏感配置。

本阶段继续仅限现有 SAFE 观察、LOW 移动与 SAFE 朝向动作。
