## 1. 核心目标与非目标

### 1.1 必须完成的目标

**F1 — 诊断世界观测不一致**

确定服务器中的真实方块状态、Mineflayer 客户端收到的方块状态、世界视图中的观察结果，以及 `minecraft_find_blocks` 的查询结果是否在同一个维度、同一个坐标系和同一个时间窗口内。

必须找出“方块已改变但查询结果为 0”属于哪一类原因：

- 服务器拒绝了实际写入，方块从未改变。
- 服务器已改变，但客户端尚未收到或加载对应区块。
- 客户端观察已更新，但业务世界视图没有更新。
- 世界视图已更新，但查询过滤、搜索范围或方块匹配存在问题。
- 查询使用了不同的客户端、世界、维度或坐标。
- 其他能够由原始证据证明的原因。

不得事先认定是服务器延迟、Mineflayer 缓存或查询实现缺陷。

**F2 — 建立可靠的真实工作台测试夹具**

使用已存在且被允许的测试环境准备方式，在测试世界中获得一个实际存在、可被 CatooBot 客户端观察到且满足交互距离约束的工作台。

夹具准备应与产品执行链分离。产品自身不获得自动放置工作台、修改地形或其他未授权的世界修改能力。

**F3 — 完成真实 3×3 合成闭环**

使用实际生产 Provider、真实 Minecraft 服务器、实际 CatooBot Runtime，以及独立的第二个 Mineflayer 游戏客户端发送用户消息。

必须证明工作台被真实观测到、真实配方被查询、计划按既有机制冻结、确认前无合成副作用、确认后实际执行合成，并由独立的真实背包读取验证产物净增和材料净耗。

**F4 — 查清迁移演练 `ok:false`**

沿着真实演练入口、返回值生成位置和原始日志追踪失败标志。确定它究竟表示：

- 演练真正失败。
- 没有需要执行的迁移，但现有工具把 no-op 报告为 `ok:false`。
- 某一检查未执行或返回不完整。
- 其他可证实的原因。

不得单纯修改最终 JSON 或报告文字，把未知失败改成成功。

**F5 — 最小范围修复和回归**

如果前述调查确实发现产品代码、测试夹具或迁移状态报告的缺陷，可以在本任务书范围内提交最小必要修复和回归测试。

如果问题来自测试环境而非产品代码，不得为了消除 BLOCKED 状态而修改生产安全策略。

### 1.2 明确不做

本阶段不是新的合成能力开发阶段。禁止扩大以下范围：

- 不开发自动放置或破坏方块能力。
- 不开发自动采集材料、挖矿、容器操作或替代配方链。
- 不开放 `minecraft_craft` 为自然语言自由能力。
- 不新增工具风险等级，不修改 `ACTION_RISK`、`TOOL_ACTION` 或 `allow_medium` 默认值。
- 不绕过用户确认、Policy、TaskAuthorization 或 TaskStepAuthorization。
- 不另建任务执行状态机，不更换 AgentBridge、Action Runtime 或现有授权链。
- 不进行数据库 schema 扩展，不重构迁移框架。
- 不因测试不稳定而放宽断言、删减测试、降低预算检查或屏蔽错误。
- 不把 mock、合成的方块响应、固定 Provider 返回值或单测通过结果当作真实服务器闭环证据。

如果现有环境或底层工具确实要求扩大权限才能继续，必须停止该部分并提交独立审批提案。

## 3. F1：世界方块观测一致性诊断

### 3.1 先确定数据流

沿现有实现追踪并记录：

1. 操作客户端发起的操作以及服务器实际回执。
2. 服务器侧可观察的最终方块状态。
3. CatooBot 的 Mineflayer 客户端收到的方块更新。
4. `minecraft_world` 的位置、维度、`self` 状态和 `age_seconds`。
5. `minecraft_find_blocks` 的实际搜索中心、半径、方块过滤与返回结果。
6. 工作台感知模块如何消费这些结果并生成六态状态。

优先阅读现有实现和日志，不要在没有证据时重写整条数据链。

重点审计以下问题：

- `setblock` 的“拒绝”是否表示方块没有被放置成功。
- 查询是否在方块变化之前、之后或客户端收到区块更新之前执行。
- `blockAt`、方块变化事件与 `findBlocks` 是否针对同一世界和同一 Mineflayer 客户端。
- 区块未加载时，工具是否错误地将未知状态转换成“附近没有方块”。
- 是否存在坐标、维度、半径、过滤器或数据键不一致。
- 世界视图年龄是否足以证明当前方块列表新鲜。
- 是否存在仅刷新部分状态、但未刷新方块观察的路径。

### 3.2 可复现诊断方法

使用真实测试服务器中的单一、已知测试坐标。只有在准备方式获得允许并被记录后，才执行方块状态实验。

对同一个坐标至少记录以下信息：

| 时点 | 必须记录的内容 |
|---|---|
| T0：夹具操作前 | 服务器/操作客户端的已知状态、CatooBot 客户端 ID、维度、玩家坐标、世界视图时间与方块查询结果 |
| T1：夹具操作返回后 | 服务器或操作客户端的原始回执、操作是否被接受、实际目标坐标 |
| T2：客户端收到更新后 | 可取得的方块更新事件、目标坐标的独立读取结果 |
| T3：业务查询后 | `minecraft_world` 原始关键字段、`minecraft_find_blocks` 参数及完整结果 |
| T4：有限观察窗口结束 | 是否出现延迟更新、更新发生的时间、查询结果是否与独立读取一致 |

可根据现有 API 设置有限、明确的只读观察窗口，例如立即、约 250 ms、1 s、2 s、5 s 进行观察。该时间表仅用于读取观察结果，不得引出无限重试、重复放置或反复修改世界的循环。

如果某个读取接口不存在，不要临时增加新的生产工具来凑齐证据；先确认现有客户端 API、事件流或服务端日志是否能提供足够信息。

### 3.3 诊断裁定

必须形成可复核的因果链。至少回答：

- 哪一端第一次看到真实方块变化？
- `find_blocks` 返回 0 时，客户端是否已加载并观察到目标方块？
- 如果独立目标坐标读取成功而搜索失败，缺陷是在查询、过滤还是业务封装？
- 如果客户端本身没有收到更新，是否能够证明原因来自区块加载、连接、维度或服务器端状态？
- 如果证据不能区分原因，缺少的关键证据是什么？

禁止使用“可能是缓存”“应该是延迟”等描述作为最终根因。

### 3.4 修复限制

只有在根因已被证据支持后才能修复。优先采用现有数据流内最小的修复方式。

任何修复必须遵守：

- 未知和过期状态仍然 fail-closed。
- 不得在无法证明搜索完整时把 0 个结果直接解释为 `NOT_FOUND`。
- 不得使用硬编码工作台坐标、伪造方块列表或过期世界快照。
- 不得扩大查询半径或无限等待来掩盖错误。
- 不得把测试夹具行为引入生产工具。
- 增加能稳定重现修复前缺陷的自动化回归测试。

如果最终证明旧行为符合设计、失败只是夹具没有建立成功，也要明确写出证据，不应为了产生代码差异而强行修改产品实现。

## 4. F2：准备真实工作台测试夹具

### 4.1 准备原则

夹具准备由独立于 CatooBot 产品执行链的测试操作客户端或测试人员完成。优先顺序：

1. 检查当前服务器是否已具备权限正确、可重复使用的测试夹具。
2. 优先由测试人员在测试世界手动放置工作台，并报告实际坐标、维度及放置结果。
3. 如果确需操作客户端自动准备夹具，只能使用独立的本地门禁脚本或测试操作客户端，且必须确认该方式在服务器上得到授权。
4. 如服务器不允许相应操作，不得连续重复失败的 `/setblock` 请求。先查明权限、命令可用性和服务器回执，转为已获许可的手动准备方式。
5. 如果任何许可方式都无法建立夹具，停止真实合成场景，裁定 `BLOCKED` 或 `PARTIAL`，并列明唯一缺失的环境条件。

**夹具准备不是产品能力。** 不允许将操作客户端的管理员权限、命令权限或直接方块操作封装进 CatooBot 的公开工具。

### 4.2 夹具要求

真实门禁开始前确认：

- 工作台方块确实存在。
- 记录准确的维度和整数坐标。
- 工作台处在实际玩家可接近且满足运行时交互距离的范围内。
- 测试期间工作台不会被其他测试任务主动移走。
- 测试玩家与观测客户端所处的世界、维度和坐标一致。
- 背包包含目标配方实际要求的足够材料。
- 所需测试操作不会影响其他玩家或非测试世界状态。
- 门禁结束后能够如实说明夹具保留还是被人工清理。

材料必须来自真实背包读取。配方必须来自实际 `minecraft_recipe_lookup` 查询，不允许为了方便将预设配方伪装成实时查询结果。

## 5. F3：真实工作台合成闭环

### 5.1 测试条件

必须使用：

- 实际 Minecraft 服务器。
- 真实 CatooBot Minecraft Runtime 与 Mineflayer 客户端。
- 实际配置的生产 Provider。
- 第二个真实 Mineflayer 游戏客户端作为用户消息来源。
- 实际生产 `TurnDecisionInterpreter`。
- 既有任务计划、确认、授权和执行链。
- 独立的真实库存读取进行前后验证。

报告必须如实说明第二个客户端是自动化客户端，不得描述为真人手工聊天验证。

### 5.2 测试场景 A：3×3 单步真实合成

使用简单、可核查、需要工作台的真实配方，例如木镐；但确切配方 ID、数量、输入和输出必须以运行时真实查询结果为准，不能硬编码预期配方 ID。

测试步骤：

1. 读取并保存执行前的真实背包。
2. 查询真实配方及工作台状态。
3. 使用第二个 Mineflayer 客户端发送明确的合成请求。
4. 保存真实 Provider 的原始决策输出及规范化决策。
5. 确认决策进入正确的受管任务路线，`minecraft_craft` 仍不在自然语言自由能力白名单。
6. 构建计划，核验工作台坐标来自真实观察，配方来自真实查询，计划内容已冻结。
7. 保存计划哈希、任务状态、步骤信息和预期库存变化。
8. **在用户确认前核验零副作用**：无合成动作、无有效 `action_id`，且目标产物及材料没有被该任务改变。
9. 通过既有确认机制执行任务，不使用内部接口跳过确认门。
10. 获取实际动作终态和执行记录。
11. 重新读取真实背包，并通过独立读取核验合成结果。
12. 对比配方预期的产物净增和材料净耗。
13. 核对运行时后置条件验证是否成功。
14. 保存从用户消息到最终库存核验的完整关联证据。

如果产品只报告工具执行成功，但库存无法读取或变化不符合配方，不能算合成成功。不得因后置验证失败而自动重试可能已经发生的合成。

### 5.3 场景 B：工作台缺失的安全对照

可复用 Phase 8G 已有场景 B 原始证据。只有在原始材料不完整、无法复核或 F1 修复改变了行为时，才重新执行。

需要证明：

- 工作台缺失能够被正确观察或报告为未知。
- 不创建可执行的工作台合成计划。
- 没有自动放置或破坏方块。
- 不会因为模型提出合成请求而绕过工作台检查。
- 无法证明工作台不存在时，不会把“观察未知”伪装成“确定没有”。

### 5.4 成功标准

场景 A 只有在真实服务器中实际完成一次工作台合成，并且确认前零副作用、确认后库存净变化均得到独立核验时，才能标为 `PASS`。

以下情况都不能替代该证据：

- 工作台感知单元测试通过。
- 规划测试成功生成 DAG。
- Mock `minecraft_craft` 返回成功。
- 只看到 `action_id` 或动作终态为 `SUCCEEDED`。
- 只由同一个未经独立读取的运行时结果声称库存变化正确。
- 测试脚本直接调用低层合成接口，绕过正式聊天、计划与确认链。

## 6. F4：迁移演练 `ok:false` 根因调查

### 6.1 必须检查的链路

定位实际迁移演练入口，阅读其：

- 输入配置与数据库副本选择逻辑。
- 演练前后的完整性校验。
- 迁移发现与执行逻辑。
- 表数量、行数或其他数据保真检查。
- `ok` 字段的定义和所有返回分支。
- `no-op`、异常、跳过、部分执行和校验失败的状态语义。
- 实际退出码、原始输出和调用方如何消费 `ok`。

不能根据报告中的 `added_tables []` 或 `lost_rows {}` 反向推断所有检查都成功了。

### 6.2 必须得到的结论

最终报告应清楚说明：

1. `ok:false` 是在哪个函数、哪个判断分支产生的。
2. 该分支为什么被触发。
3. 演练是否实际执行了任何迁移。
4. 所有必需检查是否确实运行并成功。
5. `integrity`、表数量和行数检查能证明什么、不能证明什么。
6. 该问题是工具的状态表达缺陷、真实迁移失败，还是适用迁移为空的合法 no-op。
7. 是否需要源代码修复以及修复对旧调用方的兼容影响。

### 6.3 修复和限制

如果根因是合法 no-op 被不恰当地报告为失败，可以提出最小、兼容的状态表达修复，但必须确保：

- “无迁移可执行”与“迁移执行失败”可以被区分。
- 未执行的检查不会被描述为通过。
- 返回状态不依赖固定成功值。
- 真实异常仍然产生失败结果。
- 新增针对成功、失败和 no-op 的自动化测试。
- 如果修复会改变迁移接口契约，先审计所有调用方。

如果根因证明是实际迁移失败，必须修复根本问题或保持明确的失败裁决。不能修改 `ok` 的定义以规避错误。

如果确定没有任何适用迁移且 `ok:false` 只是一个有明确定义的“无需执行”状态，必须提供源码位置及实际输出证据，并说明为什么不需要修改。不必为了把 `false` 变成 `true` 而引入无关重构。

本阶段不得新增 schema、字段或迁移。若调查证明问题只能通过新增 schema 才能解决，停止并提交独立提案。
