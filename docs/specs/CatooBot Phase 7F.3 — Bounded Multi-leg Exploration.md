# CatooBot Phase 7F.3 — Bounded Multi-leg Exploration

## 任务目标

基于当前 `173819a19c27b45d383b2aa35a5462e32f41e0ac` 基线，实现第一个有界多段探索闭环。

Phase 7F.1 已实现真实单段探索；7F.2 已把可信探索结果接入生活规划；7F.2.1、7F.2.2、7F.2.2.1 已加固终态和坐标证据边界。

本阶段目标不是简单重复调用 `move_to`，而是让罐头能够沿一条**预先规划、长度有上限的路线**，逐段移动、重新观察、验证实际到达，并在失败、取消或证据不足时可靠停止。

这是确定性、有界的多段探索，不是无界 LLM 行动循环。

## 一、先审计现有架构

实施前，核对当前 `main` 和双目录状态，重点检查：

- `app/tasks/planner.py`：`plan_exploration_task`、目标选择、距离预算。
- `app/tasks/models.py`：`TaskPlan`、`TaskStep`、`ExpectedFinalState`、序列化和 `plan_hash`。
- `app/tasks/runtime.py`：步骤状态机、异步动作完成、最终状态验证、授权、取消与停止。
- `app/tasks/validation.py`：步骤数量和动作数量限制。
- `app/tasks/agent_planner.py`、`app/tasks/agent_service.py`：探索形状识别、计划批准与执行确认。
- `app/integrations/minecraft/memory_bridge.py`、`app/tasks/exploration.py`：现有可靠探索结果如何写入记忆。
- `tests/test_task_runtime_explore.py`、`tests/test_exploration_feedback.py` 及现有真实服务器 smoke 脚本。

先明确一个关键技术问题：

**当前全任务最终状态验证是否足以保证每一段到达后才执行下一段？**

如果现有实现无法提供这个保证，应先设计最小的逐段后置条件机制；不能因为最终终态验证存在，就默认中途每一段已经经过独立验证。

在架构审计后再实施，不要仅在 planner 中堆叠多组 `move_to` 步骤。

## 二、路线与执行规则

### 1. 有界路线

第一版约束：

- 最多 **3 段移动**。
- 每段均有明确目标、目标距离和到达半径。
- 整条路线的规划距离不得超过现有 Phase 7F.1 默认探索距离预算；先核对 `EXPLORE_DEFAULT_DISTANCE`，不得把原有单段预算无意扩大为每段预算。
- 总步骤数、LOW 动作数、任务时限和重规划次数必须遵守现有 `TaskConfig`、`validate_plan` 及注册工具的限制。
- 路线目标必须有限、可序列化、坐标有效、彼此有意义；不得重复生成同一个无效目标以凑足三段。
- 在世界观察不足以安全规划多段路线时，应明确缩短路线或 fail-closed，而不是伪造观察结果。

优先复用现有探索目标选择和 SAFE 世界观察能力。需要为逐段移动生成路点时，必须有确定性、可审计的规则，并为路点去重、距离预算、坐标合法性和不可达场景增加测试。

### 2. 计划必须预先冻结

所有计划中的路线目标、动作参数、到达半径和逐段后置条件，都必须在批准前确定。

确认以下条件成立：

- 路线的所有世界操作均包含在用户批准的计划内。
- 逐段坐标后置条件如果决定执行顺序，必须纳入冻结计划、计划序列化及相应授权指纹；不能批准一份计划后再静默修改。
- 现有 `plan_hash` 和授权模型必须覆盖所有实际影响世界操作与执行分支的关键参数。
- 执行期间可以提前终止原路线，但不能因为观察到新兴趣点就自行追加未经批准的新路点。

如确实需要改变路线，必须遵守已有受控重规划、计划失效和重新授权流程。不得绕过第二道执行确认门。

### 3. 每段执行与独立到达验证

每一段的基本过程为：

1. 执行该段已经批准的 `minecraft_move_to`。
2. 等待真实异步动作终态。
3. 重新读取 SAFE 世界坐标。
4. 使用经过校验的实际坐标，检查是否进入该段的目标半径。
5. 记录可审计的逐段验证结果。
6. 只有该段到达验证通过，且继续执行的前置条件仍成立，才允许执行下一段。

不能把 `move_to` 返回成功、任务计划批准、动作进入 `RUNNING` 或上报的位置直接当成已到达。

每一段至少记录路点编号、目标坐标、实际到达坐标、目标距离或验证结果、任务与动作关联标识，以及可确定的失败原因。

可在现有 `TaskStep` / `TaskRecord` 的序列化和验证契约内扩展。不要仅依靠内存变量保存关键验证证据，否则进程恢复可能丢失当前段的完成依据。

### 4. 对观察结果的响应

本阶段以冻结路线为基础，观察结果负责验证、继续或停止，而不是产生无界的新任务。

以下情况必须阻止后续移动：

- 当前段动作失败、超时或无法证明已完成。
- 重新读取世界坐标失败、离线、缺失或无效。
- 当前段到达验证失败。
- 当前世界状态与后续步骤前置条件冲突。
- 任务已取消、过期，或停止请求已经生效。

失败状态不能伪装为成功，也不得继续执行路线剩余段。取消仍须调用既有停止链路，并验证没有遗留动作。

新观察发现有兴趣点时，可以保留现有的可信记忆回流，但不得借此修改已批准路线。如果后续需要依据新事实选择一个不同目标，应经已有授权机制建立新的受控计划。

## 三、权限与产品边界

本阶段必须保留以下不变量：

- `LifeIntent` 是想法，不是动作。
- `TaskProposal` 和 `AgentPlan` 是计划，不是执行。
- 继续使用现有计划批准与独立执行确认两道门。
- `TaskAuthorization`、`TaskStepAuthorization`、Policy、AgentBridge、ActionRuntime 及身份校验继续生效。
- `pause`、`resume`、`cancel`、`expire`、超时、停止和受控重规划语义不变。
- 不因加入更多路点而扩大工具能力、风险等级或授权范围。

第一版仍限定为 SAFE 观察、LOW 移动及已注册的 SAFE 朝向操作；不增加挖掘、放置、攻击、合成、开容器或其他世界修改能力。

不得新增任意的执行旁路、动态授权或绕过既有确认机制的内部循环。

目前产品定义文档存在不完整问题。实施前应审阅现有产品定义、Phase 7E/7F 规范及已接受的阶段报告；对缺失的产品条款明确记录，不得将未写明的行为假定为用户已授权。

## 四、测试与验收

### 必须覆盖的自动化用例

1. 成功完成两段或三段路线，每段均有独立的实际坐标验证。
2. 第一段无法到达时，第二段、第三段均未发起移动。
3. 中间一段失败或世界坐标缺失时，后续移动不会执行。
4. 中间一段超时、取消或停止时，没有遗留异步动作，也没有额外路点被执行。
5. 路线超过段数、距离、动作数量或时限上限时，计划被拒绝或安全缩短。
6. 路点坐标为 NaN、Infinity、布尔值、不可转换类型或转换溢出时，计划拒绝。
7. 批准后任何路点、参数或关键后置条件变化都会被现有授权机制检测，而非静默执行。
8. 观察发现新兴趣点时，记忆回流仍然工作，但不会追加未经批准的路点。
9. LIFE 来源仍经过 `LifeIntent → TaskProposal → AgentPlan`，第一道门之前不创建 Task，批准后未经第二道确认不得执行。
10. 重复事件、进程恢复、已完成步骤重放和终态重放不导致重复执行或重复写入错误的成功记忆。
11. 单段 Phase 7F.1 与 Phase 7F.2 反馈行为完全回归。
12. 现有 `CANCELLED`、`FAILED`、`EXPIRED`、矛盾坐标及溢出坐标测试继续通过。

必须增加真正检查“中途验证失败后后续动作没有发生”的测试，不能只检查最终 Task 状态。

- Phase 7F.2 真实记忆回流及批准后 `PENDING_CONFIRMATION`、零真实动作验证

真实门禁不得以 mock、跳过、放宽到达阈值或仅看脚本退出码替代。

真实门禁会操作 Minecraft 并可能写入 live DB。运行前备份数据库、释放 runtime 唯一会话；完成后检查数据库、清理临时文件并恢复机器人运行。保留每个用例的真实终态与坐标证据。
