# CatooBot P2 Shadow Mode — 归因管道审计、覆盖率定位与 E3 补测

## 1. 裁决及授权范围

当前 P2：PARTIAL。

本任务属于已批准的 P2 影子模式闭环，不授权 P3，不接入严格归因终态，不修改现有 dig 成功判据、任务执行链、授权链、Policy 或确认门。

保留当前正式服务器使用边界。继续使用已经获准的本机测试服务器；如果需要重新安装模组，先备份世界，并在实验结束后验证卸载与配置回滚。

## 2. 第一阶段：修复确定的归因管道缺口

先审计并修复：

1. `Booking.reserve()` 必须验证 `session_ref` 属于当前有效的服务端会话，不能直接信任请求载荷中的会话标识。
2. JOIN、登记与 AFTER 事件应显式关联各自的会话，不得依赖 `lastSessionRef` 这样的全局可变值为事件补写会话。
3. 登记和事件匹配必须包含维度、精确坐标、规范化方块 ID、玩家身份及当前会话。
4. 事件载荷必须包含足够的关联信息，包括 `event_id`、`reservation_id`、`action_id`、`session_ref`、`session_seq`、玩家 UUID、维度、坐标及方块前后状态。
5. CatooBot 接收端应验证必填字段和关联一致性。缺少必要关联字段时，只能记为 UNKNOWN 或 REJECTED，不能将服务器提供的状态字符串直接视为已验证的动作归因。
6. 将 HTTP 推送从服务器事件回调中移至有界、异步、可审计的 OUTBOX 处理；事件捕获不得因网络等待而阻塞服务器主线程，队列溢出必须计数并如实报告。
7. 修复配置、协议和代码中任何与上述语义矛盾的描述。

保持 `enabled=false` 的默认关闭行为，不改变任何产品任务终态。

## 3. 第二阶段：补齐 E2 契约测试

新增或完善覆盖以下场景的测试：

- 非当前会话的 `session_ref` 登记被拒绝；
- 两个玩家先后 JOIN，旧玩家事件不会被写入另一个玩家的会话；
- 同坐标不同维度不得错误匹配；
- 精确方块 ID 比较，不发生 oak_log/dark_oak_log 等子串误匹配；
- 缺失、过期、重复、迟到、冲突及未登记事件均不能产生严格自证；
- 事件重复发送与接收端重启后按既定幂等规则处理；
- 通道超时、认证失败及队列溢出能够正确统计；
- STOP/CANCEL 不因事件推送阻塞，且终态不被影子模式改变。

执行 Java 逻辑测试、Python 单元和 HTTP 集成测试、类型/格式检查及相关 CI。保留首次失败结果，不能通过删减断言或改变测试标签凑 PASS。

## 4. 第三阶段：定位事件覆盖率

修复并通过 E2 后，再检查每次正常挖掘为何产生或没有产生 `PlayerBlockBreakEvents.AFTER`。

每次尝试至少记录：

- 唯一实验 ID、`action_id`、`reservation_id`；
- `session_ref`、`session_seq`、玩家 UUID；
- 登记是否成功，失败原因和 TTL；
- 目标维度、坐标和期望方块 ID；
- 服务端登记前读取到的目标方块状态；
- 客户端实际派发的 dig 开始/结束及终态；
- AFTER 是否触发、事件身份、方块前后状态；
- 事件是否成功送达、是否唯一匹配；
- 动作结束时的独立世界读数与对应库存证据（若本例涉及库存变化）。

建立每次尝试的时间顺序表。对未触发 AFTER 的情况，区分登记失败、目标在操作前已改变、动作未实际开始、挖掘没有成功、事件监听/推送异常，以及仍无法确定的其他原因。

不要以单一推测认定根因。无法区分的样本保持 UNKNOWN。

## 5. 第四阶段：重新执行 E3

在完成前述代码修复和回归后，使用已经获准的本机测试服务器完成：

- 10 次正常挖掘；
- 5 次在有效登记窗口内执行的外部 `/setblock` 移除；
- 5 次他人挖掘对照。

每次尝试均保留原始日志，并能将测试动作与登记、事件、世界结果和影子记录唯一对应。

明确区分以下指标：

- 登记成功率；
- 正常挖掘 AFTER 触发率；
- 所有送达事件中的唯一匹配率；
- 以正常挖掘尝试为分母的严格匹配率；
- 登记窗口中目标已变化但没有匹配事件的 UNKNOWN 比例；
- 推送失败、重复、迟到、重放和匹配歧义；
- 影子判定与当前实际任务终态之间的差异。

不要把没有事件的 `/setblock` 结果默认为外部归因已证实，也不要把事件未送达计为零未知。

## 6. 通过条件和停止点

P2 只有在以下条件全部满足时才能裁定 PASS：

1. E2 对会话、维度、方块 ID、关联与竞态的契约测试通过。
2. E3 样本量满足任务书要求，原始尝试和失败全部可追溯。
3. 正常挖掘、外部移除与他人破坏在影子证据中得到正确区分；未知情况不冒充成功归因。
4. 事件推送不阻塞 STOP/CANCEL，且故障和队列溢出可审计。
5. 影子模块不会影响任何现有产品任务终态或授权决定。
6. CI、静态检查、凭据扫描、仓库卫生与回滚验证通过。

如果任一项仍有实质性缺口，继续判 PARTIAL，并明确指出缺口和证据。

最终交付 P2 更新报告、E2/E3 矩阵、每次尝试的日志、统计口径、构建 SHA、CI、Git 状态和回滚结果后停止。不得进入 P3，不得宣称 N9-B 已关闭。
