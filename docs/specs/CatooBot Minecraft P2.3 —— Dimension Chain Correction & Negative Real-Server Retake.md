## 2. 修复 A：事件 JSON 必须输出真实维度

### 已知缺口

在 `CatooAttributionMod.java` 的 `eventJson()` 中，函数已接收 `dimensionId` 参数，但字段仍使用配置默认值：

```java
+ "\"dimension\":\"" + CFG.getProperty("dimension_label", "minecraft:overworld") + "\","
```

这会造成匹配器和日志使用真实维度，而推送至 Python shadow 接收端的 JSON 仍可能输出错误维度。

### 必须完成

1. 让事件 JSON 的 `dimension` 字段使用本次真实事件的 `dimensionId` 参数。
2. 不得将 `dimension_label` 作为真实事件维度的数据源。
3. 若保留 `dimension_label` 配置，必须明确其用途，确保它不参与事件维度判定和事件事实字段生成。
4. 若维度无法取得或规范化失败，输出不得回退为 `minecraft:overworld`。
5. 维度未知时，匹配状态必须维持安全降级，不允许产生 `SELF_CONFIRMED`。
6. 事件 JSON、服务端日志及 `Booking.match()` 使用的维度必须来自同一条真实事件数据链。
7. 如果改变事件格式，应同时检查 Python 接收端对字段的校验要求；不得放宽接收端规则来掩盖服务端缺陷。

### 必须增加的测试

- 实际维度为 `minecraft:overworld` 时，JSON 正确输出主世界标识。
- 实际维度为 `minecraft:the_nether` 时，JSON 正确输出下界标识。
- 将 `dimension_label` 强制设为 `minecraft:overworld`，实际事件维度仍为下界时，JSON 仍须输出下界。
- 事件维度为空或未知时，不得默认伪装成主世界。
- 测试必须调用实际的 `eventJson()` 生成路径，或覆盖等价的生产数据流；仅测试 `Booking.normalizeDimension()` 不足以证明此缺口已修复。

## 3. 修复 B：预约必须使用当前真实世界，而非过期 Session 世界对象

### 已知风险

当前 JOIN 处理创建 Session 时保存了世界对象；预约处理 `handleReserve()` 又通过 `session.world` 读取目标方块。

玩家改变维度时不会因普通的维度切换而必然触发新的 JOIN。因此，预约阶段可能读取到玩家进入服务器时的旧世界，而不是请求到达时的当前世界。

这会导致预约维度、读取方块的世界和真正发生破坏事件的世界不一致。

### 必须完成

1. 检查当前版本 Minecraft、Fabric API 和实际编译映射，确认取得在线玩家、当前世界及世界维度标识的正确 API。
2. 对预约请求，根据 `session_ref` 找到有效 Session，并核实与该 Session 绑定的实际在线玩家 UUID。
3. 在处理预约时获取玩家的**当前世界和当前维度**，不能将 JOIN 时缓存的世界对象视为当前世界的权威来源。
4. 同时校验：
   - `session_ref` 仍然有效且为当前 Session；
   - 实际在线玩家 UUID 与 Session 绑定 UUID 一致；
   - 请求中的 `dimension` 是有效标识；
   - 请求维度与当前玩家的真实维度一致；
   - 目标方块读取发生在这个实际世界的目标坐标；
   - 当前方块 ID 与 `expected_block` 精确匹配。
5. 若请求维度与当前玩家所在维度不同，拒绝预约，不得在错误世界继续读取方块。
6. 玩家不存在、Session 失效、维度缺失、世界不可用、维度不一致或世界状态读取失败时，必须 fail closed，不创建有效预约。
7. 检查 HTTP 请求处理线程与 Minecraft 服务端主线程的边界。若当前环境要求将世界访问安排在服务端主线程，应使用符合当前版本 API 的线程调度方式及有界等待机制；不得为读取世界状态而无保护地跨线程访问世界数据。
8. 调度超时、执行异常或等待结果未知时，必须安全拒绝；不得猜测世界状态或使用缓存值补齐。
9. 验证玩家切换维度后，旧世界对象不会被继续当成实时世界使用。
10. 保留现有 nonce、预约去重、TTL、Session 绑定和精确方块匹配契约。不要为了修复维度问题削弱这些门禁。

### 必须增加的测试

- 当前维度与请求维度相同时，目标世界与目标方块验证正确。
- 请求维度与当前在线玩家维度不同时，预约被拒绝。
- 玩家由主世界切换到下界后，预约读取下界当前坐标，而不是旧主世界的同坐标。
- 当前在线玩家不存在或 UUID 不匹配时，预约拒绝。
- 世界读取失败或主线程调度超时后，不创建可用于 `SELF_CONFIRMED` 的预约。
- Session 被替换后，旧 Session 和旧预约不能被新 Session 复用。
- 不得只用伪造的 `Session.world` 单元测试代替实际预约请求处理链测试。

如果发现当前服务端 API 限制导致无法安全完成这条数据链，必须准确记录阻断原因和所需改动，不得假定缓存世界对象始终正确。

## 5. 负向真机测试 A：跨维度破坏不得自证

### 测试目的

证明预约发生在维度 A、实际破坏发生在维度 B 时，即便玩家 UUID、Session、坐标和方块 ID 其余条件相似，也不会错误地产生 `SELF_CONFIRMED`。

### 测试步骤

1. 让机器人玩家处于主世界，记录当前 UUID、`session_ref`、`session_seq` 和世界维度。
2. 在主世界选择一个安全、可恢复、易于正常破坏的普通方块；优先使用 `minecraft:stone` 或 `minecraft:oak_log`。
3. 创建有效预约，记录 `reservation_id`、`action_id`、坐标、预期方块 ID 和 `dimension=minecraft:overworld`。
4. 不要执行实际目标方块破坏，保留预约。
5. 将同一玩家转移到另一个真实维度，例如下界，并在对应坐标准备相同方块 ID。外部命令只可用于布置测试夹具，不能冒充被测的玩家破坏事件。
6. 让玩家从水平方向正常破坏测试方块，优先使用历史上已证明可触发 `AFTER` 的普通完整方块及几何。
7. 确认本次确实收到 `PlayerBlockBreakEvents.AFTER` 事件，并记录事件的真实维度、UUID、坐标、方块 ID、关联标识、shadow 状态及原因。
8. 检查事件 JSON 推送中的 `dimension` 是否为实际维度。
9. 检查结果绝不为 `SELF_CONFIRMED`。

### 预期结果

- `event_dimension` 是玩家实际破坏所在维度。
- JSON 输出的 `dimension` 与真实事件维度一致。
- 原预约的维度仍是登记时的维度。
- 维度不匹配不能通过预约匹配。
- 预期结果是 `UNKNOWN` 或其他满足既有安全契约的非自证状态；不得将维度不一致视为成功。
- 日志和接收端记录必须能通过 `event_id`、`reservation_id`、`action_id` 等现有字段关联。

如果 `AFTER` 未触发，该次尝试只能记录为 `NOT VERIFIED`。更换方块类型、目标位置或水平接近方向，重新建立新夹具后再测试。不能将“没有事件”写成“维度校验成功”。

## 6. 负向真机测试 B：其他真实玩家不能消费机器人的预约

### 测试目的

证明一个有效在线的第二名玩家，即使破坏了机器人已预约的同一坐标、同一方块类型，也不能使机器人的预约成为 `SELF_CONFIRMED`。

### 测试步骤

1. 让机器人和第二名真实玩家同时在线。
2. 在同一维度选择一个可正常水平破坏的普通完整方块，例如 `minecraft:stone` 或 `minecraft:oak_log`。
3. 由机器人 Session 建立预约，记录机器人 UUID、Session、`reservation_id`、`action_id`、维度、坐标和预期方块 ID。
4. 确认第二名玩家的 UUID 与机器人 UUID 不同，并确认其在线 Session 与机器人预约 Session 不同。
5. 让第二名玩家实际破坏已预约方块，机器人本人不得执行这次破坏。
6. 确认真实 `AFTER` 回调被触发。
7. 核实服务端日志中的事件 UUID 来自第二名玩家对象，推送 JSON 中的 `player_uuid` 也与实际第二名玩家一致。
8. 检查机器人预约没有被消费成 `SELF_CONFIRMED`。
9. 记录实际返回的状态及原因。按当前匹配逻辑，预约归属与 Session 不一致应保持安全降级，例如 `UNKNOWN(stale_session)`；不能要求必须返回某个特定原因而导致测试放宽。
10. 另外确认第二名玩家的真实破坏事件没有被错误归属于机器人。

### 预期结果

- `AFTER` 真实触发。
- 事件中的 UUID 是第二名玩家的 UUID。
- 不发生机器人自证。
- 不发生跨 Session 预约消费。
- 接收端仍遵守既有事件关联和签名校验。
- 不修改产品任务终态，不把这条 shadow 记录作为机器人任务成功证明。

如果 `AFTER` 未触发，则本次仍属于 `NOT VERIFIED`；更换为已在真实服务器上验证过的方块及几何后再试，不能用单元测试替代真机结果。
