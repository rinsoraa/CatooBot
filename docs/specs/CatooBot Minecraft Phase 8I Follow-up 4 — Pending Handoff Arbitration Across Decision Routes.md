# CatooBot Phase 8I Follow-up 4 — Pending Handoff Arbitration Across Decision Routes

## 0. 基线与目标

仓库：`rinsoraa/CatooBot`

开工基线：`f161eee6242d146011311207319ff3e9e695af35`

目标：修复并验证待决资源提案与上游 `TurnDecisionKind` 之间的路由耦合，使明确接受、拒绝、取消及新目标在真实 `MinecraftChatBridge` 路由中得到一致处理。

本阶段不是重写 Phase 8I，不新增 Minecraft 能力。

## 1. 已知缺陷与必须解释的证据

Follow-up 3 的真实服务器报告出现以下情形：

1. 用户先取得资源交接提案。
2. 用户发送明确接受表达，例如「好，去砍橡木原木」。
3. 上游决策层将消息判成非 `TASK_PROPOSAL`，接受门没有被调用。
4. 某次重试中，相似消息进入既有任务入口并推进先前的白桦任务。
5. 另一轮真实验证中，同一表达又成功经过接受门。

当前 `chat_bridge.py` 在 `TASK_PROPOSAL` 分支之前，先将 `QUERY`、`ATOMIC_ACTION` 路由至 `_run_capability()`；待决资源提案的显式接受门无法覆盖这些早期分支。

此外，`tests/test_phase8i_handoff_route_matrix.py` 中的 Harness 将输入固定为 `TurnDecisionKind.TASK_PROPOSAL`，因此目前的矩阵不能代表完整的上游分类及真实路由行为。

必须以这些已报告的事实作为回归基线，禁止将 E6 记录简单删除或改为 PASS。

## 2. 安全约束

继续复用现有实现：

- `MinecraftChatBridge`
- `classify_handoff_reply()`
- `_pending_handoffs`
- `_accept_pending_handoff()`
- 既有木材/资源任务入口
- 原有批准门、执行确认门、Policy、授权及逐步后置验证

不得新增工具、执行器、权限、并行任务状态机或数据库 schema。

不得修改 `ACTION_RISK`、`TOOL_ACTION`、`allow_medium` 默认值、任务授权、冻结计划或 STOP/CANCEL 的既有安全语义。

不得以放宽导航超时、距离或阈值解决本问题。

## 3. 修复要求：待决提案仲裁不应依赖上游分类结果

审计 `_route_turn()` 的入口、所有提前返回分支，以及待决提案创建、接受、取消与清理的完整路径。

为同一 `(username, session_id)` 中存在的待决提案建立确定性的仲裁位置。它必须能够在正常的早期路由返回之前，识别当前消息对待决提案的含义；但不能使普通聊天消息普遍获得执行能力。

要求：

### 3.1 明确接受

如果 `classify_handoff_reply()` 将消息判为 `ACCEPT_PROPOSAL`，且同一用户和 session 存在有效待决提案：

- 消费该提案恰好一次；
- 调用既有 `_accept_pending_handoff()` 与原有资源入口；
- 仍须经过既有批准和执行确认；
- 不得让同一条接受消息继续进入 `_run_capability()`、`_delegate_task()` 或其他普通任务入口而意外推进另一任务；
- 没有有效待决提案时，不得凭接受词单独创建资源任务。

### 3.2 明确拒绝与取消

拒绝、取消或 STOP/CANCEL 必须按各自既有语义处理，并保证待决提案不被复活。

如果取消信号还必须停止正在执行的真实任务，应沿用现有权威取消入口，不能只删除待决提案就假定活动任务已经停止。

### 3.3 新目标

新的合成或采集目标不能消费旧提案，必须按当前消息本身的语义继续走原有路由。

例如：「砍五根白桦原木」不得变成「砍橡木原木 2 根」。

对探索、跟随等不属于当前合成或木材分类器的真实新意图，不能为了保留待决提案而吞掉用户输入；也不能为了匹配新意图而消费旧提案。必须证明该消息仍进入正确的既有路由。

### 3.4 询问与歧义

普通询问和无法确定的表达不得消费待决提案。

如果这些消息本身是正常查询，应继续得到正常查询行为；待决提案仍须遵守 TTL 与同用户、同 session 隔离。

不能把所有消息强制变成任务提案，也不能要求用户只能使用一种固定接受词。

## 4. 回归测试：必须测试分类结果的变化

扩展 `tests/test_phase8i_handoff_route_matrix.py`。保留原有 27 条测试，不得删除既有断言。

测试必须覆盖两层。

### A. 确定性仲裁单元测试

验证有效接受、否定、取消、询问、歧义、新合成目标、新采集目标及无关任务的行为。

### B. 完整桥接路由测试

不再把所有消息固定为 `TASK_PROPOSAL`。让测试覆盖真实决策入口或显式回放捕获到的不同 `TurnDecisionKind`，至少包括：

- `TASK_PROPOSAL`
- `QUERY`
- `ATOMIC_ACTION`
- 实际存在且会导致不同提前返回的其他类别

针对完全相同的用户接受消息，改变上游 `TurnDecisionKind`，证明待决提案仲裁结果仍然一致。

必须新增与 E6 同构的回归用例：明确接受语被分类成非 `TASK_PROPOSAL` 时，必须仍能正确消费有效提案；不得转而推进先前的白桦任务。

对所有路径断言任务 ID、任务 objective、待决键状态、接受次数、动作轨迹及 `action_id`。

## 5. 真实服务器验证

使用真实 Java 服务器、真实 MinecraftService、真实 Provider，并尽可能使用第二个 Mineflayer 客户端。

至少复现：

1. 创建橡木资源提案。
2. 使用「好，去砍橡木原木」接受。
3. 重复执行上述场景，但通过真实决策输出或受控回放使该消息进入非 `TASK_PROPOSAL` 类别。
4. 在存在橡木提案时提交「砍五根白桦原木」，确认它不会消费橡木提案。
5. 在另一个独立 session 中重复合成请求，确认不会跨 session 消费旧提案。
6. 明确拒绝或取消后再次发送接受词，确认旧提案不复活。

第 3 项是本阶段的首要验收项。

需要独立检查：当明确接受语未进入 `TASK_PROPOSAL` 时，是否还有其他任务被创建、恢复或推进。不能仅凭没有 `handoff_accepted` 就断言零副作用。

如果第二客户端不可用，可以使用真实聊天桥事件注入验证控制流，并明确标记替代证据；不可将注入称为第二客户端真机测试。
