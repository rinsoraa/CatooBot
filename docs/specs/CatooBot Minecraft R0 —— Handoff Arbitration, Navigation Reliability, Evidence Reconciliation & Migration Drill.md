## 3. R0.1：交接接受与新目标仲裁的完整闭环

### 3.1 核心原则：对整条消息做决策，而不是只判开头或第一个目标

对每条包含待决 handoff 的消息，系统必须明确地区分以下语义：

1. **纯接受**：例如 `同意`、`可以`、`好的`、`好，就按这个方案来`。只接受当前同用户、同 session、未过期的提案，且至多消费一次。
2. **与提案一致的单目标接受描述**：例如 `好，去砍橡木原木`、`好，去砍原木`、`好，去砍两根橡木原木`、`好，去砍橡木原木带回来`、`好，去砍橡木原木再回来`。完整消费、单目标结构、数量单位和位置均通过后，目标/数量仍只能来自当前提案；继续走原有批准门和执行确认门。
3. **明确的、单一且与提案冲突的新目标**：例如树种/数量不同或新的合成目标。必须作废旧提案，绝不能把旧提案的 `oak_log × 2` 参数带入新目标；消息本身按既有新目标路径重新评估，仍遵循现有授权和确认链。
4. **与提案相容但含第二个动作/目标、未知尾部或多义结构的混合接受**：澄清，不消费、不执行，不解析或替用户选择第二个目标；旧提案继续保留在原 TTL/用户/session 边界内，直到用户明确选择、取消或过期。
5. **明确冲突的新目标，同时又包含第二动作/目标的混合消息**：旧提案作废（用户已经明确表达了不同目标，避免旧授权意外复活）；但混合消息本身不自动执行任何子目标，返回澄清要求用户重新指定一个目标。这个分支不得落入“因为 `NEW_GOAL` 优先，所以把整条消息未经结构校验地交给第一个解析器”的旁路。
6. **无关聊天/查询/普通非接受消息**：不消费提案，且保持已有消息语义；不因存在 pending handoff 就把所有聊天强行拦截。
7. **拒绝/取消/STOP**：维持现有权威语义，立即按既有控制路径处理；已拒绝/取消的提案不得复活。STOP/CANCEL 不可被接受门或模型分类覆盖。
8. **无待决提案、过期、跨用户、跨 session、重复接受**：不创建/消费幽灵提案，不把旧目标带入新上下文，所有结果可审计。

如果当前行为与以上矩阵不一致，先用生产函数最小复现确认根因，再在本任务范围内直接修复，不要把它转交为新 Follow-up。

### 3.2 必测的 NEW_GOAL + 复合动作候选（本任务必须实测，不预设它们已经失败）

待决提案 `oak_log × 2`，以下是必须收录的候选：

| 类别 | 输入候选 | 期望安全语义 |
|---|---|---|
| 数量冲突 + 重复采集 | `好，去砍三根橡木原木再砍橡木原木` | 旧提案作废；不执行混合消息；澄清只选一个目标 |
| 树种冲突 + 第二目标 | `好，去砍五根白桦原木，然后去挖石头` | 旧提案作废；不执行任一子目标；澄清 |
| 合成目标 + 第二动作 | `好，给我做 64 块橡木木板，然后去砍橡木原木` | 旧提案作废；不允许只合成或只采集后忽略另一意图；澄清 |
| 新木材目标 + 无标点第二动作 | `好，去砍五根白桦原木去挖石头` | 旧提案作废；混合消息不执行；澄清 |
| 非提案类别绕过 | 上述输入分别由 `TASK_PROPOSAL`、`QUERY`、`ATOMIC_ACTION` 路由类别承载 | 无论上游 kind 如何分类，pending 仲裁与复合门均不能被绕过 |

- 路由有明确的 `handoff_not_accept` / `handoff_compound_clarify`（或为冲突混合语义新增一个稳定、清晰的原因码），不能既记为普通新目标又静默继续执行子目标；

## 4. R0.2：真实导航可达性和动作失败闭环

### 4.1 目标不是放宽门槛，而是解释失败并保证安全停止

当前已知历史复现：Phase 8I 文档 §7.5 记录 `minecraft_move_to` 的 `step_1` 失败，目标约距 6.8 格、任务 `PAUSED`、后续步骤为 `PENDING`。历史文档将 `goal_near` 视作到达半径语义，并明确不放宽阈值。此次需要基于当前 `main` 和当前真实世界重新诊断：不要假设历史坐标或障碍仍然存在。

禁止以以下方式“修复”导航：

- 调大 `goal_near`/到达半径，放宽安全距离、动作超时或 pathfinder 成功判定；
- 使用 `/tp`、直接改 bot 坐标、直接 Mineflayer 操作或跳过现有 `minecraft_move_to`/ActionRuntime 来制造成功；
- 在失败后无限重试、无限追路、忽略 STOP/CANCEL 或在移动失败后继续挖掘/拾取；
- 将“路径请求返回成功”“到达半径”“世界坐标真实到位”当作同一个证据。

### 4.2 先诊断再修复：必须明确区分的状态

对既有 `minecraft_move_to` → `goal_near` → TaskRuntime 链路，审计真实实现和完整日志，至少区分：

1. 目标坐标或实体选择错误/歧义；
2. 目标观察过期或目标在执行中移动/消失；
3. pathfinder 无可用路径/地形不可达；
4. 路径规划成功但执行中动作失败；
5. 移动超时；
6. 真实位置已在既有 `goal_near` 半径内；
7. 机器人到达附近但目标后置条件仍不满足；
8. 任务被暂停、取消或 STOP；
9. 动作/事件迟到、重复或在任务终态后返回。

不得把所有情况都压缩成单一 “move failed”。使用既有错误类型和 route/trace 字段；若现有字段不够，优先在已有结构化日志中补最少必要诊断信息，不新增 schema 或第二套状态机。日志不得记录密钥、完整 provider 响应或不必要的敏感聊天内容。

### 4.3 必须执行的导航矩阵

每个场景先采真实世界/任务快照，并记录起点、目标、实际距离、维度、相关目标的观察时间/新鲜度、现有到达半径、pathfinder/ActionRuntime 返回和最终任务状态。

| 场景 | 输入/条件 | 通过条件 |
|---|---|---|
| N1 可达目标 | 在真实地形中选择一个当前观察确认存在且可走到的目标；优先重测历史约 6–7 格量级问题（以实际坐标为准） | 通过既有 `minecraft_move_to` 真正移动；结束后独立读取实际位置/目标状态；不能传送；完整记录开始/结束坐标和实际距离 |
| N2 近距离目标 | 一个确定可达且距离在常用路径范围内的目标 | 正常到达并走既有后置条件；不能只因初始距离近就宣告成功 |
| N3 不可达/路径失败 | 使用真实场景里能证明不可达的目标或已有可靠的失败 fixture；不为了测试而破坏正式世界 | 不执行后续挖掘/拾取；状态按既有契约进入暂停/失败/取消的正确分支，并能区分路径原因；无无限重试 |
| N4 目标丢失/变更 | 通过现有模拟/集成测试和适合的真实观察场景覆盖 | 不使用过期坐标盲目执行；停止或按已存在策略重新观察，预算有界 |
| N5 超时/动作失败 | 通过既有 Runtime 层测试注入可控失败，并在真实路径上至少核对一条运行日志 | 失败不被改记为成功；之后步骤保持未执行；错误原因、action ID、task ID 可关联 |
| N6 STOP/CANCEL | 在移动等待/路径失败/可控重试时发 STOP/CANCEL | 控制命令及时权威生效；不被重试或 provider 调用阻塞；晚到事件不复活任务/计划 |
| N7 到达语义 | 一个目标可在既有到达半径内完成，一个目标无法进入该半径 | 严格沿用当前阈值；分别验证“到达成功”与“无法到达”；不通过调大容差让失败变成功 |
| N8 失败后的生命周期 | 移动失败后检查 `PAUSED`/终态/后续步骤状态及再次确认/取消行为 | 状态转换与现有契约一致；不能让任务无限期挂起而又没有可诊断原因或可用控制；没有自动跨过待执行步骤 |

真实世界中如果没有安全、稳定的不可达场景，可由真实服务的可控错误返回配合 Runtime 集成测试覆盖 N3/N5，但必须明确标记哪些属于注入/fixture，不能把它们称为自然地形真实失败。N1 至少必须有真实移动客户端与独立位置核验。

### 4.4 不可达/故障处置要求

- 如果审计证明现有错误处理已满足上述语义，则不重写导航实现，只增补必要测试和文档证据。
- 如果路径失败分类、任务状态、步骤抑制、后置验证或 STOP/CANCEL 有缺陷，直接修根因，不放宽距离/安全阈值。
- 不新增自动搭桥、自动拆障、自动破坏地形绕路等能力；这不属于 R0。
- 真实服务器 N1 成功、N3/N5 有可复现的失败证据，以及 N6 控制权威必须同时通过，才可认定 R0.2 PASS。

## 6. R0.4：真实成功数据库迁移演练（同任务包的独立运维子门）

### 6.1 先找真实旧版本样本，禁止造假迁移

### 6.2 真迁移必须证明什么

对隔离副本使用当前仓库正式迁移入口/迁移代码完成一次真实版本升级，记录：

- 演练前后 `user_version`/项目 schema version 和实际迁移步骤；
- 前后 schema snapshots/fingerprints/diff，新增/变更对象与预期一致；
- `PRAGMA integrity_check` 前后均 `ok`；
- 所有应保留表的行数/关键数据完整性，数据损失仅能是迁移定义明确允许且经证明的转换；
- migration report 明确判为 `migrated`，非 `no_op`；退出码与报告一致；
- 重新运行时按既有迁移契约稳定成为合法 `no_op`，不能二次破坏数据。

不得上传数据库文件或含用户数据的 dump 到 GitHub，不得把本地 DB、日志、密钥或 backup 放入提交。保留本地测试产物与安全的摘要报告即可。

## 8. 修复执行流程：所有工作在一个任务周期内完成

建议按以下顺序推进，不得切成一串独立 Follow-up：

1. **Step A — Baseline & evidence inventory：** 完成 §2，建立证据清单和统一缺陷表。
2. **Step B — Reproduce before modify：** 先跑所有历史案例和 §3.2 新目标复合候选；按 §4.3 重现导航；只读取迁移源库并建立隔离副本。产出修复前结果。
3. **Step C — Root cause classification：** 每个失败归入明确层：消息分类、待决仲裁、目标语法、普通路由、路径规划、ActionRuntime、TaskRuntime 状态、日志相关性或 migration reporting。禁止只用新关键词绕过根因。
4. **Step D — Consolidated fix：** 在一次实现阶段修复所有确认属于 R0 的根因。优先少量、可审计的确定性修复；不造平行架构。所有 mixed-goal 场景 fail closed；所有单一合法目标继续可用。
5. **Step E — Full regression：** R0.1 全矩阵 + R0.2 全矩阵 + Phase 8D/8E/8F/8G/8H/8I 相关回归 + 全量 pytest/ruff/format/mypy/WebUI/CI。
6. **Step F — Real gates：** 用真实第二客户端完成 §7.3 场景；真实导航场景不使用传送/旁路；执行隔离 DB 迁移演练。
7. **Step G — Docs & final audit：** 追加阶段文档、CHANGELOG、R0 Final Closure Report；核验权限区域、敏感信息、镜像与远端状态。
8. **Step H — Final verdict：** 按 §9 DoD 输出 `R0 PASS / PARTIAL / BLOCKED`。报告列全量剩余边界与明确归属。不要在结尾生成“建议开 Follow-up 7”的任务书；本任务是最终 R0 收口合同。

如果 Step B 暴露本任务范围内的新缺陷，直接将其添加到同一矩阵并继续 Step C–H。本阶段允许的迭代是“本任务内部迭代”，不允许每轮新建阶段号或要求用户反复粘贴新任务书。
