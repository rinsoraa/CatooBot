# CatooBot Phase 7F.5.2 — Pre-dispatch Pause Race Closure

## 一、基线与裁定

权威基线：

- Phase 7F.5.1 代码提交：`3ba395ec1367878eef152c551a9105116a0fdf84`
- Phase 7F.5.1 最终发布：`5181e07b7f95f8e7663fdaec23d18b1f0ce175b6`

本阶段是定向并发安全修正，不新增 Minecraft 游玩能力。

已发现问题位于 `app/tasks/runtime.py`：

- `_dispatch_precheck()` 检查任务是否为终态，但没有拒绝 `TaskState.PAUSED`。
- `pause()` 在 `pending_action_id` 为空时，会直接将任务持久化为 `PAUSED`。
- `_dispatch_precheck()` 返回 `False` 后，原来的 `drive()` 仍可能持有旧的 `RUNNING` 内存对象。如果不同时修复这一点，就可能继续循环、覆盖持久化状态，甚至重新发起派发。

**不能仅在 `_dispatch_precheck()` 里补一条 `PAUSED` 判断，就认为问题已经解决。**

## 二、必须修复的安全不变量

### 1. 发出动作前必须确认任务仍可执行

在 `TaskRuntime._dispatch_precheck()` 中，重新读取持久化任务后，必须验证：

- 任务处于明确允许派发的状态，正常派发应为 `RUNNING`；
- 当前步骤仍处于本次派发代次的 `INTENT`；
- 派发代次没有变化；
- 对应的授权仍然有效，且满足原有任务、计划与步骤约束；
- 当前 Runtime 实例满足本次派发的身份要求；
- 任务没有在派发前被暂停、取消、过期、要求重新规划或以其他方式失去执行资格。

任何一项不成立，都不得继续发出本次动作。

### 2. 派发检查失败后，必须同步执行流程状态

不能让 `drive()` 在拒绝派发后继续使用陈旧的 `TaskRecord`。

必须保证：

- 持久化状态已变为 `PAUSED` 或终态时，当前执行流程立即停止；
- 不会通过下一轮 `drive()` 循环重新执行同一步；
- 不会把持久化的 `PAUSED` 覆盖回旧的 `RUNNING`；
- 不会因为当前步骤仍然是 `INTENT`，就在下一轮再次增加派发代次；
- 返回给调用方的任务状态与持久化真相一致；
- 恢复任务仍然必须遵守现有的用户确认、授权时效和重新规划规则。

可以引入明确的阻断结果或状态刷新路径，但不得用吞异常、伪造动作成功或跳过确认来处理。

### 3. 修复授权复核的暂停状态缺口

检查 `TaskRuntime.authorize_step()` 以及 AgentBridge 调用链。

在步骤真正执行之前，授权复核不能仅因为任务不是终态、授权对象仍存在就放行。已经暂停或处于不允许执行的状态时，必须拒绝步骤授权。

同时应梳理 `_dispatch_precheck()` 和 AgentBridge 的实际调用时序，保证用户暂停与派发交错时，安全行为是可解释且可测试的。

不要求机械地增加一把跨整个网络调用的锁。若考虑使用锁、派发租约或其他同步手段，必须先证明不会因 `_pause_ambiguous_dispatch()` 中的 `stop_action()`、Runtime 健康检查或实例变化回调而死锁。

### 4. 明确处理“派发意图已落盘，但外部请求正在进行”的窗口

必须区分：

- 外部动作尚未发出：可以安全拒绝派发，且外部动作计数应为零；
- 外部请求已经发出，但响应或 `action_id` 尚未落盘：无法假定动作没有发生，必须遵循现有歧义和人工核对语义；
- 已知动作正在运行：暂停与停止沿用既有生命周期处理，不能重复派发同一代次。

不能把所有竞态统一处理成“清空状态后重试”。本阶段继续不宣称 exactly-once。

## 三、必须新增的故障注入测试

至少加入以下场景：

1. **暂停发生在 INTENT 落盘后、派发复核前。** 强制在这个窗口执行 `pause()`，验证外部动作未被启动、持久化任务仍为 `PAUSED`，之后没有自动恢复或再次派发。

2. **暂停发生在授权复核前。** 验证 `authorize_step()` 不会仅凭尚未过期的授权放行已暂停任务。

3. **暂停与派发交错，原执行协程持有旧对象。** 验证旧对象不能覆盖持久化的新状态，`drive()` 不会从陈旧状态继续推进。

4. **取消或过期发生在派发意图与真实调用之间。** 验证没有外部副作用时不得派发；若外部请求已经发出，则必须保持既有的歧义处理，不得盲目重试。

5. **Runtime 实例变化和用户暂停同时发生。** 验证无死锁、无二次派发、无未经确认的新动作。

6. **真实派发已经进行中的暂停。** 验证实际动作生命周期与任务状态不会出现“任务已安全暂停但动作仍无记录地运行”的假象；无法确认外部状态时必须如实进入受控暂停与人工核对路径。

测试必须断言外部动作调用次数、任务状态、`authorization`、`dispatch_state`、`dispatch_generation`、`pending_action_id`、`replan_required` 和数据库回读结果。

应使用可控的存储或调用钩子制造并发交错，不要依赖随机 sleep 碰运气。
