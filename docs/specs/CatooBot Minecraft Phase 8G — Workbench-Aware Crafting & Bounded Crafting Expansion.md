## 1. 目标与非目标

### 1.1 必须实现的目标

**G1 — 工作台感知：** 可靠判断工作台是否存在、是否可定位、是否可达，以及观测结果是否过期或不确定。

**G2 — 工作台合成：** 对已有、可达且满足条件的工作台配方，在用户明确提出请求并通过既有确认门后执行真实合成。

**G3 — 有界多步合成：** 将合成计划从最多两级扩展为可配置、可审计的多步 DAG；先使用保守默认值，并由测试证明所有预算和依赖约束均有效。

**G4 — 上下文语义决策：** 保留 Phase 8E 建立的统一 LLM 决策链。所有普通玩家消息继续结合真实上下文进行语义判断；不得恢复到由关键词直接触发合成或工作台操作的模式。

**G5 — 安全闭环：** 每个产生世界副作用的步骤都经过现有授权与执行链，完成后使用真实状态验证；取消、失败、超时、状态不确定时不得谎报成功。

### 1.2 本阶段明确不实现的能力

- 自动放置工作台。
- 自动破坏、挖掘或拾取方块。
- 自动移动、替换或破坏玩家已有的工作台及建筑。
- 未经单独审计的容器打开、物品存取、丢弃、交易或物品转移。
- 新增自由执行的 `minecraft_craft` 能力。
- 为方便实现而修改 `ACTION_RISK`、`TOOL_ACTION`、`allow_medium` 默认值、双确认门或授权规则。
- 通过直接调用 Mineflayer、MinecraftService 或底层 Action Runtime 绕过现有 Policy、TaskAuthorization、TaskStepAuthorization、冻结计划及动作生命周期。
- 将未知的世界状态、库存状态或工作台状态默认为空、可用或安全。
- 为通过测试而放宽冻结的评测标签、伪造工具结果或跳过真实服务器门禁。

若工作台无法使用，系统应明确说明原因，并允许用户选择先放置工作台或稍后继续；但放置工作台的动作不属于本阶段。

## 3. G1：工作台感知

### 3.1 统一工作台状态模型

至少区分以下状态：

- `AVAILABLE`：发现工作台，位置与观测有效，且可达性检查通过。
- `NOT_FOUND`：在已明确的搜索范围内未发现工作台。
- `UNREACHABLE`：已发现工作台，但当前路径或使用条件不满足。
- `STALE`：观察已过期，无法据此执行。
- `UNKNOWN`：观察能力不支持、数据缺失或结果无法确认。
- `ERROR`：观察过程发生明确错误。

具体类型名称可遵循仓库现有枚举风格，但必须保留这些语义差异。

### 3.2 工作台发现规则

1. 使用已有的真实世界观察能力，或实现范围明确的 SAFE 只读观察接口。
2. 工作台搜索必须有明确的距离或搜索范围上限。
3. 返回方块类型、坐标、维度（若可用）、观测时间、来源与可信状态。
4. 区分“没有发现”与“没有能力发现”。
5. 不得将旧世界快照当成当前世界状态。
6. 不得仅凭坐标存在就声称工作台可达。
7. 工作台发现和可达性检查不得修改世界。
8. 维度、位置或世界会话发生变化时，必须使旧定位结果失效。

如果现有路径规划器能可靠判断目标方块可达，可以复用它；否则明确返回 `UNKNOWN` 或 `UNREACHABLE`，不得伪造成功。

### 3.3 测试要求

至少覆盖：

- 工作台在搜索范围内且可达。
- 搜索范围内没有工作台。
- 工作台存在但路径不可达。
- 世界视图过期。
- 世界观察接口离线。
- 方块类型或坐标数据缺失。
- 维度切换、世界重连或位置变化。
- 搜索范围边界与上限。
- 多个工作台的候选选择规则。
- 只读检查不触发动作、任务执行或世界修改。

## 4. G2：工作台合成

### 4.1 执行前置条件

只有同时满足以下条件时，才能创建可执行的工作台合成计划：

1. 用户明确提出了合成目标与数量；存在歧义时先澄清。
2. LLM 通过统一决策链选择合适的 `QUERY` 或 `TASK_PROPOSAL`，而非关键词路由。
3. 当前背包数据可用且足够新鲜。
4. 真实配方查询返回明确、可验证的配方。
5. 工作台存在、可定位且满足执行条件。
6. 配方所需材料、剩余空间、输出数量与步骤预算经过核验。
7. 计划冻结并通过现有用户确认与授权机制。
8. 所有实际合成操作仍通过既有受管任务执行链。

任意条件不满足时，应返回可解释的阻断原因，而不是尝试低层操作。

### 4.2 配方与计划冻结

计划至少冻结：

- 目标物品及目标数量。
- 每步精确的 `recipe_id`。
- 每步输入材料、数量、输出物品与输出数量。
- 工作台需求和工作台定位依据。
- 步骤依赖关系。
- 每步预期库存变化。
- 总材料预算、总操作预算与输出数量上限。
- 执行前置条件、库存后置条件与失败处理策略。

`recipe_id` 必须来自真实查询，不得由 LLM 编造，不得在执行时根据名称重新挑选另一个配方。

用户批准后，如果配方、目标数量、材料需求、工作台条件或步骤结构发生变化，必须重新核验并重新授权。不得在原授权下静默修改计划。

### 4.3 工作台使用边界

本阶段仅允许使用已存在且符合条件的工作台。

不得因为没有工作台而自动：

- 制作并放置工作台。
- 破坏其他方块以腾出位置。
- 挖掘地面或改变周围地形。
- 把物品放入箱子或其他容器。

如果底层合成执行器会自动移动玩家、放置方块或改变世界，必须先明确审计其副作用；不能证明其符合本任务书边界时，不得开放该执行路径。

### 4.4 执行后验证

每步执行完成后，必须检查真实背包变化：

- 目标产物是否增加。
- 输入材料是否按配方预期消耗。
- 是否发生部分完成。
- 是否存在额外或意外库存变化。
- 库存读回是否有效。
- 运行时结果与实际库存是否一致。

工具返回成功但库存不匹配时，必须将该步骤标记为验证失败或状态不确定；不得直接宣布制作成功，也不得自动重试可能导致重复制作的步骤。

## 5. G3：受限多步合成 DAG

### 5.1 目标

将 Phase 8F 的两级深度限制扩展为显式、可审计、可配置的多步任务计划。

不能将简单的递归配方展开直接视为安全计划。每个计划必须经过依赖解析、库存模拟、材料预算和执行可行性检查。

### 5.2 计划构建规则

1. 根据真实配方构建有向无环图 DAG。
2. 先计算当前背包可直接提供的材料，再计算需要由前置步骤生成的材料。
3. 合并相同物品的需求，防止多个分支重复消费同一份库存。
4. 检查配方循环、缺失配方、材料不足、工作台需求及输出上限。
5. 在计划创建阶段计算每一步的预期库存状态。
6. 检查背包空间、输出堆叠及运行时实际支持的数量限制。
7. 在执行前冻结完整 DAG，不能边执行边让 LLM 自由增加步骤。
8. 计划超出任何预算时，应明确拒绝或要求用户缩小目标。

### 5.3 初始预算

以下是 Phase 8G 的保守初始上限，最终数值必须通过现有执行器能力审计与测试确认；若底层限制更严格，以更严格者为准：

- 最多 4 级合成依赖深度。
- 最多 12 个合成步骤。
- 每个目标物品最多 16 个。
- 每个计划限定总输入材料量和总动作数。
- 不允许无限递归、无界配方展开或无界等待。
- 不允许在执行期间自动追加未冻结的步骤。

预算应集中配置，避免散落的硬编码上限互相冲突。

### 5.4 执行策略

默认按依赖拓扑顺序执行。

每一步都必须：

1. 检查前置步骤是否成功。
2. 确认库存和执行条件仍满足冻结计划。
3. 通过现有授权及动作执行机制。
4. 等待真实终态事件。
5. 核验库存后置条件。
6. 记录结果后才允许派发依赖该步骤的后续步骤。

遇到材料变化、世界变化、工作台不可用、取消、超时或库存不确定时，必须停止相关后续步骤。

不得为了继续任务而重新计算一个未授权的新计划。

## 6. STOP/CANCEL、并发与异常

沿用现有 STOP/CANCEL 优先路径，不得要求控制命令等待普通 LLM 语义决策完成。

至少验证：

- 计划确认前取消：零动作。
- 多步任务步骤之间取消：不派发后续步骤。
- 正在执行时取消：遵循已有 Action Runtime 取消语义。
- 迟到的动作终态事件：只收敛状态，不重复派发。
- 重复事件：不重复制作。
- 工具声称成功但库存未变化：验证失败。
- 库存读回失败：不宣布成功。
- 部分完成：如实报告已完成与未完成步骤，不自动重试有副作用的步骤。
- 工作台被移走或失效：停止相关任务。
- 材料被其他玩家消耗：停止并要求重新核验、重新授权。
- 服务重启、世界重连与旧任务恢复：不得恢复未被证明仍然有效的授权。
- 两个并发任务争用同一材料：不得双重承诺同一份库存。
- 两个并发任务争用工作台：明确串行化、资源占用或失败策略。

不得仅依靠任务级互斥来推断整个服务器中没有其他玩家改变背包或工作台状态。

## 7. LLM 语义决策与评测

### 7.1 决策契约

继续使用 Phase 8E 的统一上下文与九类决策体系。

合成意图应进入现有 `TASK_PROPOSAL`；配方和库存查询应进入 `QUERY`。模型可以提出用户意图，但不能决定自己是否拥有权限。

模型输出不得直接提供或覆盖：

- 授权状态。
- 风险等级。
- 用户确认结果。
- 冻结计划哈希。
- `action_id`。
- 执行器内部参数。
- 超出允许范围的能力标识。

这些数据必须由受信任的运行时、计划构建器和权限系统生成。

### 7.2 新增冻结样本

至少建立 24 条独立评测样本，覆盖：

- 普通闲聊与游戏叙述。
- 查询背包和查询配方。
- 需要工作台的合成请求。
- 缺少材料。
- 工作台未知、缺失或不可达。
- 目标物品与材料名称容易混淆。
- 数量过大。
- 多步合成请求。
- 歧义目标。
- 不支持的目标。
- STOP/CANCEL。
- 越权、伪造工具名及提示注入。

在运行评测前冻结样本文本、预期标签、允许的等价结果与版本标识。不得根据运行结果回头修改标签以提高正确率。

### 7.3 评测要求

- 报告总体正确率及逐类分子、分母。
- 分别统计普通语义分类错误与后续计划层拒绝。
- 报告违禁能力命中、伪造授权和无确认副作用次数。
- 记录 Provider、模型、提示词版本、参数和原始结果。
- 每轮评测使用相同的冻结样本；新增样本应单独标注。
- 对分类错误的安全影响作分析，不能只报告总体准确率。

不得把“计划层最终拒绝”记作“模型语义分类正确”。

## 8. 测试矩阵与真实服务器门禁

### 8.1 自动化测试

至少覆盖：

- 工作台状态模型及边界。
- 真实配方与库存计算。
- 多步 DAG 构建和拓扑顺序。
- 材料合并与库存模拟。
- 配方缺失、循环、超预算及数量上限。
- 工作台失效、观察过期和不可达。
- 确认前零副作用。
- 计划冻结和哈希兼容性。
- 逐步库存后置验证。
- STOP/CANCEL、并发与迟到事件。
- Phase 8A–8F 的已有路由、权限、隐私、木材、合成与生命周期回归。

### 8.2 真实 Provider 测试

必须使用实际配置的 Provider 运行，不得将 mock 或固定返回值冒充真实 Provider。

至少验证：

1. 用户提出需要工作台的合成请求。
2. 模型选择正确的受管任务路线。
3. 计划构建器使用真实库存和真实配方。
4. 无工作台时安全阻断。
5. 有工作台时生成待确认计划。
6. 确认前不存在 `action_id` 和世界修改。
7. 越权请求不能扩大执行能力。

### 8.3 真实 Minecraft 服务器门禁

必须使用真实 Minecraft 服务器、真实 Provider 和第二个真实 Mineflayer 游戏客户端发送消息。

至少完成以下场景：

**场景 A：已有工作台的单步合成**

- 在测试世界预先准备工作台与足量材料。
- 从游戏聊天发送合成请求。
- 记录真实决策、真实配方、冻结计划和确认状态。
- 确认前证明没有副作用。
- 通过既有确认门执行。
- 独立读取合成前后库存。
- 证明产物净增、材料净耗与配方一致。

**场景 B：没有工作台**

- 提出需要工作台的配方请求。
- 证明系统报告工作台缺失或状态未知。
- 证明没有自动放置、破坏或其他世界修改。

**场景 C：多步合成**

- 选择可验证的两级以上配方链。
- 证明完整 DAG 在执行前冻结。
- 验证各步骤依赖、库存变化和最终产物。
- 中间步骤失败时证明后续步骤不会执行。

**场景 D：执行中取消**

- 让多步任务进入执行状态。
- 在步骤边界触发取消。
- 证明不会继续派发后续步骤。
- 证明已发生的副作用如实记录，不会被错误宣称为回滚。

**场景 E：状态变化或库存不确定**

- 在可控测试条件下制造材料变化、工作台失效或库存读回失败。
- 验证任务停止，不会基于旧状态继续执行。

每个场景必须保存原始事件、时间戳、请求来源、Provider 结果、任务 ID、动作 ID、前后库存和独立核验结果。

协议级客户端不等于人手操作，报告必须如实说明客户端类型，不得将自动化客户端描述为真人手工测试。

## 9. 数据库、兼容性与受保护区域

### 9.1 数据迁移

优先使用现有持久化结构。

如确实需要保存 DAG、工作台定位或新的状态字段，必须先提交迁移设计，说明兼容性、回滚与旧任务恢复行为。不得为追求“零迁移”而将必要状态仅存于无法恢复的内存中，也不得在未授权情况下新增 schema。

### 9.2 计划哈希

保持旧计划的序列化与哈希兼容性。

只有新计划确实需要新增字段时，才增量修改计划结构。对于没有使用新字段的旧计划，序列化结果应保持兼容；不得通过改写旧字段默认值或排序规则制造无关的计划哈希变化。

### 9.3 必须保护的区域

不得修改或绕过：

- `ACTION_RISK` / `TOOL_ACTION`。
- `allow_medium` 的默认安全设置。
- `Policy` 与两道确认门。
- `TaskAuthorization` / `TaskStepAuthorization`。
- 冻结计划和计划哈希验证。
- Action Runtime 生命周期。
- AgentBridge 的安全执行边界。
- Phase 8E 统一决策契约和上下文可信度规则。

若实现确实需要触及受保护区域，立即停止该子任务，提交影响分析和独立审批提案。

## 11. 最终验收门槛（DoD）

以下条件全部满足，才能裁定 `PASS`：

- [ ] 基线与最终 Git 状态可复现，历史未被改写。
- [ ] 工作台状态区分存在、缺失、不可达、过期和未知。
- [ ] 工作台发现不产生世界修改。
- [ ] 已有工作台的真实配方可以经既有确认链执行。
- [ ] 无工作台时不会自动放置或破坏方块。
- [ ] 多步计划在执行前冻结，并满足依赖与预算约束。
- [ ] 每一步均经过既有授权、执行及真实状态验证。
- [ ] 取消、超时、并发、迟到事件和状态不确定场景均安全收敛。
- [ ] LLM 评测样本和标签在执行前冻结，统计逐项自洽。
- [ ] 真实 Provider 与真实服务器门禁达到要求。
- [ ] Phase 8A–8F 的关键安全回归全部通过。
- [ ] `pytest tests -q`、`ruff check .`、`ruff format --check .`、`mypy app` 和 `git diff --check` 全部通过。
- [ ] 迁移检查结果明确解释；不得将 `ok:false` 直接宣称为通过。
- [ ] 凭据扫描无泄漏，受保护文件审计符合要求。
- [ ] CI 全绿，镜像 HEAD 与 `origin/main` 一致，工作区干净，`scripts/` 不包含应排除的本地脚本。
- [ ] 任务书、阶段文档和最终报告已提交并可从远端核验。

如果工作台感知依赖尚不存在的接口、真实服务器环境无法提供所需场景，或必须扩大权限才能继续，应明确裁定 `PARTIAL` 或 `BLOCKED`，记录缺口及后续提案。不得通过伪造数据、放宽验收标准或绕过安全链取得 `PASS`。

## 12. 最终报告格式

最终报告至少包括：

1. 裁决：PASS / PARTIAL / BLOCKED。
2. 开工与收尾基线 SHA。
3. 每项 DoD 的证据链接或原始产物位置。
4. 工作台状态感知的真实结果与失败路径。
5. 多步 DAG、预算及计划冻结证据。
6. 每步授权、动作终态和库存前后快照。
7. Provider 冻结样本、总体与逐类统计。
8. 真实服务器门禁逐场景结果。
9. STOP/CANCEL、并发和异常回归结果。
10. schema、迁移和旧计划兼容性。
11. 受保护文件差异与凭据扫描。
12. 测试、静态检查与 CI。
13. 最终 SHA、镜像一致性、工作区状态和未跟踪文件。
14. 已知限制、未验证项和下一阶段建议。

**最终原则：** 罐头可以理解并提出制作目标，但是否能执行，必须由真实状态、冻结计划、现有授权链和执行后验证共同决定。工作台感知与多步合成的扩展不得削弱这一原则。
