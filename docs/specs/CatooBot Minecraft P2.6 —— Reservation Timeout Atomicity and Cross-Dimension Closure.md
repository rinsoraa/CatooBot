## 4. 阶段 A：先修复预约生命周期

### A1. 正确性要求

预约准备中的在线身份、会话、当前世界/维度与方块读取仍必须在服务端主线程完成。世界读取不得持有会阻塞 HTTP 取消的全局/请求锁。

必须定义唯一、可解释的提交点，保证：

1. 排队超时、读取中超时、线程中断、调度拒绝、工作异常均不能留下本请求可匹配、可消费的有效预约。
2. 请求已返回 timeout/interrupted 等失败后，任何迟到完成都不能再使预约生效。
3. timeout 与提交并发时只允许一个结果获胜；不得对外返回超时却同时保留成功预约。
4. 提交获胜时返回同一预约的成功结果，不能被随后超时或中断错误地改写为失败；明确说明成功与失败的线性化点。
5. 在完成方块读取后重新验证请求生命周期及必要的会话/身份/维度上下文；不能只在读取之前检查。
6. 准备失败或取消不留下可匹配的半成品；nonce/action 的失败、重试与重放语义有明确测试，不能无意放宽重放保护。
7. HTTP 等待继续有界；禁止以无限 join、持锁执行慢读取或等待整个工作完成来掩盖竞态。
8. 服务端线程内调用不会自等待；线程判定若调整，应基于真实线程身份，不把任意同名线程视为主线程。

实现可采用适合当前结构的请求状态机/有界准备与原子提交机制。选择后必须用实际调用链和竞态测试证明，不能以新增布尔检查代替原子性证明。

### A2. 必需自动化矩阵

| 场景 | 必需断言 |
|---|---|
| 正常快速成功 | 单个成功回复、单个有效预约、事件仅消费一次 |
| 工作异常/缺失执行器/拒绝调度 | 明确失败，零有效预约 |
| 尚未开始即超时 | 排队任务后续执行也不创建有效预约 |
| 已进入方块读取后超时 | 先收到 timeout，再释放读取；最终零有效预约、事件不得 SELF_CONFIRMED |
| 读取已结束、提交前超时 | 取消获胜，后续提交无效 |
| 提交与超时交错 | 分别强制两种顺序，回复与有效预约一致，无双结果 |
| 等待线程被中断 | 保留中断标记，失败后无迟到有效预约 |
| 准备期间会话替换/失效 | 旧请求不能给新会话创建或消费预约 |
| 主线程内调用/同名异线程 | 无自等待；同名异线程不能旁路调度 |
| 原契约 | 维度/UUID/位置/方块/TTL/nonce/action/重复消费/UNKNOWN 断言全部保留 |

竞态测试优先使用 latch/barrier/future 控制时序，所有等待有上限；不要依靠长 sleep 或随机压力替代确定性反例。
先记录旧代码在新增回归中的真实失败，再修复并重跑。将可独立运行的请求生命周期测试纳入 CI；Fabric 依赖的测试仍走完整本地入口并明确边界。

## 5. 阶段 B：新构建 P2 真机补证

### B1. 环境保护与诊断准备

1. 只读确认服务器当前进程、端口、世界目录、现存模组/配置和客户端状态，不中断未核实的其他服务。
2. 通过服务器的受控停止流程保存世界；变更前将世界、待替换 JAR 与配置备份到已授权的位置，记录完整性和哈希，不带入 Git。
3. 构建新 JAR 并运行完整 Java 测试，记录 SHA-256；部署后重新计算服务器实际 JAR，必须完全一致。
4. 使用一次性本机 token 和回环监听。记录服务端版本/模组版本/启动日志、接收端状态和运行端口，不输出 token。
5. 夹具选择独立区域，先记录原方块、实体位置与维度，准备可恢复石室，限定坐标范围、次数、等待和动作预算。
6. 若使用 Windows UI，先遵循 computer-use 技能的初始化、确认和目标窗口规则；命令/协议控制优先复用已核实的现有测试接口，不盲打 UI。

### B2. 同次严格跨维度配对

每次使用新实验 ID、action_id、nonce 和预约 ID。最多三个独立尝试，每个阶段均有明确超时；失败样本全部保留，不无限换方向/换方块搜索。

1. 同版本正向控制：确认选定普通方块和水平挖掘几何能产生真实 AFTER 并正确匹配。
2. 机器人在主世界，服务端读取目标坐标 P 的方块 B，取得有效主世界预约 R；记录会话/UUID/TTL/维度/坐标/方块。
3. 下界同一整数坐标 P 放置同种方块 B，记录独立服务端读数；主世界目标保持不动。
4. 安全转移机器人并有界等待客户端与服务端均稳定处于下界；核验 P 可见、可达、在挖掘范围内，预约仍在有效窗口内。
5. 实际正常挖掘下界 P，必须取得真实 AFTER，事件维度必须为下界、真实事件 UUID 为机器人、前置方块为 B。
6. 该事件不得匹配/消费主世界 R，不得得到 SELF_CONFIRMED；主世界 P/B 仍存在，原预约仍未消费，接收端分类一致。
7. 在同次 TTL 仍有效的条件下回到主世界执行正向消费，验证 R 仍只可能由正确维度/位置/身份事件消费一次；若 TTL 不足或上下文失效，如实记录，不伪装此附加证明完成。

若没有 AFTER、预约已过期、坐标/方块未严格对应、机器人重连更换会话或客户端尚未同步，该次不能计作 G4 通过。
`/setblock` 夹具改变世界不产生玩家 AFTER 时只能 UNKNOWN，不证明外部破坏归因。

### B3. 新构建回归采样

- 正常挖掘 10 次、有效登记窗口内外部命令移除 5 次、他人实际挖掘 5 次；每次目标、登记、事件与前后读数可唯一关联。
- 明确区分登记成功率、AFTER 触发率、正常尝试严格匹配率、UNKNOWN、推送失败、重复/迟到和歧义；不把无事件排除出分母。
- 默认关闭新构建：无归因监听、HTTP/worker、匹配或 outbox 累积，至少两次真实挖掘对照。
- 验证 STOP/CANCEL 不受影子推送/请求等待阻塞、现有产品任务结果不受影子分类影响；缺少真实产品路径证据时，写明源代码隔离与 E2 的证明边界。
- 原样保留旧实验 10/5/9 等历史样本；本轮新构建数据单列，不混写成一次实验。
