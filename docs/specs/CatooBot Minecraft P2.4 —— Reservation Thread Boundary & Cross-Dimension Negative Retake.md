## 2. 缺口 A：预约世界访问必须遵守服务端线程边界

### 当前发现

`handleReserve()` 由 HTTP 服务接收请求后执行。目前路径会调用 `currentDimensionOf(sessionNow)`，随后通过 `currentWorldOf(sessionNow)` 获取世界，再调用世界对象读取方块。

当前代码没有明确把这些世界访问操作调度到 Minecraft 服务端主线程，也没有证明此访问方式在固定运行版本中是安全的。

同时，维度检查、世界选择、目标方块读取和预约创建分成多个步骤，存在状态改变导致结果不一致的可能。

### 必须完成的工作

1. 检查本项目固定环境：
   - Minecraft 1.21.1；
   - Fabric Loader 0.19.5；
   - fabric-api 0.116.17+1.21.1；
   - 当前构建实际使用的映射与 Java 版本。

2. 核实 Minecraft 服务端对在线玩家、当前世界、维度标识及方块状态的线程访问约束。不得仅凭单测通过或偶然真机成功，就宣称跨线程读取安全。

3. 若需要主线程访问，则将预约验证所需的游戏状态读取安排到服务端主线程。不要在 HTTP handler 上直接访问世界状态。

4. 优先把以下操作放在一个有明确边界的服务端主线程任务中：
   - 核验 Session 仍为当前有效 Session；
   - 核验玩家仍在线且真实 UUID 与 Session 绑定身份一致；
   - 获取玩家此刻的当前世界和维度；
   - 校验请求维度与玩家实际维度一致；
   - 在同一个实际世界中读取目标坐标的方块 ID；
   - 只有全部条件满足后，才允许创建有效预约。

5. 不允许继续将 JOIN 时保存的 `session.world` 当作当前世界的权威数据源。

6. 不允许在维度校验结束后使用另一次没有一致性保护的世界读取，让维度检查与方块读数可能分别对应两个世界。

7. 对 HTTP 请求使用有界等待或等效的非阻塞设计。不得无限等待服务端主线程。

8. 如果调度超时、玩家掉线、Session 被替换、世界不可用或读取异常，则拒绝本次预约。

9. 尤其注意超时竞态：不能因为 HTTP 请求已经超时，就让一个尚在队列中的迟到任务随后悄悄创建有效预约。必须设计并测试明确的请求生命周期、超时及提交语义，保证超时请求不会在响应之后产生意外预约。

10. 不得以 `join()` 无限阻塞 HTTP handler 的方式简单掩盖线程问题；也不得在 Minecraft 主线程上等待自己排队的任务完成。

### 必须新增或强化的测试

- 有效在线玩家、正确 Session、正确维度和方块：预约成功。
- 玩家当前维度与请求维度不一致：预约被拒绝。
- 玩家已掉线、Session 已替换或身份不匹配：预约被拒绝。
- 目标世界不可用、方块读取失败：预约被拒绝。
- 调度超时或请求过期：不得事后产生有效预约。
- 从主世界切换到下界后，再次创建预约时必须读取下界当前世界，不得读取旧世界。
- 维度切换发生在请求前后或并发时，结果必须保持一致且安全降级。
- 已成功创建的预约仍保留原有 nonce、TTL、重复 action、精确方块 ID 与 Session 绑定契约。
- 不得通过只构造 `Booking.Session` 对象的纯逻辑单测，宣称真实 HTTP 到 Minecraft 世界读取链已经通过。

必须提供代码位置、测试命令、执行结果和能证明失败时不会留下有效预约的证据。

## 5. G4：跨维度负向真实服务端复验

### 5.1 测试目的

证明机器人先在主世界建立一个有效预约，再在下界实际破坏另一维度中同坐标、同方块 ID 的目标时，不能消费主世界预约，也不能获得 `SELF_CONFIRMED`。

历史基线 `e51873d` 的两次跨维度尝试均未产生真实 `AFTER` 事件，继续保留为历史 `NOT VERIFIED`，不得追溯改为成功。

### 5.2 安全夹具

必须使用新 JAR 和可恢复的测试服务器状态。

先确认目标位置、维度和区块加载状态。可以在下界建造一个封闭的小型石室，避免玩家坠落、接触熔岩或因死亡重生中断测试。

例如，由服务端命令在下界创建石质外壳，再挖空内部：

```text
/execute in minecraft:the_nether run fill 8 60 8 12 63 12 minecraft:stone
/execute in minecraft:the_nether run fill 9 61 9 11 62 11 minecraft:air
```

这里的坐标仅为夹具示例。使用前必须检查区块、实体位置和世界状态，确认不会覆盖重要建筑或玩家资产。不得在未经检查的生产建筑区域直接执行 `fill`。

在执行实际破坏前，必须确认机器人已经稳定处于下界，且 Mineflayer 的玩家位置、维度状态和服务端观察一致。不能将命令返回成功等同于客户端状态已同步。

若跨维度传送后客户端状态尚未同步，不得立即调用 `bot.dig`。使用有界等待观察位置及维度收敛；超时后停止该次尝试并记录，不得无限重试。

### 5.3 测试步骤

1. 先进行新版本的正向控制测试，确认当前 JAR 的 `AFTER` 回调可以对选定方块和几何触发。
2. 在主世界选取一个正常、完整且可恢复的普通方块。
3. 由机器人创建预约，确保预约合法，记录：
   - `reservation_id`；
   - `action_id`；
   - `session_ref`；
   - `session_seq`；
   - 机器人 UUID；
   - 预约维度、坐标、预期方块 ID。
4. 不破坏主世界目标，保留预约。
5. 确认下界对应目标坐标已存在与预约相同的方块 ID，记录当前维度与世界读数。
6. 安全传送机器人至下界的封闭石室，等待客户端状态与服务端状态同步。
7. 让机器人从室内水平方向正常破坏墙上的目标方块，避免脚下方块、短草等历史上容易不触发事件的类型。
8. 若 `bot.dig` 返回 `Digging aborted`，先记录原始错误、位置、维度、玩家状态和服务端日志；不得将错误转换成通过。
9. 如需重新布置夹具，必须使用新目标、新预约及新的关联 ID。保留此前失败样本。
10. 只有真实 `PlayerBlockBreakEvents.AFTER` 出现，才能继续判定该次负向测试是否通过。

### 5.4 预期结果

- 服务端 `AFTER` 事件真实存在；
- 事件 `dimension` 为 `minecraft:the_nether`；
- JSON 的 `dimension` 与真实事件维度一致；
- 事件玩家 UUID 是机器人事件对象实际提供的 UUID；
- 原预约仍然绑定 `minecraft:overworld`；
- 下界事件不能匹配并消费主世界预约；
- 不得产生 `SELF_CONFIRMED`；
- 不得因没有触发事件而假定维度校验正确；
- 事件日志、预约日志及 Python 接收端记录可以通过现有 `event_id`、`reservation_id` 和 `action_id` 等字段关联。

若真实事件没有触发，结果记为 `NOT VERIFIED`，不得以单元测试替代。

- 预约线程与状态一致性问题得到可靠解决；

适用于：

- 代码与自动化测试通过；
- 但 G4 未取得真实 `AFTER`，或线程一致性、超时竞态仍缺乏必要证据；

- 仍可能在错误维度读取方块；
- 超时请求仍可在后台意外创建有效预约；
- 线程访问风险未解决且可能损害运行正确性；
- 负向场景产生错误 `SELF_CONFIRMED`；
- 通过降低断言、删除用例或伪造证据获得表面通过。
