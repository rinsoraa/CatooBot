## 1. 已知缺陷

当前 `app/integrations/minecraft/chat_bridge.py` 的 `classify_handoff_reply()` 采用以下顺序：

`拒绝 → 新合成目标 → 询问 → 接受 → 新采集目标 → 兜底`

`_is_acceptance()` 允许匹配位于消息开头、后接指定标点的接受词。

因此，在存在「采集 2 根橡木原木」待决提案时：

`好，去砍五根白桦原木`

可能先被判为 `ACCEPT_PROPOSAL`，而不是 `NEW_GOAL`。待决提案随后按旧目标 `oak_log × 2` 被消费，而用户当前明确提出的白桦数量目标遭到忽略。

这是 Follow-up 4 验收条件中「新目标不能静默使用旧提案的目标与数量」未完全关闭的边界。

不得只凭原有不带接受前缀的白桦测试通过，就宣告本问题已解决。

## 3. 目标一致性契约

### 3.1 纯接受表达

在存在有效待决提案时，下列表达可以接受当前提案：

- 「同意」
- 「可以」
- 「好，就按这个方案来」
- 「好，去砍橡木原木」

最后一种表达只有在上下文确实表明用户接受当前橡木提案时才可消费提案。它不是授权忽略消息中其他明确目标的通配符。

### 3.2 接受表达与新目标冲突

对下列消息必须新增回归测试：

- 「好，去砍五根白桦原木」
- 「同意，改砍白桦」
- 「可以，不过这次砍五根橡木原木」
- 「好，先跟我去另一个地方」
- 「好，给我做 64 块橡木木板」

如果当前消息明确指定的新目标或参数与待决提案冲突：

1. 不得消费旧提案。
2. 不得将旧提案的目标、树种或数量代入新请求。
3. 按当前消息的自身意图进入既有路由，或者在无法无歧义地区分意图时请求澄清。
4. 只有符合当前提案的明确接受才能触发 `_accept_pending_handoff()`。

特别是树种或数量明确不同的请求，不能因为开头带有「好」「可以」或「同意」，就自动被解释为接受旧提案。

### 3.3 与现有“接受后续述”语义兼容

不要简单地把 `parse_wood_request()` 移到 `_is_acceptance()` 前面，因为「好，去砍橡木原木」本身可以是对当前橡木提案的合理接受表达。

需要明确区分：

- 纯接受：接受当前提案。
- 接受 + 与当前提案一致的描述：可以接受，但目标只能来自待决提案。
- 接受 + 与当前提案冲突的新目标：新目标优先，不能接受旧提案。
- 接受 + 无关新任务：不能消费旧提案，应走自己的路由或澄清。
- 语义不清：fail closed，不消费提案。

实现可以采用带上下文的判定，或在 `_arbitrate_pending_handoff()` 中加入确定性的一致性校验。具体结构由代码审计决定，但不能引入第二套独立授权机制。

### 4.1 测试矩阵

假设当前待决提案为 `oak_log × 2`。

| 当前消息 | 预期结果 |
|---|---|
| `同意` | 消费当前提案一次 |
| `好，去砍橡木原木` | 接受当前提案，不得重复创建任务 |
| `好，去砍五根白桦原木` | 不消费旧提案；按白桦新请求路由 |
| `同意，改砍白桦` | 不消费旧提案；按新目标路由或澄清 |
| `可以，不过这次砍五根橡木原木` | 不静默采用旧数量；按新目标路由或澄清 |
| `好，给我做 64 块橡木木板` | 不消费旧提案；重新评估合成需求 |
| `好，先跟我去另一个地方` | 不消费旧提案；保留原有任务意图处理 |
| `好难` | 不接受，不消费提案 |
| `可以吗？` | 不接受，不消费提案 |
| 明确拒绝或取消 | 作废提案；随后接受词不得复活 |
| 不存在待决提案时说 `同意` | 不创建资源任务 |

### 4.2 路由及状态断言

不能只测试分类器返回值。至少调用真实 `_route_turn()` 与真实 `_arbitrate_pending_handoff()`。

每条负向用例必须检查：

- `_pending_handoffs` 是否按契约保留、消费或作废。
- `_accept_pending_handoff()` 是否被意外调用。
- 实际资源任务入口收到的目标是否正确。
- 任务 ID 与 objective 是否属于当前消息。
- 不存在由旧提案意外创建的任务。
- 不存在意外 `action_id`、执行轨迹或库存变化。
- 对合法的新任务，不要错误地以「任务数量必须为零」阻止正常路由；应确认它走的是自己的既有授权链。

至少覆盖 `TASK_PROPOSAL`、`QUERY`、`ATOMIC_ACTION` 与其他已验证类别，防止一致性修复重新引入 FU4 的跨路由问题。

## 8. 验收标准

只有全部满足以下条件才可 PASS：

- 「好，去砍橡木原木」仍可接受当前橡木提案。
- 「好，去砍五根白桦原木」不会消费旧橡木提案。
- 对同一树种但不同数量的明确新目标，不会静默套用旧数量。
- 与当前提案不一致的合成、探索、跟随或其他新意图不能消费旧提案。
- 原有跨决策路由一致性、取消、过期、跨 session 与双确认契约继续成立。
- 真实服务器证据覆盖至少一个匹配接受场景和一个目标冲突负向场景。
- 所有质量门禁与 CI 通过。
- 不修改权限模型、工具白名单或数据库 schema 来规避问题。

任一目标冲突场景仍能消费旧提案，都必须裁决为 `PARTIAL`。

本阶段只处理待决提案与当前消息目标的一致性；导航可达性、配方变体排序、数据库迁移演练及其他自主行为仍是独立后续事项。
