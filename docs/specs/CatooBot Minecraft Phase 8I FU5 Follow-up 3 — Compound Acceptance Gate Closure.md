## 1. 阶段目标

解决当前复合意图接受门仍可能将第二个目标静默忽略的问题。

待决提案为 `oak_log × 2` 时，当前已知仍可能被错误地判为 `accept_proposal` 的消息包括：

- `好，去砍橡木原木去挖石头`
- `好，去砍橡木原木探索附近`
- `好，去砍橡木原木挖附近的石头`
- 木材目标之后追加了一个现有解析器完全识别不出的目标短语。

当前实现使用连接词、标点切分、跟随/合成解析及 `再` 后续目标判断来检测复合意图，但尚不能保证接受描述的全部文本都被解释。

**本阶段不再通过不断追加连接词和动作关键词来追赶反例，而要建立完整消费的正向许可语法。**

## 2. 不可违反的边界

1. 不新增 Minecraft 工具、执行器、权限、平行任务状态机、数据库 schema、字段或迁移。
2. 不修改 `ACTION_RISK`、`TOOL_ACTION`、`allow_medium` 默认值、Policy、TaskAuthorization、TaskStepAuthorization、两道确认门、冻结计划、`plan_hash`、逐步后置验证、STOP/CANCEL 权威路径。
3. 复用现有 `_arbitrate_pending_handoff()`、`_accept_pending_handoff()`、`_pending_handoffs`、`parse_wood_request()`、`parse_craft_request()` 和 `TaskIntentDetector`。
4. 原有有效修复不得回退。开工先核对工作区、镜像和远端状态；禁止覆盖或丢弃已有未提交工作。
5. 任何不能被完整、确定地解析为许可接受形式的消息均须 fail closed：不消费旧提案、不创建或推进任务、不产生世界动作。
6. 本阶段只收敛提案接受语义，不扩展采集、导航、建筑、战斗或主动生活能力。

## 3. 目标语义契约

### 3.1 允许接受

以下消息必须保持既有合法语义：

- `同意`
- `可以`
- `好，就按这个方案来`
- `好，去砍橡木原木`
- `好，去砍原木`
- `好，去砍两根橡木原木`
- `好，去砍橡木原木带回来`
- `好，去砍橡木原木再回来`

有效提案只能被消费一次。目标、树种和数量必须来自待决提案，不能由自由文本覆盖。

### 3.2 明确冲突的新目标

以下语义必须保持：

- `好，去砍五根白桦原木`
- `同意，改砍白桦`
- `可以，不过这次砍五根橡木原木`
- `好，给我做 64 块橡木木板`

不消费旧提案；遵守既有 `NEW_GOAL` 契约，作废旧提案并交回新目标自身的既有路由或澄清路径。不能将这些情况错误地统一处理成保留旧提案的复合澄清。

### 3.3 复合或未知消息

以下消息必须澄清：

- `好，去砍橡木原木并跟我走`
- `好，去砍橡木原木，然后探索附近`
- `好，去砍橡木原木，帮我挖附近的石头`
- `好，去砍橡木原木，挖点石头`
- `好，去砍橡木原木再去挖石头`
- `好，去砍橡木原木去挖石头`
- `好，去砍橡木原木探索附近`
- `好，去砍橡木原木挖附近的石头`
- `好，去砍橡木原木，帮我找附近的煤`

任何无法被许可语法完整解释的未知尾部，都不能被默认视为无害。

复合或未知消息必须：

- 不调用 `_accept_pending_handoff()`；
- 保留原待决提案；
- 不调用木材、合成、跟随、探索或通用任务执行入口；
- 不执行真实观察、规划、任务创建或 Minecraft 动作；
- 返回明确澄清，说明罐头暂不动手，并要求用户明确只做哪一件；
- 在统一仲裁入口处生效，而不是只在某个 `TurnDecisionKind` 分支内生效。

本阶段不要求识别或执行被澄清的第二个目标。

## 4. 实现方向：完整消费的正向许可语法

先审计以下现有解析器和语义入口：

- `parse_wood_request()`
- `explicit_log_count()`
- `parse_craft_request()`
- `TaskIntentDetector`

然后选择实现方案并记录依据。

可以采用：

**方案 A：给现有解析器增加完整消费信息。** 解析结果不仅要说明识别出的目标，还应能说明哪些字符未被解释。只有所有剩余内容都属于明确许可的单任务语法时，才能接受。

**方案 B：定义窄而明确的正向许可接受语法。** 复用现有 `WOOD_SPECIES`、动作词、数量单位及已验证的收尾语，避免复制维护第二套树种或别名词表。整段文本必须完整匹配，不能从长句抽出一个木材目标后忽略其余内容。

经审计的其他方案也可以接受，但必须先给出确定的语法、判定表、失败行为和测试，再开始修改。

必须满足：

1. 未解释的尾部不能默认为无害。
2. 不通过不断增加关键字黑名单来解决问题。
3. 继续支持已验证的单任务收尾语 `带回来` 和 `再回来`，避免过度拒绝。
4. 区分合法接受、明确冲突目标和无法完整解析的复合/不明输入。
5. 不新增第二套授权机制或任务状态机。
6. 不因上游恰好判为 `TASK_PROPOSAL` 而忽略接受门。
7. 未知尾部若不能被证明属于许可语法，必须澄清而不是猜测。

## 5. 自动化测试矩阵

继续扩展 `tests/test_phase8i_handoff_route_matrix.py`。保留已有测试与断言，不得删除或放宽以取得通过。

### 5.1 合法接受

覆盖 §3.1 中全部表达，断言提案只消费一次、任务目标来自提案，以及允许的单任务收尾语继续通过。

### 5.2 已知复合消息

覆盖 §3.3 中全部消息，尤其必须包括：

- `好，去砍橡木原木去挖石头`
- `好，去砍橡木原木探索附近`
- `好，去砍橡木原木挖附近的石头`

新增测试必须驱动真实 `_route_turn()` 和真实 `_arbitrate_pending_handoff()`，而不只是测试纯函数输出。

每条负向用例必须断言：

- `_accept_pending_handoff()` 零调用；
- 原提案仍存在于 `_pending_handoffs`；
- 出现 `handoff_compound_clarify` 或经审计确认的等价稳定原因码；
- 实际返回非空澄清话术；
- `wood_routes`、`delegate_calls`、`capability_calls` 均为空；
- `plans.calls == []`；
- 没有任务、工具执行、`action_id` 或其他副作用。

### 5.3 未知尾部

构造当前 `TaskIntentDetector` 无法识别的额外目标、未知动作或资源短语，以及无标点、无连接词的连续消息。

逐条证明：只要无法证明整段输入符合许可接受语法，就不能消费旧提案。明确记录应触发复合澄清还是普通不匹配澄清。

### 5.4 生命周期与跨路由回归

继续验证：

- `TASK_PROPOSAL`、`QUERY`、`ATOMIC_ACTION` 等决策类别下的复合消息均不能消费提案；
- 复合消息之后发出纯接受，仍恰好消费一次；
- 拒绝/取消后接受不能复活提案；
- 无待决提案时说“同意”不能创建资源任务；
- 跨用户、跨 session 和过期隔离仍成立；
- STOP/CANCEL 权威及双确认契约不变。

## 9. 最终验收标准

以下全部满足才可裁决 `PASS`：

- §3.3 列出的所有已知无标点、无连接词反例不再消费旧提案；
- 仅当整段接受描述被许可语法完整解释时，才能消费提案；
- 未知尾部不能被静默忽略；
- 纯接受、相容单目标描述及已认可的收尾语继续通过；
- 树种/数量冲突和新合成目标保持既有 `NEW_GOAL` 行为；
- 复合/未知输入保留提案、不调用接受或执行入口，并返回澄清；
- 跨决策类别、用户/session、过期、拒绝、STOP/CANCEL 和双确认契约无回归；
- 自动化测试、真实服务器门禁、静态检查及 CI 两个 Job 全部通过；
- 权限模型和受保护区域未修改，临时脚本/日志没有入库。

若仍有已知消息能够把第二个或未知目标静默吞掉并消费旧提案，必须保留 `PARTIAL`。不能以“自然语言总有边界”为理由忽略已有可复现反例。

**范围声明：** 本阶段目标是建立可审计的正向许可接受语法，不声称理解任意自然语言中的所有语义组合。
