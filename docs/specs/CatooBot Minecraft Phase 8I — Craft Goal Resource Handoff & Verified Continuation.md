## 1. 核心目标与边界

### 1.1 必须实现的目标

**H1 — 缺料诊断**

当用户请求合成目标时，先沿用 Phase 8H 的真实库存、配方候选和有界 DAG 规划。

如果计划无法完成，系统应返回可解释的缺料信息，包括实际缺少的材料、数量和相关配方依赖。不得把查询失败、背包读取失败或工作台状态未知伪装为材料不足。

**H2 — 资源任务交接**

当缺少的材料属于现有资源任务能力支持的目标时，系统可基于真实观察提出一个明确的资源获取方案。

资源任务只能复用经过审计的现有规划入口与工具。必须核实实际资源目标、可达性、工具能力及风险要求；不能仅凭缺少某种物品就假设附近一定有可采集的目标。

**H3 — 独立授权与执行**

资源获取属于独立的受管任务。用户提出“制作木镐”不能自动视为已经授权砍树、挖掘或其他世界修改。

用户明确接受资源获取方案后，仍须经过现有 AgentPlan 批准和执行确认流程。不得复用合成计划的授权来绕过资源操作所需的审批。

**H4 — 验证后的合成重新规划**

资源任务结束后，必须重新读取真实背包和必要的真实世界状态，再重新运行合成规划。

不得直接执行资源任务开始前的旧合成 DAG。重新规划的方案必须保留真实配方 ID、预算、依赖关系、工作台定位和逐步后置条件，并遵循现有确认要求。

**H5 — 有界的单次交接**

本阶段只支持一个明确的资源获取交接流程。不开发无人值守的连续采集循环，不在一次用户请求下无限寻找材料、执行资源任务、重规划并继续执行。

如果仍然缺少材料，系统如实说明缺口，并等待用户决定下一步。

### 1.2 明确不做

- 不新增 Minecraft 工具或扩大现有工具权限。
- 不修改 `ACTION_RISK`、`TOOL_ACTION` 或 `allow_medium` 默认值。
- 不绕过 Policy、TaskAuthorization、TaskStepAuthorization 或现有两道确认门。
- 不开放 `minecraft_craft` 为自然语言自由能力。
- 不自动放置或破坏工作台。
- 不自动访问容器、丢弃物品、战斗、跨维度采集或连续挖矿。
- 不把一次制作请求转化为无人值守的长时间自动采集。
- 不在旧计划下静默切换配方、增加步骤或消耗额外材料。
- 不新增数据库 schema、字段或迁移。
- 不因测试失败而删除断言、放宽预算或绕过真实状态核验。

## 3. H1：准确的缺料诊断

### 3.1 只使用可信事实

缺料信息必须来自真实库存与真实查询结果。

区分至少以下情况：

- `insufficient_material`：配方存在，但当前库存及允许的前置合成链不足以满足目标。
- `no_recipe`：真实配方查询没有提供可用配方。
- `crafting_table_required`：缺少满足条件的工作台，或工作台状态不能支持执行。
- `inventory_unavailable`：无法可靠读取背包。
- `search_budget_exceeded`：配方候选搜索超过既有预算。
- `recipe_cycle`、深度或步骤预算超限等其他既有原因。

继续复用 Phase 8H 已有稳定原因码。不得将未知或查询失败统一翻译成“缺少材料”。

### 3.2 资源交接的适用条件

只有当缺失材料能够映射到现有资源任务支持的具体目标时，才可以提出资源获取方案。

例如：

- 合成目标缺少橡木原木，而真实世界观察发现可达的橡木原木方块，并且现有资源任务具备相应能力时，可以提出获取橡木原木的提案。
- 目标缺少材料，但周围没有可确认的采集目标时，不得假设目标存在；应说明目前无法建立可执行的资源计划。
- 缺少的物品需要工作台制作、容器操作、战斗或未支持的工具时，不得把这些行为包装成当前已具备的资源能力。

只有通过真实观察与现有能力校验的目标才能生成可执行提案。

## 4. H2：资源任务提案与用户交接

### 4.1 默认行为

当用户提出合成请求而规划器发现缺料时，默认先返回诊断结果和一个可选的资源获取提案，而不是自动执行采集。

提案必须说明：

- 原合成目标及数量。
- 实际缺失的材料与数量。
- 为什么当前合成计划不可行。
- 资源获取目标来自什么真实观察。
- 资源任务预计执行哪些已有步骤。
- 可能发生的世界修改与实际风险。
- 哪些前置条件仍未满足。

不能把提案等同于已经建立执行任务，更不能把提案等同于用户已经批准。

### 4.2 统一决策契约

继续使用 Phase 8E 的统一语义决策体系。

必须区分：

- 单纯询问“为什么做不了”——只读查询。
- 提出制作目标——受管合成任务提案。
- 明确要求获取材料——受管资源任务提案。
- 仅仅接受资源规划建议——按现有生命周期推进，不能直接开始执行。
- STOP/CANCEL——继续沿用既有优先路径。

不得仅靠关键词把普通闲聊或材料查询自动转成资源采集任务。

### 4.3 授权要求

资源获取方案必须使用既有 AgentPlan、批准与确认机制。

用户没有明确接受资源获取方案时：

- 不执行资源动作。
- 不产生资源任务的有效执行 `action_id`。
- 不修改世界。
- 不因原始合成请求而自动开始采集。

用户接受方案后，所有资源动作仍须符合现有 Policy、风险、前置条件、预算及授权校验。不得将资源获取与后续合成合并成一个绕过确认的执行链。

## 5. H3：资源任务执行及结果交接

### 5.1 复用现有执行链

资源任务必须沿用现有唯一执行链。不得建立新的执行器或让合成规划器直接调用破坏性 Minecraft 工具。

所有资源步骤必须通过现有工具注册、风险验证、授权、Action Runtime 和 TaskRuntime。

### 5.2 资源任务结果判定

资源任务完成后，不得只根据工具返回成功就认为材料已获得。

必须读取真实背包，验证目标物品的净增与实际任务需求相符。如果资源任务结束但背包未出现足够材料，必须如实返回结果，不得继续制作。

以下情况都必须安全终止后续合成：

- 资源任务失败、被暂停或被取消。
- 实际获得的材料不足。
- 读取背包失败。
- 外部操作改变了目标状态。
- 观察过期、目标不可达或关键前置条件失效。
- 资源任务的终态事件迟到、重复或不确定。

已经发生的世界修改必须如实记录，不能声称取消会自动回滚，也不能因超时而重复执行可能有副作用的操作。

### 5.3 重新规划

只有资源任务成功终结、真实库存验证通过且用户仍有继续目标时，才可重新调用合成规划器。

重新规划时：

1. 读取新鲜真实背包。
2. 重新查询所需配方；需要工作台时重新验证工作台状态。
3. 根据当前真实状态重新建立完整 DAG。
4. 重新计算库存净值、材料需求与全部预算。
5. 重新冻结配方、依赖关系、工作台坐标和逐步后置条件。
6. 通过既有确认与授权机制批准新的合成方案。

旧合成计划不得因为与新计划的目标相同，就被视为仍然有效。

**本阶段不得自动连续执行多次资源获取任务。** 一轮资源任务后若依然缺料，应将新的缺口交还用户，而不是无限循环。

## 6. H4：任务关联与连续性

优先使用现有任务记录和任务元数据将资源获取结果关联回原合成目标。

需要明确区分：

- 原始用户目标。
- 原始合成计划及其拒绝原因。
- 被批准的资源任务。
- 资源任务的真实结果与库存净变化。
- 重新规划生成的新合成计划。
- 新计划的批准、确认及执行结果。

关联信息只需满足追溯和正确性要求，不要为了跨步骤关联新增数据库 schema。优先使用现有记录、checks 或其他已支持的任务上下文。

如果进程重启、任务恢复或上下文不完整后无法证明关联仍然有效，应要求重新确认，不得自动恢复旧的执行授权。

本阶段不存储模型思维链，不复制完整世界快照，也不将非必要的原始聊天数据写进 Minecraft 任务记录。

## 7. H5：自动化测试与安全回归

### 7.1 缺料和提案测试

至少覆盖：

- 背包材料充足时，合成计划直接进入原有合成任务流程。
- 缺少原始材料且存在真实可达目标时，生成资源任务提案。
- 缺少材料但不存在已确认的资源目标时，明确报告不能建立执行计划。
- 缺少材料但只存在未支持的资源获取能力时，明确拒绝扩展能力。
- 背包读取失败或配方查询失败时，不得把失败解释为普通材料不足。
- 普通查询不会自动创建采集任务。
- 用户没有明确接受资源提案时，资源任务没有执行副作用。

### 7.2 授权、执行与验证测试

至少覆盖：

- 资源提案批准前没有执行。
- 执行确认前零世界修改。
- 资源任务每个动作仍通过既有 Policy、授权和风险验证。
- 工具返回成功但真实库存没有相应变化时，不触发后续合成。
- 实际材料增加量不足时，不触发后续合成。
- STOP/CANCEL、迟到事件、重复事件、任务暂停、重启与恢复按既有生命周期安全收敛。
- 资源任务后真实重读库存并重新生成合成计划。
- 原计划内容变化后必须重新冻结并授权。
- 新合成计划失败时没有被静默切回旧计划。
- 资源交接不会新增数据库迁移或平行状态机。

### 7.3 真实服务器门禁

使用真实 Minecraft 服务器、真实 CatooBot Runtime、实际生产 Provider 和第二个真实 Mineflayer 客户端作为游戏聊天输入。

至少完成：

**场景 A：缺料 → 资源提案 → 合成完成**

- 使用真实背包确认缺少目标材料。
- 由真实世界查询找到一个确实可达、可被现有资源能力处理的目标。
- 第二个客户端提出制作请求。
- 真实 Provider 使用统一决策链产生受管任务路径。
- 系统解释材料不足并提出资源获取方案。
- 确认资源提案前零执行副作用。
- 用户通过既有门槛批准并确认资源任务。
- 资源任务完成后独立读取背包，确认实际获得材料。
- 基于新库存重建合成计划。
- 经新的确认与授权后执行合成。
- 独立核验最终产物、材料净耗和整个过程的任务关联。

**场景 B：资源获取失败**

- 在可控测试条件下让目标不存在、不可达或关键前置条件失效。
- 系统必须拒绝执行或将已有任务安全终止。
- 不得反复采集，不得伪造获得材料，也不得继续执行旧合成计划。

**场景 C：获取资源后材料依然不足**

- 实际资源任务成功，但最终库存不足以完成目标。
- 重新规划应如实报告剩余缺口。
- 不得自动开启第二轮资源获取任务。

**场景 D：中途取消或外部状态改变**

- 验证实际副作用与终态准确记录。
- 不自动回滚或重复执行资源动作。
- 不继续触发后续合成。

所有场景必须保存实际 Provider 结果、任务状态、授权记录、动作 ID、服务器事件、前后库存和独立核验结果。

真实 Mineflayer 客户端必须如实注明为自动化客户端，不得描述为真人手工聊天。

以下条件全部满足才能裁定 `PASS`：

- [ ] 现状审计已完成，所有新增行为复用已有工具与执行链。
- [ ] 缺料信息来自真实库存与配方规划，并能区分查询失败、材料不足和预算问题。
- [ ] 有效资源目标必须由真实世界观察与现有能力校验确认。
- [ ] 合成请求不会自动授权资源获取。
- [ ] 资源获取提案批准前没有执行副作用。
- [ ] 资源任务沿用既有两道门、Policy、风险映射和授权机制。
- [ ] 资源结果由真实背包核验，不依赖工具自述成功。
- [ ] 资源任务终结后必须重新读取状态并重新规划，不复用旧合成计划。
- [ ] 后续合成重新冻结并重新授权。
- [ ] 单次交接有硬边界，不会无限循环采集或自动连续合成。
- [ ] STOP/CANCEL、失败、部分完成、迟到事件和外部状态变化安全收敛。
- [ ] 自动化测试、既有回归与适用真实服务器门禁通过。
- [ ] 不新增工具、权限、schema 或平行执行系统。
- [ ] 代码、文档、CI、最终提交和镜像状态可复核。

**裁决规则：**

- `PASS`：授权、安全、库存核验和真实端到端交接门槛全部通过。
- `PARTIAL`：核心实现完成，但真实资源任务或后续合成闭环缺证据。
- `BLOCKED`：现有工具、真实环境或权限边界无法支持目标，且需要独立提案。

不得通过自动采集、跳过审批或复用旧计划获取 `PASS`。

4. 缺料诊断和资源提案的决策契约。

11. 未解决边界、真实环境缺口和下一阶段建议。

**最终原则：** 罐头应能理解玩家想完成的游戏目标，并把观察、资源获取、制作和结果验证连接成连贯的体验；但每个具有副作用的任务仍由真实状态、明确提案、既有授权和执行后验证控制。把这些环节接起来，不等于把角色变成无人值守的自动采集脚本。
