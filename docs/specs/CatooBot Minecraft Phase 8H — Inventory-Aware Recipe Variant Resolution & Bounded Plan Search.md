## 1. 必须解决的实际问题

### 1.1 已确认的失败模式

当前 `app/tasks/planner.py` 中的 `craft_recipe_of()` 会按真实配方的 `available` 字段优先选择可立即制作的变体；但当所有变体均 `available: false` 时，排序最终退化到 `recipe_id` 字母序。

Phase 8G Follow-up 已有的真实证据是：

- 请求目标：`wooden_pickaxe`。
- 真实工作台配方查询共返回 11 个变体。
- 背包没有木板，但可能有橡木原木和木棍。
- 所有木镐变体都不可立即制作。
- 当前排序会先选到类似 `!wooden_pickaxe*1=acacia_planks*3+stick*2` 的变体。
- 即使背包内的橡木原木能够通过真实橡木原木配方转化成木板，错误变体也可能让规划器提前报告材料不足。

因此，**`available: false` 不等于该配方在现有受限合成 DAG 中不可实现**。它只说明当前观察下不能直接满足该配方的即时材料要求；规划器还需要评估其前置材料能否通过其他真实配方获得。

## 2. H1：有界、库存感知的配方候选解析

### 2.1 目标

将当前“每种物品只挑选一个配方”的逻辑，增量调整为：

1. 获取真实运行时允许使用的配方候选。
2. 对每一个候选配方，评估当前真实库存及已允许的前置合成配方是否能满足材料要求。
3. 在已有深度、步骤、材料和数量预算内，寻找完整可行的合成路径。
4. 选择确定性、可解释的候选计划。
5. 若不存在满足条件的完整计划，则明确拒绝，并提供可信的材料不足、配方缺失、预算超限或工作台不可用原因。

可以调整现有 `craft_recipe_of()` / `RecipeSpec` / `build_craft_plan()` 的接口，但必须先审计调用者，采用最小必要改动，避免给现有 2×2、3×3、木材任务和任务恢复机制带来无关变化。

### 2.2 配方候选来源

所有候选必须来自实际 `minecraft_recipe_lookup` 返回值。

禁止：

- 硬编码木镐、木板或其他 Minecraft 配方。
- 由 LLM 自行编造 `recipe_id`。
- 仅凭物品名称拼接配方 ID。
- 因查询返回为空或异常就假设某配方存在。
- 用旧缓存或过期的库存状态证明材料足够。
- 因某候选目前不可用，就跳过其完整的前置材料可行性评估。

当不带工作台的真实查询返回 `crafting_table_required` 时，必须沿用 Phase 8G Follow-up 的既有路径：真实观察工作台、检查其可用性，并按当前工作台坐标重查配方。工作台状态未知、过期或不可达时，不得伪造候选可用性。

同一物品可能包含 2×2 和 3×3 候选。应在真实接口契约允许的范围内保留所有可选候选，再由规划器评估其前置条件，而非过早锁定单个配方。

### 2.3 可行性评估

对每个候选方案，评估完整目标数量，而不是只评估第一刀：

- 现有库存能直接提供的材料。
- 由该候选配方消耗的材料数量。
- 缺少的材料能否通过真实查询得到子配方。
- 子配方及其依赖能否继续在预算内解析。
- 递归依赖是否出现循环。
- 同名材料是否被正确合并，避免重复承诺同一份库存。
- 多个分支能否共享真实库存中已经拥有的材料。
- 工作台要求是否能够满足。
- 整个计划的步骤、总输入量、产物净值和动作数是否符合既有执行器限制。

在完整计划构建完成前，不允许因为某个子配方单次不可用就立即宣布整个目标不可行。

反过来，也不能因为每一种材料“似乎都能找到某个配方”，就假定整个计划可行。必须完成完整 DAG 的库存模拟和预算验证。

### 2.4 有界搜索与确定性

候选解析可能形成分支。必须为搜索本身设置明确的集中式预算，不得使用无界递归或无界回溯。

执行前需要根据现有配方规模和预算确定一个保守的 `max_recipe_search_states` 或等价上限，并记录：

- 上限的配置来源。
- 一个搜索状态的精确定义。
- 重复候选、循环依赖和重复子问题如何处理。
- 超过搜索预算时使用的稳定原因码。
- 如何保证相同输入、候选和库存状态产生相同决策结果。

推荐使用有界深度优先或其他可验证的确定性搜索，并结合循环检测、候选去重和必要的记忆化。具体实现方式可由 DSH 根据审计结果决定，但所有边界必须以代码和测试落实，不能只写在注释中。

任何搜索预算超限都应明确拒绝，不得偷偷退化为字母序选择后继续制作。

### 2.5 候选计划排序规则

规划器应优先选择可完成整个用户目标的方案，而不是只挑当前最先返回的配方。

在安全约束相同的情况下，建议采用以下确定性优先级：

1. **完整可行性优先**：能用当前库存及预算内真实子配方完成全部目标的方案，优先于不可完成的方案。
2. **缺失材料最少**：用于诊断不可行候选，不能据此授权执行缺材料的计划。
3. **额外合成步骤更少**：避免为了完成简单请求生成不必要的依赖链。
4. **合成次数及剩余材料浪费更少**：在目标数量、预算和后置条件允许的前提下比较。
5. **前置条件更少**：在其他条件相当时优先使用可行的 2×2 配方，减少不必要的工作台依赖。
6. **稳定决胜规则**：仍然相同的候选才按规范化的完整配方 ID 序列排序。

上述优先级不得覆盖硬约束。任何候选只要缺少必需材料、工作台条件不满足、搜索预算超限或依赖不合法，就不能成为可执行计划。

如果所有候选都不可行：

- 不得选择字母序第一个候选冒充最佳方案。
- 不得返回伪造的可执行 DAG。
- 应使用现有原因码体系，或者提出经过审计的新稳定原因码。
- 如需展示最佳诊断候选，必须明确标记其不可执行并列出实际缺少的材料及数量。
- 不得将“模型判断了正确意图”或“规划器最终拒绝”混记为配方选择成功。

## 3. H2：完整 DAG 的库存模拟和冻结

### 3.1 冻结规则

一旦完成候选解析，完整计划必须冻结：

- 用户目标、目标数量和实际计划数量。
- 每一步的真实 `recipe_id`。
- 真实查询得到的输入数量和产出数量。
- 子步骤依赖关系。
- 工作台要求及观察坐标。
- 每一步的预期库存前后条件。
- 总预算和具体使用的候选路径。
- 计划哈希。

计划在用户确认前可以重新规划，但如果候选配方、输入需求、步骤依赖或目标数量变化，必须重新冻结并重新走现有确认授权机制。

确认后不得静默切换成另一种配方、追加新步骤或重新选择材料来源。

### 3.2 库存计算

计划模拟应以初始真实库存为唯一基线。

必须正确处理：

- 同一材料被多个分支消耗。
- 前置步骤的产物被后续步骤再次消耗。
- 一次制作多件产生的余量。
- 目标要求数量与配方整数刀数之间的差异。
- 每一步的净库存变化和整条计划的最终净变化。
- 由于执行器上限导致的有效步骤数比配置预算更严格的情况。

禁止把某个子步骤的毛产出直接当作最终净增。不得重复使用同一份库存满足两个互斥候选或不同分支的需求。

### 3.3 执行和后置验证

继续沿用当前执行链。每一步必须：

1. 检查前置步骤的实际结果。
2. 核实当前执行条件。
3. 保存执行前的真实背包基线。
4. 经既有授权和动作执行机制派发。
5. 等待真实终态。
6. 使用新鲜真实背包读取核验产物净增与材料净耗。
7. 只有验证通过后才允许派发依赖步骤。

缺少库存基线、执行结果不确定、材料被外部消耗或后置条件不符时，必须 fail-closed；不得自动重试可能已经发生副作用的步骤。

## 4. H3：迁移三态模块边界复核

本项是对 Phase 8G Follow-up 新增代码的针对性审计，不应扩展为数据库迁移框架重构。

审计 `app/database/migration_report.py`：

- `rehearsal_status()` 目前如何使用 `integrity_after`、版本变化和 `lost_rows`。
- `integrity_before` 为什么不参与状态分类。
- `tables_before`、`tables_after`、`added_tables` 为什么只进入报告而不参与三态判定。
- 同样的版本号，但表结构实际发生改变时，是否可能被报告为合法 `no_op`。
- 迁移版本上升、schema 变化、行数损失和合法 no-op 的状态契约是否明确。

### 必须增加的边界测试

- 完整性正常、版本不变、无表结构变化、无行数损失：`no_op`。
- 版本上升且符合迁移契约：`migrated`。
- 完整性失败、版本倒退或已确认的数据损失：`failed`。
- **版本不变但实际观察到 schema/表结构变化**：必须按照明确定义的契约处理，不可默认视为合法 no-op。
- 迁移前后检查存在缺失或不确定结果时，不得伪造健康结论。

如果审计证明现有契约可以接受某种表结构变化，应通过文档及测试说明理由；如果证明存在误报路径，则进行最小修复并检查所有调用方。

不得以修改返回值、跳过检查或硬编码 `ok=true` 的方式通过测试。不得新增 schema、字段或数据库迁移。

**允许的自动化范围**仅为：在用户请求进入原有受管任务链、计划完整冻结并获确认之后，执行计划里已明确列出的合成步骤。

## 7. H6：真实 Provider 与真实服务器门禁

### 场景 A：所有直接变体不可用，但前置合成可行

准备真实测试环境，令罐头的背包包含：

- 足够制作目标的橡木原木。
- 足够制作木镐的木棍。
- 不包含足够木板。

具体数量以所选真实配方的材料需求决定。

从第二个 Mineflayer 游戏客户端发送：

`在工作台上做一把木镐`

要求：

1. 实际 Provider 正确判定为受管 `task_proposal`，不是直接执行工具。
2. 读取真实库存与全部相关真实配方变体。
3. 识别目标配方的前置材料可以通过现有真实子配方产生。
4. 选择正确的可行变体，并在执行前冻结完整 DAG。
5. 将橡木原木转化为木板的步骤和木镐步骤都明确写入计划，或采用实际查询证明的等价合法方案。
6. 所有 `recipe_id` 均来自真实查询，不硬编码。
7. 确认前零合成副作用、零有效执行 `action_id`。
8. 经既有确认授权机制执行。
9. 每个步骤完成后通过新鲜库存读取核验。
10. 独立核对最终木镐产物、材料净耗及多出来的木板。
11. 所有步骤均遵守现有预算、授权与取消语义。

### 场景 B：没有任何可行的候选路径

准备另一个真实输入状态，使目标无法由当前库存和受限子配方完成。

要求：

- 不能随意选取字母序首个候选并生成虚假可行计划。
- 明确报告真实缺失材料或配方原因。
- 确认前没有合成副作用。
- 不自动采集、放置方块或扩大工具权限。

### 场景 C：候选方案发生外部状态变化

在可控测试条件下，使规划后、执行前或多步执行期间的真实库存发生改变。

证明系统不会在旧库存基线上执行不再可行的计划，不会静默改选已批准计划之外的配方，并且失败后不再派发依赖步骤。

### 真实证据要求

必须使用：

- 实际 Minecraft 服务器。
- 实际 CatooBot Runtime。
- 真实生产 Provider。
- 第二个真实 Mineflayer 游戏客户端。
- 正式决策、计划、确认和授权链。
- 独立读取的真实库存快照。

报告中需要说明客户端是自动化客户端，不得把它写成真人手动聊天测试。

保存请求、时间戳、真实查询结果、候选列表、选择理由、完整冻结计划、计划哈希、确认前后状态、每步动作 ID 和终态、前后库存以及独立核验结果。门禁原始日志和凭据不得进入发布镜像。

如果真实服务器环境无法准备所需材料或工作台，必须明确标记 `BLOCKED`，不可用 Mock 结果替代真实闭环。

## 8. 回归、静态检查和 CI

在权威开发目录按实际项目环境执行：

```powershell
pytest tests -q
ruff check .
ruff format --check .
mypy app
git diff --check
```

并确保：

- 完整 pytest 在最终提交前重新通过。
- Phase 8A–8G 的安全回归没有被删除或降级。
- 新增测试不使用硬编码配方冒充真实配方。
- Provider 语义评测继续使用预先冻结的样本，不能根据输出回头修改标签。
- CI 两个 Job 都通过。
- 最终差异没有触及受保护区域。
- `scripts/` 中的本地门禁文件不进入发布镜像。
- 凭据扫描没有泄漏。
- 镜像 HEAD 与 `origin/main` 一致，工作区干净。

如 `minecraft_runtime` E2E 再次出现失败，应保存完整失败日志并比较失败与成功运行的差异。不得把重跑成功写成根因已修复；在没有复现证据时，不应擅自放宽超时、断言或测试环境门槛。

## 9. 最终 DoD

以下条件全部满足才能裁定 `PASS`：

- [ ] 找到并修复（或通过可复核的设计证据排除）配方变体选择的实际缺陷。
- [ ] 配方候选完整来自真实查询。
- [ ] 规划器能够评估前置材料的可合成性，而不只依赖单次 `available`。
- [ ] 搜索和递归有明确预算，循环检测及重复子问题处理有效。
- [ ] 候选排序确定、稳定、可解释。
- [ ] 不可行计划明确拒绝，不会默默退化到字母序候选。
- [ ] 完整 DAG、真实配方 ID、依赖和逐步后置条件在确认前冻结。
- [ ] 预算、库存净值、数量和工作台检查均保持严格。
- [ ] 新增测试矩阵通过，Phase 8A–8G 既有安全回归通过。
- [ ] 真实 Provider 与真实服务器场景 A 达成完整闭环。
- [ ] 场景 B 的不可行路径与场景 C 的外部状态变化均安全收敛。
- [ ] 迁移三态模块的表结构变化与 no-op 边界已明确，有对应测试。
- [ ] 全量测试、静态检查和 CI 通过。
- [ ] 无未授权的工具、权限、schema 或确认链变更。
- [ ] 变更文档、最终 SHA、CI、镜像一致性和未解决事项均可复核。

**裁决规则：**

- `PASS`：所有必需门槛均通过，包括真实服务器门禁。
- `PARTIAL`：主要实现完成，但真实门禁或边界契约仍缺少关键证据。
- `BLOCKED`：当前环境或实际接口限制使核心目标无法在现有安全边界内完成。

不得以单元测试通过、计划生成成功或模型判定正确代替真实配方与库存闭环。

## 10. 最终报告格式

报告至少包含：

1. 裁决与逐项 DoD。
2. 开工基线、收尾 SHA、远端和工作区状态。
3. 原有配方选择失败的最小复现。
4. 运行时真实配方返回契约与候选数量。
5. 配方搜索算法、搜索预算、确定性排序和失败原因设计。
6. 代表性输入下各候选的评估结果、选择理由与完整 DAG。
7. 材料净值、目标产出、逐步后置条件与计划哈希核验。
8. 单元测试及 Phase 8A–8G 回归结果。
9. 真实 Provider 和服务器门禁的原始证据与独立库存验证。
10. 迁移三态模块边界审计结论及相应测试。
11. 受保护文件、schema、凭据和本地脚本审计。
12. CI、最终提交 SHA、镜像一致性与尚未解决的事项。

**最终原则：** 罐头可以根据真实库存和配方提出更聪明的制作路径，但不能通过猜配方、伪造材料、静默切换已批准计划或扩大工具权限来显得聪明。所有替代配方选择都必须发生在确认前，并在完整、受限、可验证的计划中冻结。
