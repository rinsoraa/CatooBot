# CatooBot Phase 7F.5 — Runtime Lifecycle Reconciliation & Bridge Trust Boundary

## 一、任务目标

基于当前 `f31b4ec600b4cebda002abd7c52d5bcaaa452542`，加固 CatooBot Python TaskRuntime 与 Node Minecraft Runtime 之间的信任边界、动作关联及运行时生命周期恢复。

Phase 7F.4 已实现持久化派发意图、派发代次、歧义 fail-closed 和人工核对策略。本阶段不推翻这些机制，而是在其基础上解决已知遗留问题：

1. Python 仍在运行，但 Node Runtime 已重启，导致异步动作事件不再到达。
2. 动作事件只扫描最近 50 条任务，可能错过更早的未决任务。
3. `action_id` 的唯一性依赖当前运行时实例，跨实例关联存在歧义风险。
4. 本地桥接动作 API 仅绑定 `127.0.0.1`，但缺少有效的调用鉴权。
5. 对外部动作状态未知的情况，系统应及时、安全地进入可审计状态，而不是永久等待至 TTL 到期。

这是一个安全性与可靠性阶段，不新增 Minecraft 游玩能力。

## 二、先审计再实施

以当前 `main` 为准，先核对代码、历史提交与工作区，不要假设当前实现与报告完全一致。

重点审计：

- `app/tasks/runtime.py`：`recover()`、`resume()`、`drive()`、`on_action_event()`、`recover_persisted_tasks()`、`_pause_ambiguous_dispatch()`。
- `app/tasks/models.py`：`dispatch_key_of()`、`dispatch_generation`、`dispatch_state`、`recovery` 和相关序列化。
- `app/integrations/minecraft/task_adapter.py`：HTTP 请求、连接错误分类、响应解析与 action_id 关联。
- `minecraft_runtime`：ActionRuntime 的启动、终止、action_id 生成、事件发布、状态端点、服务重启行为。
- `app/core/bot.py`：Node Runtime 生命周期管理与 Python 侧恢复触发。
- 现有 `tests/test_action_dispatch_safety.py` 及运行时 E2E 测试。

先输出一份状态机与故障窗口表，明确哪些状态已被可靠持久化、哪些只能观察到，以及哪些外部事实无法查询。然后制定最小修复计划。

不得假定服务端具有请求去重、跨重启查询或 exactly-once 能力。

## 三、统一运行时实例与动作关联

### 1. 运行时实例身份

审计当前 `action_id` 格式及实际冲突概率。若存在跨 Runtime 实例重用标识的可能，应为每次 Runtime 启动建立一个稳定于该进程生命周期的实例标识，并将其纳入动作关联或事件校验协议。

要求：

- 不同 Runtime 实例产生的动作必须可区分。
- Python 能识别事件属于哪个 Runtime 实例。
- 旧实例事件不能误匹配到新实例的任务。
- 实例重启后，不能仅因动作序号从头开始就把新动作归属到旧任务。
- 不得把实例 ID 当成请求幂等键；它解决的是关联唯一性，不提供服务端去重保证。

优先使用现有协议与序列化模型，不新增第二套任务系统。

### 2. 派发关联状态

保留 Phase 7F.4 已建立的状态语义：

- `INTENT`：派发意图已持久化，但外部是否接受未知。
- `ACCEPTED`：已取得有效的外部 action_id，等待真实终态。
- `SETTLED`：已取得明确终态。
- `AMBIGUOUS`：无法可靠确定派发结果，必须 fail-closed。

所有状态及关联信息必须可持久化、可序列化，并对重复事件保持幂等。

如果没有证据证明外部动作未发生，就不得因超时、重启或连接失败自动重新派发。

## 四、动作事件必须可靠关联，不受最近 50 条任务限制

当前 `on_action_event()` 扫描最近 50 条任务来匹配 `pending_action_id`。审计该限制是否会导致有效终态事件被丢弃。

应优先通过既有任务存储实现完整的未决动作索引或直接查询。索引必须能从持久化任务记录重建，不能只放在进程内存中。

要求：

- 一个已知 action_id 最多匹配一条有效未决派发。
- 多条记录匹配同一 action_id 时，按歧义处理，不能使用“第一个匹配项”猜测归属。
- 未知事件不得改变任何任务状态或授权。
- 旧 Runtime 实例事件不得结算新实例的动作。
- 重复终态事件只被接受一次，消费后的关联必须持久化清理。
- 恢复时，必须能重建所有相关联的未决任务，而非只扫描固定数量的最近任务。

不要为索引引入无必要的数据库表或迁移。优先复用现有 `agent_task_runs.payload` 与可重建索引；若审计证明现有存储无法实现，则先提交设计说明，再决定是否需要迁移。

## 五、Python / Node Runtime 生命周期对账

### 1. 识别 Runtime 实例变化

在现有本地协议上建立轻量的 Runtime 实例身份与健康检查机制。

当 Python 发现当前 Runtime 实例与动作接受时所使用的实例不一致时，应检查所有属于旧实例的未决动作。

不能只依靠某次请求失败推断 Runtime 已经重启；也不能把一次健康检查失败等同于 Runtime 已死亡。

### 2. 对未决动作分类处理

对每个旧实例动作明确区分：

- 有可靠终态证据：按已知结果收敛。
- 有可靠证据证明动作已失效：按既有恢复语义暂停并要求重新规划。
- 外部状态无法确认：进入 `DISPATCH_AMBIGUOUS` 或等价的明确歧义状态，清除旧授权，并要求人工核对。
- Runtime 恢复可用但旧动作状态无法查询：不得仅因为新 Runtime 可用就重新派发旧动作。

状态未知时，安全优先于自动恢复。可以让任务进入受控暂停，但必须保存原因、Runtime 实例标识、action_id、dispatch_key、dispatch_generation 和相关时间戳。

禁止通过伪造动作完成结果、清除歧义标记或自动递增派发代次来绕过人工核对。

### 3. 恢复与重规划

保持既有规则：

- 已取消或已过期的任务不得复活。
- 已派发过的动作不能利用旧授权继续执行。
- 新路线仍须重新观察、生成计划并经过现有授权流程。
- 多段探索在恢复后仍要先核实所有前序路点。
- 未经确认的后续动作不能执行。
- 恢复检查与健康检查本身不得引入新世界动作。

## 六、修复桥接 API 的鉴权边界

当前桥接 API 只监听 `127.0.0.1` 并不等于它已通过调用者身份鉴权。本阶段应审计并加固实际能够触发动作的本地接口。

实施要求：

- Python 与 Node Runtime 之间建立明确的服务端凭据校验。
- 所有动作启动、停止、取消及其他控制端点均应纳入鉴权审计。
- 未提供凭据、凭据错误、凭据缺失或格式错误的请求必须被拒绝。
- 鉴权失败不得触发动作，也不得修改 Task 状态、派发代次或授权记录。
- 凭据不得写入 Git、日志、错误响应、事件摘要或 WebUI。
- 凭据只能通过现有安全配置途径注入，不能硬编码进源码或提交到仓库。
- 正常 Python → Node 请求、健康检查及现有运行时 E2E 必须继续通过。
- 继续绑定受限的本地监听地址，不因鉴权实施而扩大到公网或局域网监听。
- 不得把桥接 Token 视为替代 TaskAuthorization、TaskStepAuthorization 或用户确认门的机制。

如果已有 API 在系统初始化或诊断阶段被匿名使用，必须逐一确认用途并迁移为明确的安全接口契约。不能为了让旧测试继续通过而保留未受保护的动作旁路。

## 七、必须增加的故障测试

### Runtime 生命周期

至少覆盖：

1. 动作派发前 Runtime 尚未启动。
2. 派发意图已持久化、请求尚未发出。
3. Runtime 已接受动作，但客户端响应丢失。
4. Node Runtime 在动作进行中重启，而 Python 不重启。
5. Node Runtime 重启后，新动作产生了与旧动作相同的局部序号。
6. 旧实例迟到事件在新实例启动之后到达。
7. 旧任务位于最近 50 条记录之外，但仍有未决动作。
8. 多条任务记录具有冲突的动作关联标识。
9. Runtime 健康检查暂时失败，但之后恢复。
10. Runtime 已恢复运行，但旧动作的真实状态不可查询。

检查任务状态、授权状态、派发代次、动作启动计数及事件匹配对象。未知时必须暂停或进入歧义状态，不得自动重发。

### API 鉴权

至少覆盖：

1. 未带凭据的动作请求被拒绝且没有副作用。
2. 错误凭据被拒绝。
3. 有效凭据可以正常执行原有允许的调用。
4. Stop / cancel 控制端点也执行相应鉴权。
5. 鉴权失败不改变 Task、授权或 dispatch 状态。
6. Token 不出现在日志、错误响应、事件内容及提交文件中。
7. Python 与 Node Runtime 重启后，凭据注入行为确定且可审计。
8. 现有 WebUI 与 Python → Node 的正常路径仍保持兼容。

所有测试都必须使用真实的请求入口或可验证的协议层测试，不能只断言某个局部函数返回了预期值。
