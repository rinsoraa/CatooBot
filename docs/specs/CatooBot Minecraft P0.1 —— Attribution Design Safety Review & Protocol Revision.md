# CatooBot Server-Side Block Attribution — 设计安全复审与协议修订任务书

## 1. 任务定位

本任务属于 R1 之后的独立能力设计准备，不属于 R1 已通过门禁的返工，也不授权直接实现或部署服务端模组。

产品背景：

- R1.1：PASS
- R1.2：PASS（依据原始 DoD）
- R1.3：PARTIAL，N9-B 仍为 `BLOCKED`
- R1.4：PASS
- R1 总体：PARTIAL

当前问题：真实服务器证据表明，目标方块在 `WAITING_ACTION` 窗口内被外部移除后，现有 `dig` 仍可能报告 `SUCCEEDED`，而归因结果只有 `SELF_INFERRED`、`strict_self_proof=false`。

现有设计：

`docs/specs/CatooBot Minecraft P0 —— Server-Side Block Attribution Design.md`

只允许修订设计和协议，不修改正式服务器、不编写或部署 Fabric 模组、不修改现有授权策略，也不声称 N9-B 已关闭。

## 2. P0：修复 fail-closed 语义矛盾

当前设计在 §3、§4、§5、§6 中对事件缺失和通道故障的处理不一致。

必须先统一以下规则：

1. 只有可信、唯一匹配的服务端玩家破坏事件可以产生 `SELF_CONFIRMED`。
2. 如果动作窗口内目标消失，但不存在对应的严格归因事件，必须保留 `UNKNOWN` 或其他明确的非成功状态。
3. 未匹配事件、外部玩家破坏、身份不匹配、重复/冲突事件、归因通道断开、认证失败、数据缺失和超时，都不得退回 `SELF_INFERRED` 并报告成功。
4. 服务端通道恢复后，迟到事件不得改变既有任务终态。
5. 非成功状态应沿用现有生命周期、暂停/失败语义与审计机制，不得创建第二套任务状态机。
6. 必须区分“没有证明自己挖掘成功”与“已经证明是外部操作”。证据不足时只能报告未知或未确认，不可伪称已经确认外部归因。

请明确说明上述保守策略会如何影响正常挖掘、暂时性服务端故障、服务器重启及断线重连。

不能为了维持表面上的功能可用性而保留已经被真实反例否定的成功判据。

## 3. P0：修正跨进程事件关联协议

目前设计使用 Java 服务端的 `System.nanoTime()` 换算值与 CatooBot 客户端动作时间窗口直接比较。不得假设两个进程的时钟起点一致。

请优先设计以下因果关联方案：

### 动作开始

CatooBot 在派发 `dig` 动作前，通过经过认证的本地控制接口登记一项有界的待匹配记录。至少包括：

- `session_id`
- `action_id`
- bot 当前服务端会话标识
- 目标维度与整数坐标
- `expected_block`
- 唯一关联 nonce 或等价标识
- 服务端登记回执与有效期限

请求登记失败、响应不确定或服务端无法核验目标前置条件时，不得将本次动作当作已经具备严格归因能力。

### 服务端事件

`PlayerBlockBreakEvents.AFTER` 回调时，应取得服务端观察到的玩家、维度、坐标和被破坏前的方块状态。

需要在服务端定义：

- 可信事件的生成时点；
- 破坏后的方块状态如何读取；
- 什么条件才能与某一条待匹配记录唯一关联；
- 匹配记录何时过期；
- 一个事件只能消费一次；
- 一个活动 `action_id` 不能消费其他动作的事件；
- 目标、维度、方块前置条件、玩家身份或会话不匹配时如何拒绝。

禁止通过客户端自报玩家 UUID 或动作时间戳来直接产生 `SELF_CONFIRMED`。

### 动作结束

CatooBot 只消费关联到当前 `action_id` 的可信事件。

以下条件任一成立，都不能以 `SELF_CONFIRMED` 宣告成功：

- 动作结束时仍没有对应事件；
- 多个候选事件无法消歧；
- 事件身份或目标不匹配；
- 服务端确认目标已变化，但找不到对应玩家破坏证据；
- 事件迟到、重复或与当前会话不一致。

如果不能唯一匹配，必须保留可审计的未知或非成功结果。

## 4. P1：明确服务器事件的证据边界

以 Minecraft 1.21.1 Fabric 为目标，继续评估原生 `PlayerBlockBreakEvents.AFTER`。

必须注意：

1. `AFTER` 表示服务端成功执行了玩家破坏方块的事件；事件中的 `BlockState` 是破坏前状态。
2. 不得假设回调参数直接包含破坏后的方块状态。
3. 命令、其他模组或外部系统对世界的修改，不能仅因为与某个动作时间接近就归因于该玩家。
4. 正常事件、取消事件、方块替换、事件监听器异常、服务端重启以及其他玩家同时破坏同一目标，都必须有明确结果语义。
5. `PlayerBlockBreakEvents.AFTER` 只能证明服务端记录的玩家破坏行为，不能自动证明掉落、拾取、库存净增或任务整体成功。

在实现前，用明确的真实服务器实验确认 vanilla 命令 `/setblock` 是否产生所选事件，并测试事件回调读取到的实际方块状态。不以设计假设替代实验记录。

## 5. P1：修正身份与会话契约

当前环境使用 `online-mode=false`。

请把“服务端会话内的玩家标识”与“经过在线认证的账户身份”区分开来。

至少规定：

- UUID 来源与实际含义；
- 当前 bot 连接会话的绑定方法；
- 断线后旧会话与新会话之间如何隔离；
- 同名重连或 UUID 重新解析时，旧待匹配记录如何失效；
- bot UUID 不匹配、未知玩家、重复身份和会话冲突时，如何 fail-closed。

不要将离线模式 UUID 直接描述为在线认证身份。

## 6. P1：认证、重放与通道安全

保留现有本地通道的最小权限方向，但把以下内容写成可测试的契约：

- 仅允许预期本机接口接收归因请求；
- token 和 HMAC 密钥不进 Git、不写日志；
- HMAC 校验失败不得生成可消费事件；
- 事件 ID、关联 nonce 与会话标识必须有幂等与防重放规则；
- 过期事件、旧会话事件和服务器重启前遗留事件不得绑定到新动作；
- 服务端重启后，所有旧待匹配记录必须失效；
- 通道不可用时，系统必须进入非成功归因状态，而不是回退到 `SELF_INFERRED` 并报告成功。

请定义事件接收、验证、唯一匹配、消费和终态提交之间的原子性与竞态处理规则。

## 7. P2：输出最小实现规格

设计复审完成后，应形成可以单独审批的实现规格，至少包括：

1. 服务端模组的最小职责与禁止职责；
2. 客户端到服务端的动作登记协议；
3. 服务端到客户端的破坏事件协议；
4. `action_id`、会话标识、nonce 与事件 ID 的关联关系；
5. 明确的归因状态转换；
6. 超时、丢包、重复、迟到、重启和 STOP/CANCEL 的状态矩阵；
7. 正常挖掘与外部移除的真实服务器实验方案；
8. 部署、版本兼容、配置、监控和回滚；
9. 最小必要日志字段与敏感数据边界；
10. 分阶段实施计划和每阶段的验收门禁。

不新增第二套授权系统，不在服务端模组中直接执行游戏动作，不扩大工具白名单或用户授权。

## 8. 验收矩阵

设计稿必须覆盖并明确预期结果：

| 场景 | 必须达到的结果 |
|---|---|
| 本 bot 正常挖掘，唯一服务端事件匹配 | `SELF_CONFIRMED`；其他成功条件仍须分别验证 |
| 外部 `/setblock air` 导致目标消失 | 无严格归因；不允许任务成功 |
| 其他玩家挖掉目标 | 不归因给 bot；不允许任务成功 |
| 动作窗口内没有收到事件 | `UNKNOWN` 或明确的非成功状态 |
| HMAC 错误或身份不匹配 | 拒绝消费事件 |
| 同一事件重复投递 | 只消费一次 |
| 两个候选动作无法消歧 | 拒绝归因 |
| 服务端或连接通道重启 | 旧记录全部失效；不产生成功归因 |
| STOP/CANCEL 与事件同时到达 | 终态唯一，迟到事件不得复活任务 |
| 方块已移除，但拾取或库存未确认 | 只确认方块破坏归因，不推断拾取或库存成功 |

- 完整状态转换与竞态矩阵；
- 一份实现前风险审查结论；
- 明确的下一步实现范围、权限边界和真实服务器验收计划。

保留旧设计的历史与修订记录。不得声称已经实现、部署或关闭 N9-B。

完成设计审查后停止，等待单独批准实现。
