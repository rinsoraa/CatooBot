## 2. 缺口 A：事件维度必须来自真实事件世界

### 当前已知问题

当前实现的 `Booking.Reservation` 已保存 `dim`，但 `Booking.match()` 的匹配过程没有将事件真实维度作为输入进行比较。

当前事件 JSON 中的 `dimension` 使用类似以下配置值：

`CFG.getProperty("dimension_label", "minecraft:overworld")`

这不能证明事件实际发生在该维度。若事件来自其他维度，日志和归因字段可能错误地报告 `minecraft:overworld`。

### 必须完成的修改

1. 检查本项目固定的 Minecraft、Fabric API 和 Yarn/映射版本，核实 `PlayerBlockBreakEvents.AFTER` 回调参数及真实世界维度 ID 的正确获取方式；不得凭印象猜测 API。
2. 在事件发生时，从实际事件回调提供的 World/世界对象取得维度标识，使用规范、可比较的命名空间 ID，例如 `minecraft:overworld`。
3. 将实际事件维度传入归因匹配过程。必须真正比较：

   - 预约记录中的预期维度；
   - 事件发生时的实际维度。

4. 不得再把配置里的 `dimension_label` 当作事件真实维度。若兼容性原因需要保留该配置，只能用于显示或其他有明确语义的用途。
5. 事件输出中的 `dimension` 必须反映实际事件维度。
6. 当实际维度缺失、无法规范化、预约维度未知或两者不一致时，必须 fail closed：该事件绝不能被标记为 `SELF_CONFIRMED`。
7. 维度不匹配时应使用明确的拒绝原因或降级状态，并保留可审查证据；不得通过回退到默认维度来继续匹配。
8. 核实会话切换维度、重新连接及 Session 替换场景，确保不会使用过期的世界对象或错误的维度假设进行归因。

### 必须新增或强化的测试

- 预约维度与真实事件维度相同：允许继续进行其他必要的匹配检查。
- 预约维度与真实事件维度不同：不得 `SELF_CONFIRMED`。
- 事件维度缺失或未知：不得 `SELF_CONFIRMED`。
- 配置默认值是 `minecraft:overworld`，但真实事件来自其他维度：输出必须是实际维度，或在无法获取时明确降级，绝不能伪报 overworld。
- 维度不匹配不得被误判为 `UNREGISTERED_BREAK` 就足够了，必须明确证明它无法满足 self-proof 条件。
- 现有相同维度预约、TTL、消耗状态、位置及方块 ID 匹配测试不得退化。

## 3. 缺口 B：事件玩家 UUID 必须独立验证

### 当前已知问题

现有事件回调通过玩家名称取得 Session，随后从该 Session 读取 UUID，并将这个 UUID 传给 `Booking.match()` 和事件 JSON。

这意味着 UUID 校验可能只是拿 Session 中预期的 UUID 再与 Session 绑定信息比较，没有独立核验当前事件里的实际玩家。

### 必须完成的修改

1. 在真实事件回调中，从事件自身的 player 对象读取玩家 UUID，核实使用的 API 与当前固定版本匹配。
2. 事件 JSON 的 `player_uuid` 必须取自真实事件玩家，不能用 `session.uuid` 覆盖真实事件身份。
3. `Booking.match()` 的身份比较必须使用实际事件 UUID；不得先用 Session UUID 替换实际 UUID，再进行匹配。
4. Session 查找不能仅依赖玩家名称就认定身份一致。至少必须核验事件玩家 UUID 与 Session 绑定 UUID 的一致性；必要时调整 Session 查询或匹配接口，避免同名玩家、重连、Session 替换等情形产生错误归属。
5. 预约中绑定的 `playerUuid`、`sessionRef`、`actionId` 及现有相关关联字段仍必须按既有契约检查。不得因为 UUID 正确就跳过 Session 一致性检查。
6. 若当前事件玩家 UUID 与预约或当前会话绑定身份不符，该事件绝不能被标记为 `SELF_CONFIRMED`。
7. 对有效但不属于当前机器人 Session 的其他玩家事件，保留真实事件玩家 UUID，并维持既有 `UNREGISTERED_BREAK` 等适用分类；不得错误归属于机器人。
8. UUID 无法获取、Session 不存在或 Session 已替换时必须 fail closed。不能将缺失身份默认成机器人身份。
9. 不得把所有 UUID 不匹配都简单丢弃：应保留现有对其他玩家事件的观察与分类能力，同时确保不产生自证。

### 必须新增或强化的测试

- 实际事件 UUID 与预约 UUID、Session UUID 均一致：在其余条件都满足时可以通过身份检查。
- 实际事件 UUID 与 Session UUID 不同：不得 `SELF_CONFIRMED`。
- 实际事件 UUID 与预约 UUID 不同：不得 `SELF_CONFIRMED`。
- 玩家名称相同但 UUID 不同：不得误归属给原 Session。
- Session 被替换后，旧预约不能通过新 Session 获得自我确认。
- 实际 UUID 缺失、未知或无法读取：不得 `SELF_CONFIRMED`。
- 其他玩家真实事件仍能以实际玩家 UUID 形成正确的非 self-proof 记录。
- 保留现有 Python 接收端对身份、关联字段、事件结构及异常状态的严格校验。

必须明确验证：测试覆盖的是**实际事件身份到匹配器的完整数据流**，而不只是直接向 `Booking.match()` 传入人工构造的 UUID。

## 4. 缺口 C：`enabled=false` 必须真正关闭观测

### 当前已知问题

现有初始化逻辑在 `ENABLED` 为 false 时停止启动 HTTP 服务和 outbox worker，但事件回调仍可能无条件注册并执行，读取事件、调用匹配器、构建 payload 或向队列入队。

这与默认关闭语义不一致，也可能在没有 worker 的情况下积累队列内容。

### 必须完成的修改

1. 核实配置加载与事件监听注册的顺序。
2. 配置确定为 `enabled=false` 时，不应注册此模组的 JOIN/AFTER 归因监听器；不得只依赖“worker 不运行”来声称关闭成功。
3. 在必要的关键入口增加防御性关闭检查，避免任何初始化时序、测试环境或配置状态变化导致关闭模式意外运行观测逻辑。
4. `enabled=false` 时，不启动 HTTP 服务和 outbox worker，不进行 attribution match，不构造或发送归因事件，也不调用 `OUTBOX.offer()`。
5. 关闭模式不能悄悄积累事件；队列不得因未消费事件产生增长或溢出。
6. 保留正常初始化所必需的最低限度配置读取和状态说明。不得为证明关闭而删除必要日志、掩盖配置读取失败或吞掉异常。
7. `enabled=true` 时，既有监听、匹配与投递行为应维持工作。
8. 如果 Fabric 事件 API 或项目架构要求某些回调必须注册，应提供可验证的替代实现，并明确说明为什么它等价于完全关闭；不得仅在报告中声明等价。

### 必须新增或强化的测试

- `enabled=false`：归因事件监听器不注册，或通过可验证的等价机制确保其完全不执行。
- `enabled=false`：HTTP server 未启动。
- `enabled=false`：outbox worker 未启动。
- `enabled=false`：输入挖掘事件不会调用归因匹配器。
- `enabled=false`：`push_ok`、`push_fail`、`outbox_overflow` 不因这些事件产生变化。
- `enabled=false`：队列保持空且不会积累事件。
- `enabled=true`：现有观察与投递测试继续通过。
- 配置缺失或非法时，沿用项目既有安全默认值；不得把配置解析失败意外转换为启用。

测试必须证明运行行为，而不是只断言 `ENABLED == false` 这个布尔值。

## 7. 验收门禁

下列所有适用门禁均必须给出 PASS / FAIL / NOT RUN 及其证据。

| 门禁 | 验收要求 |
|---|---|
| G1 维度匹配 | 真实事件维度参与匹配；字段准确；未知或不一致不得 SELF_CONFIRMED |
| G2 玩家身份 | 事件 UUID 独立获取并向匹配器传递；不一致、缺失、会话替换不得 SELF_CONFIRMED |
| G3 关闭语义 | `enabled=false` 下不注册或不执行归因观测、不启动 HTTP/worker、不入队 |
| G4 原契约回归 | 位置、方块 ID、预约消费、TTL、Session/Action 关联、幂等及异常降级测试继续通过 |
| G5 接收端回归 | Python 校验和安全降级测试通过，未放宽契约 |
| G6 真机证据 | 实际运行本轮构建；按能力边界完成真机复验并提供关联证据 |
| G7 产品隔离 | 产品任务执行链与终态判定无变化；shadow 结果仍不能直接宣告任务成功 |
| G8 工程门禁 | 适用 CI、Java 测试、Python 测试和 lint 结果可复核；无意外脏文件 |

**最终裁定规则：**

- 只有全部适用门禁均 PASS，且必须的真实服务端复验完成，才可考虑将本轮裁定为 `PASS`。
- 若代码与单测修复通过，但真实服务端证据缺失或不完整，应裁定 `PARTIAL`，列出未完成证据。
- 若任一关键身份、维度或关闭语义仍能产生错误的 `SELF_CONFIRMED`，必须裁定 `FAIL`，不得通过降低契约来获得验收。
